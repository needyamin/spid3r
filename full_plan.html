Spid3r → self-hosted · full_plan

Roadmap document — living file, updated as phases complete. Created 2026-11-14 against the audited state of the repository (v1.1.0, LLVM 23.1.0 AOT backend, CI green). This is a plan, not a claim: the progress ledger below records exactly which steps are done; every checkbox carries the decision ID (SH-n) it implements, from docs/SELFHOST.md.

The one rule that governs every checkbox on this page.
A checkbox may only be checked when its Gate — the concrete verification written under the step — has actually run and passed on the real repository, with the evidence (date, command, result) recorded in the Progress ledger at the bottom. If a gate cannot be verified, the step stays open and says why. No fake implementations, no fake results, no “done” without evidence.

Mission

Make Spid3r compile its own compiler, standard library, runtime, and core build tools through the LLVM Native AOT backend, so that future compiler builds do not require Rust. Rust remains forever as the stage-0 bootstrap — the same role it plays in GCC, Go and Rust’s own histories — but day-to-day development and releases become self-hosted.

Scope decisions (owner-confirmed 2026-11-14):
  • Core dev tools are in scope: the self-hosted toolchain must include the test runner, formatter and package tooling. LSP, GUI, agent, debugger and REPL remain Rust-side tools; porting them is an optional late phase.
  • Prebuilt runtime first: during bootstrap the self-hosted compiler links the existing runtime staticlib (AOT trampolines + 230 stdlib natives) shipped as a checksummed, versioned binary artifact. Rebuilding compilers needs no Rust; rebuilding the runtime itself is Phase 9.

Bootstrap chain

Stage 0 — Rust compilertoday’s spid3r; compiles any .matrix program; stays the bootstrap and the parity oracle
→
Stage 1 — Spid3r compilersources in selfhost/, compiled by Stage 0’s AOT backend into spid3r-self
→
Stage 2 — fixed pointspid3r-self compiles its own sources again; the result must work identically

After the fixed point holds, Stage 0 is retired from the build path (Phase 10) and kept only as the historical bootstrap and the reference oracle.

Ground rules (non-negotiable)

GR-1SH No fake implementations, no fake results — including speed

GATE every checkbox on this page carries a verifiable Gate line; the ledger records the evidence. A phase without a passing gate is reported as open, never as done.

GATE no speed claim without benchmark evidence under the phase0 protocol (9 warmups / 21 repeats / 2 passes, MAD gates, startup calibration — tools/phase0_bench.py). Targets are tiered: Tier A no-regression floors (blocking), Tier B measured-improvement targets vs frozen baselines (blocking), Tier C stretch (measured, labeled, never blocking). This discipline exists because earlier targets were formally retired when measured unreachable — docs/PERF_TARGET_RETIREMENT.md.

GR-2SH-5 Engine contract holds at every step

GATE after every merged step: tools/gate.sh 9/9 and tools/difftest.sh ALL MATCH — the tree interpreter remains the semantic oracle throughout (docs/ENGINE_CONTRACT.md).

GR-3SH-7 Security invariants

SEC no new unsafe outside src/native/rt.rs with a written safety argument; the new FFI pointer surface is sandbox-aware (capability-filtered like every native); all artifacts (selfhost binaries, .matrixc, runtime staticlib) carry SHA-256 integrity; the Spid3r-written lexer/parser is fuzzed against the Rust oracle before any parity claim; compiler operations perform no network access.

GR-4SH-4 Frozen corpus contract

DELIV Phase 0 locks a corpus of programs (the 24 examples, the 87-case engine-matrix programs, the hand-built edge corpus, negative/error programs) with committed SHA-256 checksums. Every parity gate in Phases 1–7 runs against this exact corpus; changing the corpus requires a new ledger entry stating why.

PHASE 1 Spid3r-written lexer (~1.2k Rust LOC to port first)

Sources live in selfhost/lexer/ as Spid3r modules, compiled and exercised by Stage 0 (spid3r build / spid3r run), so every phase ships working code before its checkbox moves.

1.1SH-3 · SH-5 Token model + spans

DELIV the token set as Spid3r data (kind, lexeme, byte span line/col/len) matching src/lexer/token.rs; JSON serialization for the parity harness.

GATE the token model round-trips: serialized tokens of the corpus lexed by the Rust oracle re-parse into the Spid3r model without loss.

1.2SH-5 All lexical rules

DELIV integers, floats, bigint 123n literals, strings with every escape, identifiers/keywords, line + block comments, every operator and punctuation form, byte-exact spans — per src/lexer/mod.rs.

GATE token-stream parity (Spid3r lexer vs stage-0 oracle, byte-for-byte JSON) on the frozen corpus; any gap is fixed or the corpus case is diagnosed — no silent acceptances.

1.3SH-5 Lexer errors

DELIV unterminated strings/comments, invalid characters, number errors — same first-error behavior and message text as the oracle.

GATE diagnostic parity on the corpus error programs (phase label + message + span).

1.4SH-5 Fuzz + teeth proof

DELIV the existing fuzz infrastructure feeds random/mutated inputs to both lexers; a deliberately broken comparison harness is proven RED, then restored.

GATE ≥1,000 fuzz cases with zero token-stream differences; teeth test recorded in the ledger; CI parity job green.

GATE · PERF Tier B: selfhost lexer throughput ≥ ½ the stage-0 lexer’s MB/s on the corpus — measured A/B on the same machine under the phase0 protocol (the port must be fast, not just correct).

2.3SH-5 Parser diagnostics

DELIV first-error behavior with identical messages and spans (“expected ‘(’ after match…”, selective-import errors, etc.).

GATE diagnostic parity on the corpus negative programs; fuzz ≥1,000 cases with zero AST/diagnostic differences.

GATE · PERF Tier B: selfhost parser throughput ≥ ½ the stage-0 parser’s (programs/second on the corpus, phase0 protocol).

DELIV the ANF-style desugarings (ternary, ?., ??, enums→constructors, generators, bigints) in evaluation-order-preserving form, per src/lower/mod.rs.

PHASE 5 LLVM-C codegen layer written in Spid3r (~4.5k Rust LOC equivalent — the heart of self-hosting)

DELIV extern fn declarations (using Phase 0’s ptr support) for the exact LLVM C API subset src/native/ir.rs exercises — module/context/builder/type/target-machine/object-emission — discovered by enumerating inkwell’s call sites, kept in one auditable selfhost/llvm/ module.

GATE the declarations compile and a minimal Spid3r program creates a module, builds one function, verifies it, and emits an object that the system linker accepts.

5.2SH-5 Expression/statement codegen

DELIV the ir.rs port: locals/slots, control flow, closures/upvalue cells, classes/vtables, match lowering, try/catch pending-throw protocol, string append buffer, spawn/await — every arm parity-checked against the Rust codegen’s behavior, not reimplemented from imagination.

GATE the Spid3r compiler compiles the corpus to objects; LLVM verify passes; the linked executables answer byte-identically to Stage-0 builds on the corpus.

GATE · PERF Tier B — output-quality parity: corpus programs compiled by the self-hosted compiler run ≤ 1.25× the wall time of the same programs compiled by Stage 0 (the Spid3r codegen must reproduce Stage 0’s optimization quality — loop rotation, fusion, inlining — or the whole language silently gets slower). PHASE 11 Performance engineering — “lightweight and rocket speed”, with receipts

What “rocket speed” honestly means here, in three tiers (the retirement discipline of docs/PERF_TARGET_RETIREMENT.md applies — every tier is a measured number, never a slogan):
  • Tier A — no-regression floors (blocking). The 8 existing bench floors stay enforced; the selfhost toolchain and its outputs get their own floors. A regression that breaks a floor blocks the merge.
  • Tier B — measured-improvement targets (blocking). Speedups vs frozen, checksummed baselines — each landed only with A/B numbers under the phase0 protocol, exactly like the W1–W5 program did (W2.2 −21.8% construction, W3.2 2.63×→1.04× scaling, native prime 3.26× vs VM).
  • Tier C — stretch (measured, labeled, non-blocking). Closing the measured gap to the Node.js and Rust reference points on the shared workloads. These are pursued, published, and retired openly if measured unreachable — never promised.
The reference points are real, not marketing: Node.js and Rust reference implementations of the same workloads already exist in benchmarks/compare/ (prime.js/json.js/map.js, prime.rs) — Phase 11 first measures them under the identical phase0 protocol, then publishes Spid3r-AOT vs Node vs Rust on the same machine, same inputs, same statistics. Where the gap to Rust/Node is structural (JIT vs AOT, boxed dynamic values vs unboxed), the benchmark page says so — honestly, with the measured ratio.
