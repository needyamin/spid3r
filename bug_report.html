Scope. Every module of the toolchain was reviewed: lexer, parser, semantic checker, both interpreters, the bytecode VM (compiler, dispatcher, optimizer, serializer), the LLVM native backend and its extern "C" runtime, the standard library (serialization, crypto/KDF, database wire-protocol clients, media, compression, TOML, regex), the language server, the formatter, the bundler/packager, the WASM C-ABI boundary, the CLI, and the scheduler. Findings were confirmed by executing hostile inputs against real builds; nothing in this report is asserted from code reading alone.

1. Executive summary

The audit found 17 confirmed defects, all of which are now fixed and pinned by regression tests. Six were remotely triggerable from untrusted input (crafted serialized payloads, malicious database servers, hostile LSP frames), three were crash-level bugs in the compilers (panics where diagnostics were required), two were memory-safety issues (an out-of-bounds read in the native backend, an allocation-layout mismatch across the WASM boundary), and the remainder were correctness, resource-exhaustion, or spec-conformance defects.

No finding remains open that is not explicitly documented as an accepted design trade-off in §5 Unresolved & accepted risks. The toolchain is not declared production-ready on the strength of this audit alone: the suite passes, but the residual risks below (notably the text-protocol SQL surface and the native backend's arena memory model) are inherent design properties that applications must account for.

2. Methodology

  • Parallel module audits. Four review passes ran concurrently over (a) front end — lexer/parser/checker/formatter/LSP, (b) standard library, (c) dev tooling — CLI, bundler, packager, WASM, build, and (d) native backend + GUI bridge — each producing candidate findings.
  • Manual re-verification. Every HIGH/MEDIUM candidate was re-verified by hand before any fix: a hostile input was built (audit/probes/), executed against a real spid3r build, and the failure mode observed (panic, abort, signal, wrong output).
  • Differential testing. Programs run on all three engines (tree, VM, compiled+exec); stdout must be byte-identical. Fixes that changed engine-visible behavior were checked for parity.
  • Protocol fuzzing by hand. The MySQL and PostgreSQL clients were driven by purpose-built malicious servers (a Python fake MySQL server for the initial probes, then pure-Rust fake servers inside the regression tests) sending truncated, empty, and oversized messages.
  • Regression pinning. Every fix is pinned by a test in tests/audit_hardening.rs, tests/lsp_tests.rs, or tests/gc_vm_autocollect.rs so it cannot silently regress.

4. Detailed findings

S-1  High  CBOR / msgpack length-prefix handling

src/stdlib/serialize.rs — Reader::take() (~line 187), fn remaining() (171), capacity hints (275, 283, 291, 301, 316, 325, 491, 499)
Symptom
Malicious payloads either aborted the allocator (capacity overflow) or sliced out of bounds.
Repro
cbor_decode(hex_decode("5bfffffffffffffff7")) — 0x5b = byte string with 8-byte length 264−9, chosen so pos + n wraps to 0 and passes the old pos + n > data.len() check. Also cbor_decode(hex_decode("9bffffffffffffffff")) (array, u64::MAX length) and msgpack_decode(hex_decode("ddffffff")) (array32, 0xFFFFFFFF count).
Root cause
take() computed the end offset with wrapping arithmetic, and eight container decoders called Vec::with_capacity(n) with an attacker-controlled n before reading a single element.
Fix
take() now uses pos.checked_add(n) and reports length prefix overflows the input size; a new Reader::remaining() feeds Vec::with_capacity(n.min(r.remaining())) at all eight sites, so the hint can never exceed the bytes actually present.
Tests
cbor_length_prefix_overflow_is_a_clean_error, cbor_u64_array_bomb_is_a_clean_error, msgpack_array32_bomb_is_a_clean_error — all three now print err(...) identically on tree and VM.

S-2  High  PNG dimension bomb

src/stdlib/media.rs — lines 144–151
Symptom
A 69-byte PNG whose IHDR claims 100000×100000 RGBA (40 GB) aborted the process at the pixel-buffer allocation.
Repro
png_decode(hex_decode("89504e47…49454e44ae426082")) (probe audit/probes/p6_png_dimension_bomb.matrix).
Root cause
width * height * channels * bytes_per_sample was computed with wrapping arithmetic and allocated with vec![0u8; total] before any validation of the IDAT stream.
Fix
Checked-arithmetic product (checked_mul chain) plus a MAX_PIXEL_BYTES = 256 MiB cap enforced before allocation; oversized images return png: image is too large to decode.
Tests
png_dimension_bomb_is_a_clean_error (both engines).

S-3  High  Native backend: out-of-bounds argv read on short calls

src/native/rt.rs — lines 439–453 (spid3r_call_inner, Value::Cfn arm)
Symptom
Calling a compiled function with too few arguments killed the process with SIGSEGV (exit 139).
Repro
fn two(a, b) { return a + b; } called through a list — let fs = [two]; let g = fs[0]; g(1); — so the semantic checker cannot see the callee statically and the call reaches generated code unchecked.
Root cause
Generated prologues load argv[offset + i] for every declared parameter. A short call left the tail of the array uninitialized; the garbage handle was later dereferenced as a *mut Value.
Fix
Arity is now checked in spid3r_call_inner before entering generated code (argc < c.min_arity || argc > c.arity), raising the same catchable error the tree and VM engines produce: two expects 2 argument(s), got 1. min_arity covers trailing constant defaults.
Tests
native_short_call_is_a_clean_error_not_a_segfault — builds the program with the LLVM backend and asserts exit 1 with the diagnostic (skipped when LLVM is absent).

S-4  High  break/continue scoping and a VM compiler panic

src/vm/compiler.rs — 541, 558  ·  src/semantic/mod.rs — 1548, 1602, 1622, 1698, 2619, 2663
Symptom
let g = fn() { break; }; inside a loop compiled on the tree engine (error only when the closure was called) but panicked the VM compiler via .expect("break outside loop"). The two engines disagreed about the same program.
Root cause
The checker's loop_depth was not reset at function boundaries, so a closure inherited the enclosing function's loop context; the VM compiler had no diagnostic path for the resulting state.
Fix
Two parts. (1) The semantic checker saves, zeroes, and restores loop_depth at all three function-body entries (function declarations, function literals, class methods), making break/continue lexically scoped to the function's own loops. (2) The VM compiler emits break outside a loop / continue outside a loop diagnostics instead of panicking.
Tests
break_in_a_function_literal_is_rejected, continue_in_a_function_literal_is_rejected, break_without_any_loop_is_rejected (both engines exit 1 with the diagnostic), and the sanity test normal_break_and_continue_still_work (loops inside functions, inside closures, and nested loops print 3, 8, 4, 2 identically on both engines).

S-5  High  LSP frame-size allocation

src/lsp/mod.rs — lines 1315–1316
Symptom
A client announcing Content-Length: 8589934592 crashed the language server with STATUS_NO_MEMORY (3221226505) instead of an error.
Root cause
The frame buffer was allocated with vec![0u8; len] before any bound on len; the 4 GiB (and larger) request was honored by the allocator.
Fix
MAX_FRAME_BYTES = 64 MiB is enforced before the allocation; oversized frames are rejected cleanly and the server keeps serving.
Tests
Verified by probe (server stays alive, exit 0); the LSP session harness in tests/lsp_tests.rs covers the framing layer.

S-6  Medium  LSP positions were not UTF-16 code units

src/lsp/mod.rs — line_at (175), char_to_utf16_col (180), utf16_to_char_col (188), span_range (223), position_of (910)
Symptom
Editors placed diagnostics, hover, rename, and outline selections on the wrong character whenever an astral character (emoji) appeared earlier on the line.
Repro
Open let a = "😀😀😀"; let x: int = "bad";: the diagnostic on "bad" was reported at column 28; the LSP requires 31 (three emoji are six UTF-16 units but three scalars).
Root cause
Spid3r counts Unicode scalars internally; the LSP layer passed those counts straight through instead of converting.
Fix
Conversion helpers added and applied on both edges — outgoing positions (span_range, full_range, document symbols) convert scalars → UTF-16; incoming positions (position_of, used by hover/definition/completion) convert UTF-16 → scalars.
Tests
positions_are_utf16_code_units_not_unicode_scalars — asserts the diagnostic at character 31 (end 36) and the x symbol at 18.

S-7  Medium  Three parser depth-guard bypasses

src/parser/mod.rs — parse_if_expr else-branch (944–962), parse_pattern (1031–1050), interpolation-hole sub-parser (1894–1897)
Symptom
Three source shapes recursed without counting against MAX_PARSE_DEPTH = 64 and overflowed the parser stack: a 300-deep else if chain, 300-deep nested match patterns (a(a(a(…)))), and 20 000-deep string interpolation holes ({h({h(…)})}).
Root cause
parse_if_expr recursed into its else branch without incrementing depth; parse_pattern had no guard of its own; the interpolation-hole sub-parser reset depth and value_block_depth to 0 instead of inheriting them.
Fix
The else-if branch now brackets its recursion with self.depth += 1 / -= 1; parse_pattern enforces the standard guard and increments depth around its body; the hole parser inherits the parent's depth and value-block depth.
Tests
else_if_chain_hits_the_parser_depth_guard, nested_pattern_hits_the_parser_depth_guard (both produce nesting deeper than 64 levels), and deep_interpolation_hole_does_not_overflow_the_stack (asserts the process exits normally — code 0 or 1 — rather than dying on a stack overflow).

S-8  Medium  VM try-offset range (i16 wrap)

src/vm/compiler.rs — message at 1616, patch_try_offset at 1626–1636
Symptom
A function body larger than 32 KiB containing try produced wrapped (wrong or negative) handler offsets — the VM would jump to an arbitrary instruction.
Root cause
Try/catch/finally offsets are encoded as i16; the four offset patches used unchecked casts while patch_jump was range-checked.
Fix
New patch_try_offset with an i16::try_from check; all four try patches use it. Oversized bodies fail compilation with function body too large: bytecode exceeds the 32 KiB jump range (split the function).
Tests
vm_try_body_over_32kib_is_a_clean_error — a 20 000-statement try body: the VM exits 1 with the diagnostic, the tree engine runs it and prints 20000 (see R-4 for the documented divergence).

S-9  Medium  Formatter quadratic amplification

src/fmt.rs — indent() 486–494 (MAX_INDENT_DEPTH = 64)
Symptom
Formatting a deeply nested file produced output quadratic in the depth: a 360 KB probe expanded to 1.6 GB (disk exhaustion / OOM).
Root cause
The formatter is token-based, so it never saw MAX_PARSE_DEPTH; every line was indented by depth * 4 spaces with no cap, and the sum over depth is quadratic.
Fix
Indentation depth is capped at 64 levels (self.depth.min(MAX_INDENT_DEPTH)), bounding the output to a small multiple of the input.
Tests
formatter_indentation_is_bounded — a 20 000-deep file (320 KB) formats to 10.4 MB with the longest line 265 bytes; the test asserts the line-length cap and a 16 MB output ceiling.

S-10  Medium  MySQL client panicked on malformed server packets

src/stdlib/mysql.rs — MAX_PACKET_PAYLOAD (54), head_byte (58), lenenc_bytes (167), column-definition bounds (277), cstr (672)
Symptom
A hostile or broken MySQL server could panic the client process: a zero-length result packet indexed packet[0] directly; a 7-byte column definition read def[after_org + 7] past the end; lenenc integers and C-strings were read without bounds checks.
Repro
Driven by fake servers: audit/probes/fake_mysql.py (Python, discovery) and the pure-Rust fake servers inside the regression tests (empty packet / truncated column definition modes).
Root cause
The client trusted the server's framing and field lengths.
Fix
head_byte() returns mysql: empty packet; lenenc_bytes uses checked arithmetic; cstr and the column-definition reader (type_at) bounds-check and report mysql: truncated column definition; result-set and auth-loop reads are hardened; Vec::with_capacity hints are capped.
Tests
mysql_empty_packet_is_a_clean_error, mysql_truncated_column_definition_is_a_clean_error — Rust fake servers speak the real handshake, then send the hostile packet; both engines must surface the error.

S-11  Medium  PostgreSQL client unbounded message allocation

src/stdlib/postgres.rs — MAX_MESSAGE_BYTES (60), check (81–83), helpers be16 (139), slice_at (166), rest (175)
Symptom
A server could name a 4 GiB message body in a 5-byte header; the client allocated it before reading a byte and aborted.
Root cause
read_message trusted the u32 length; RowDescription/DataRow/auth-loop readers indexed payloads unchecked.
Fix
64 MiB cap (MAX_MESSAGE_BYTES) before allocation — postgres: message 'E' is too large (… bytes) — plus checked helpers (be16, be32, slice_at, rest) used by the row/auth readers.
Tests
postgres_oversized_message_is_a_clean_error — a Rust fake server sends 'E' with length 0x7FFFFFFF; both engines must error, not allocate.

S-12  Medium  argon2 argument validation

src/stdlib/argon2.rs — positive() closure (459–465), out_len range (495)
Symptom
argon2(pw, salt, -1, 32, 1, "id") never returned (passes −1 → u32::MAX iterations); argon2(pw, salt, 1, 32, 1, "id", -1) aborted the allocator (out_len −1 → usize::MAX capacity); memory cost was unbounded.
Root cause
Raw as u32 / as usize casts of user-supplied integers.
Fix
A positive() validator (strictly positive, ≤ u32::MAX) gates passes, memory_kib, and lanes; out_len must be 1..=1024; the existing 1 GiB memory cap is now actually reached. Errors are runtime errors, identical on both engines.
Tests
argon2_rejects_non_positive_passes, argon2_rejects_non_positive_out_len, argon2_rejects_oversized_memory.

S-13  Medium  More than 255 parameters

src/semantic/mod.rs — 1554, 1615, 2625
Symptom
A 300-parameter function compiled on the VM with silently truncated slot indices (locals/parameters occupy 1-byte slots), producing wrong behavior instead of an error.
Root cause
No limit was enforced at the front end, so an out-of-range function reached the VM compiler.
Fix
The semantic checker rejects >255 parameters at all three parameter-list sites with too many parameters in one function (max 255) — so both engines refuse uniformly and spid3r test parity is preserved.
Tests
more_than_255_parameters_is_rejected.

S-14  Medium  WASM allocation/deallocation layout mismatch

src/wasm.rs — alloc_payload (182–196), spid3r_wasm_free (208–213)
Symptom
Potential undefined behavior across the C-ABI boundary: a buffer allocated with with_capacity + resize does not guarantee capacity == len, while spid3r_wasm_free reconstructed the box assuming the requested length — if the allocator had rounded capacity up, the free used the wrong layout.
Root cause
Allocation and deallocation used two different assumptions about the buffer's exact capacity.
Fix
Both paths now go through into_boxed_slice() — the one constructor that guarantees capacity == len — with Box::into_raw on allocate and Box::from_raw(slice::from_raw_parts_mut(ptr, len)) on free, making the layouts match by construction.
Tests
Existing tests/wasm_tests.rs passes; the change is layout-level and covered by the full suite.

S-15  Low  Markup injection in bundle output

src/bundle.rs — escape_markup() (309), applied at the <title>, single-file HTML, index.html, and android:label sites
Symptom
A project name containing markup (e.g. <script>) was interpolated unescaped into generated HTML/XML, so a crafted project name could inject script into the bundle preview page.
Root cause
Template interpolation without escaping of developer-controlled strings.
Fix
escape_markup() escapes & < > " '; applied to every site where the project stem reaches output.
Tests
Existing tests/bundle_tests.rs passes; verified by generating a bundle from a project whose stem contains markup characters.

S-16  Low  spid3r test panicked on non-UTF-8 paths

src/cli.rs — 776–791
Symptom
Running the differential test command over a file whose path is not valid UTF-8 panicked (.as_os_str().to_str().unwrap()).
Root cause
Three sites unwrapped the UTF-8 view of an OsStr.
Fix
Replaced with to_string_lossy().to_string() at all three sites.
Tests
Code-level fix verified by review; covered by the full suite (the panic path is not reachable from the existing fixtures on this platform).

S-17  High  VM never auto-collected cyclic garbage

src/vm/mod.rs — maybe_collect() at the VM poll point (583–593)
Symptom
A VM program that allocated cyclic garbage in a loop leaked every cell until process exit: 400 000 mutual Node cycles left >1.2 M live cells, while the tree engine reclaimed them (the divergence broke spid3r test parity on memory behavior and made long VM runs grow without bound).
Root cause
The mark-sweep cycle collector ran at the interpreter's statement boundary, but the VM's periodic poll point never invoked it.
Fix
crate::value::gc::maybe_collect() is called at the VM's poll point — the analogue of the statement boundary that docs/GC.md specifies for both engines. It is safe at an instruction boundary (every live value is held as a strong Value reference) and no-ops unless the allocation threshold is reached.
Tests
tests/gc_vm_autocollect.rs — churns 400 000 mutual cycles with no explicit gc_collect() on both engines, asserts live cells fall below 100 000 (pre-fix the VM held >1.2 M) and that a deliberately kept cycle survives collection.

6. Unresolved & accepted risks

IDSeverityItemAssessment / recommendation
R-1Low Native for-in iterator is not freed when a loop is abandoned by throw/return (src/native/ir.rs ~1447–1453: spid3r_forin_end runs only on normal completion). Cosmetic inconsistency, not a leak of new magnitude: the native runtime is an arena by design (see R-5). Measured at 2 M iterations — throw-abandoned loop 402 MB vs. clean loop 357 MB, i.e. the same order as the documented per-value arena cost. Not worth special-casing the unwind path.
R-2Low bcrypt accepts cost 31 (src/stdlib/bcrypt.rs: bcrypt_parse and n_bcrypt_hash both allow 4..=31). CPU DoS when the cost comes from untrusted input (e.g. a hash string read from a database): measured 40 ms at cost 10, 637 ms at cost 14 (×16 per 4 steps) → cost 31 ≈ 24 hours per call. Recommendation: cap the accepted cost in bcrypt_parse (e.g. ≤ 16) or document the limit for callers.
R-3Info pg_query / mysql_query / redis_command are text protocols with no parameterized API. SQL injection is the application's responsibility (the built-in SQLite driver is parameterized). Recommendation: document prominently; consider a parameterized variant in a future release.
R-4Info The tree engine has no 32 KiB function-body limit; the VM rejects such bodies (S-8). Documented engine divergence, surfaced as a clean diagnostic. spid3r test differentials never combine a >32 KiB body with try, so parity is unaffected.
R-5Info The native backend has no garbage collector — every value is a boxed allocation that lives for the process (arena). Deliberate, documented trade-off (docs/NATIVE.md §Memory model): dependency-free runtime and identical semantics across engines. Applications with long-running, allocation-heavy native workloads must account for it.

7. Appendix — environment notes

OneDrive synchronization hazard (observed during this audit). The project lives under OneDrive/Desktop. At one point during the session, native executables built by the debug toolchain briefly behaved as if the arity fix were absent. Root cause was environmental, not a code defect: the runtime static library (target/debug/spid3r_lang.lib) that spid3r build links into generated executables had been momentarily replaced/restored by the sync client, so an outdated runtime was linked. After a rebuild, all builds were verified correct and deterministic (5/5 identical runs; forced touch src/native/rt.rs && cargo build confirmed the library tracks source changes). Recommendation: keep the working copy off synced folders (or pause sync during builds), and after any sync event verify target/<profile>/spid3r_lang.lib is newer than src/native/rt.rs.

Checks that could not be performed in this environment: none material — LLVM 18 was available, so the native-backend tests ran rather than skipped; the database-client tests use purpose-built Rust fake servers and need no external services.

Continuous integration (GitHub Actions). The first push of this audit (c8ffea6) went red on all clippy jobs, and would also have failed the rustfmt gate: the round-2 edits drifted from cargo fmt in 15 spots, and the wasm free-path fix used slice::from_raw_parts_mut where clippy 1.99 requires ptr::slice_from_raw_parts_mut (identical semantics — the fat pointer is built directly). A third latent break surfaced only when the gates were run locally in CI's exact configuration: the native arity regression test asserted on a toolchain binary built without the native feature, which is precisely what CI's core job (cargo test --no-default-features) builds; the guard now checks cfg!(feature = "native") as well as the presence of LLVM-C.dll and skips cleanly. All three clippy variants, rustfmt, and the full suite (837 passed / 0 failed with default features; 805 / 0 with --no-default-features, the 32 GUI-feature tests excluded) pass locally after the corrections; the corrected push is verified green below.
