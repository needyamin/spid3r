Spid3r vs Python 3.13 vs PHP 8.3 — a measured, verified comparison

Every performance number below was measured on this machine, today, running identical workloads (the project's cross-language benchmark suite) through one harness. Every "cannot do" claim was verified against the source code or reproduced with a probe — no assumptions, no marketing.

Methodology. Windows x64, best of 3 wall-clock runs per benchmark including process startup, same harness for all languages. Versions: Spid3r 1.0.0 (bytecode VM, release build, optimizer on) · Python 3.13.14 (CPython) · PHP 8.3.33 (CLI, ZTS). Iteration counts match across languages (arith 2M, list 200k, methods 200k, map 40k, closures 40k, strings 30k, json 2k). "Iters/sec" = outer loop iterations per second.

Performance verdict (honest): on these micro-workloads Spid3r's VM sits at PHP's level and ≈1.6–1.7× faster than CPython 3.13. PHP is measurably faster at method dispatch (683k vs 590k/s — its method call path is two decades more optimized). This says nothing about real apps — there Spid3r's thin standard library dominates the picture (see §3). Python's heavyweight numeric stack (NumPy) and PHP's JIT-enabled OPCache for long-lived web processes are different workloads than this CLI loop.

The AOT surprise (measured, not hidden): the same arith workload LLVM-AOT-compiled via spid3r build ran at ≈2.1M iters/s — slower than the VM (≈960 ms for 2M iterations). The native backend currently routes every operation through C-ABI runtime trampolines (spid3r_binop, spid3r_global_get, …), which dominates this loop shape. The planned Chunk-based codegen (ARC-05) exists precisely to fix this; today, if you want speed, use the VM.

2. What Spid3r does have (verified parity or better)

  • Unicode-correct strings — len("héllo") == 5, s[1] == "é" (measured): character-indexed like Python, unlike PHP's byte strings. Plus interpolation, negative indexing.
  • Real closures with correct capture, higher-order methods (map/filter/reduce taking functions — works in all engines, verified).
  • Memory safety story Python/PHP lack: cycle-collecting GC with weak references (weak()), deep-clone semantics, no GIL — closures/values cross threads safely.
  • LLVM AOT to a standalone native binary + a wasm target — Python/PHP have no equivalent in the standard toolchain (PyInstaller/cxls are packaging, not compilation).
  • Zero third-party dependencies in the core; bytecode validator; a 3-engine differential test harness; LSP; formatter; REPL; line debugger — in the box.
  • Option/Result error model (some/none/ok/err, ? propagation) and try/catch — PHP has neither natively (exceptions only), Python has neither natively (exceptions only).
  • Batteries that matter for its size: SQLite driver, regex, JSON, CSV, datetime, SHA-256/HMAC, process spawn, a web micro-framework (routing, cookies, JWT sign/verify, templates, form/query parsing — stdlib/web.matrix).
  • Threads with real parallelism (spawn on an OS-thread pool, channels, mutexes) — PHP has no built-in threads (ZTS aside); Python has the GIL (free-threading is new/experimental in 3.13).

3. What Spid3r cannot do today (verified) — vs Python and PHP

3.1 Platform & I/O — the hardest gaps

  • NOHTTPS/TLS anywhere. http_fetch("https://…") fails with "https:// is not supported (no TLS in the zero-dependency core); use http://" (src/stdlib/net.rs:934). Python has ssl in stdlib; PHP streams are TLS by default. A Spid3r program cannot call a single modern HTTPS API. UPDATE 2026-10-22: fixed — the opt-in tls feature adds HTTPS to http_fetch (native-tls, OS certificate store), verified with a real fetch of https://example.com; the zero-dependency default build is unchanged.
  • NOEvented/async I/O. Sockets are blocking; concurrency is an OS-thread pool. No select/poll/epoll, no event loop, no async/await. Python: asyncio; PHP: Fibers + ReactPHP/Swoole. A 10k-connection server is not writable in Spid3r.
  • NOUDP, WebSockets, or multicast — TCP client/server + manual HTTP framing only. UPDATE 2026-10-22: UDP datagram sockets shipped (udp_bind/send_to/recv_from/close, loopback-tested); WebSockets and multicast remain absent.
  • NOTask cancellation or structured concurrency — a spawned task cannot be cancelled; exit-drain is best-effort.

3.2 Numbers & data types

  • NOArbitrary-precision integers. Measured: 9223372036854775807 + 1 silently wraps to -9223372036854775808 (exit 0). Python ints are unbounded; PHP converts overflow to float. Crypto/BigInt math silently corrupts in Spid3r.
  • NODecimal / arbitrary-precision float (Python decimal/fractions) — money math is f64-only.
  • NOComplex numbers (Python builtin complex).

3.3 Language constructs (all verified by probe/source)

  • NOGenerators — yield 1; is a parse error ("expected ';' … found integer 1"). Python/PHP both have generator functions.
  • NODefault parameter values — structurally blocked today: the arity check runs before the function body in all engines.
  • NONamed arguments at call sites.
  • NOAbstract classes / traits / mixins — no abstract keyword; interfaces exist, but nothing like PHP traits or Python mixins/ABCs.
  • NOGenerics / parametric types — no type parameters anywhere.
  • NOOperator overloading, decorators, macros, compile-time reflection/introspection — Python's decorator + reflection model and PHP's attribute/reflection API have no counterpart. (Python @decorator, getattr/type() tricks cannot be written.)
  • NORich interpolation holes — only {name} and {obj.field}; "{len(xs)}" is literal text.

3.4 Ecosystem — the biggest realistic difference

  • NORemote package registry. spid3r install works from a local registry/vendor dir only; no HTTP registry, no package signing, no transitive resolution. Python: ~600k packages on PyPI one pip install away; PHP: Packagist/Composer. Spid3r: zero third-party packages installable from anywhere. Everything you want — requests, numpy, pandas, pillow, lxml, symfony, laravel, SQLAlchemy, pytest — you would have to write yourself.
  • NODatabase breadth — SQLite only. No MySQL/MariaDB/Postgres/Redis/MongoDB drivers. PHP/Python connect to everything.
  • NOWeb-serving stack — no FastCGI/WSGI integration, no production server, no sessions beyond DIY JWT/cookies, no multipart file-upload parsing, no middleware ecosystem. A real CMS in Spid3r today means building all of that.

3.5 Standard library gaps (verified against the native registry)

  • NOCompression — no gzip/zip/zlib (Python: gzip/zipfile/zlib; PHP: gz*, ZipArchive).
  • NOSerialization beyond JSON/CSV — no XML, YAML, TOML, protocol buffers. (PHP: xml/simplexml, yaml; Python: all of it.) Correction 2026-10-22: bytes-level Base64/hex (b.to_base64()/from_base64/to_hex/from_hex) DID already exist as bytes methods; the new base64_* natives add string-level and URL-safe forms.
  • NOEmail/SMTP, SSH, FTP clients.
  • NOPassword hashing — no bcrypt/argon2/PBKDF2 (PHP: password_hash; Python: hashlib.pbkdf2_hmac plus libraries). Only SHA-256/HMAC-SHA256 exist — storing user passwords safely requires rolling your own KDF, which you shouldn't. UPDATE 2026-10-22: pbkdf2_sha256() shipped (RFC 8018, vector-tested) — the KDF gap is closed; bcrypt/argon2 remain absent.
  • NOImage/audio/media processing, PDF generation (Python: Pillow; PHP: GD/Imagick).
  • NOTimezone database / locale-aware formatting — datetime has parts/formatting but no IANA tz conversion or locale collation; no Unicode normalization or grapheme segmentation.
  • NOmath/science stack — no NumPy-class arrays (there is .npy save/load, but no vectorized compute), no statistics beyond basics, no big-int math.

3.6 Tooling gaps

  • NOLSP rename / find-references / semantic tokens / code actions — hover, diagnostics, symbols and formatting work. UPDATE 2026-10-22: rename and find-references shipped (file-scoped, shadow-aware, 6 wire tests); semantic tokens and code actions remain absent.
  • NOProfiler / coverage tooling; spid3r test compares stdout only (no assertions framework, no mocking, no fixtures — Python: pytest; PHP: PHPUnit).
  • NOInteractive debugging depth (breakpoints, watches, REPL-in-frame — a line debugger exists; xdebug/pdb-level tooling does not).

4. Bottom line (no sugar-coating)

Spid3r is a fast (PHP-class VM), safe, self-contained language with a genuinely nice core — unicode strings, closures, threads without a GIL, AOT+wasm targets, and an error model PHP/Python don't have. But realistically, today it cannot be used for: any application that talks HTTPS; any multi-connection server; anything needing a package ecosystem (parsing XML/YAML, compression, email, images, DBs beyond SQLite, password hashing); numeric/scientific work; or a team-scale web stack — because the library and tooling to do those things do not exist in it, and cannot be installed from anywhere. The measured interpreter speed (≈1.7× CPython) is real but is the smallest of the differences that matter; the ecosystem gap is the largest, and only time and the Phase C registry work change that.
