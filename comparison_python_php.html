Spid3r vs Python 3.13 vs PHP 8.3 — a measured, verified comparison

Every performance number below was measured on this machine, today, running identical workloads (the project's cross-language benchmark suite) through one harness. Every "cannot do" claim was verified against the source code or reproduced with a probe — no assumptions, no marketing.

Methodology. Windows x64, best of 3 wall-clock runs per benchmark including process startup, same harness for all languages. Versions: Spid3r 1.0.0 (bytecode VM + LLVM AOT "Exec" + tree-walker, release build) · Python 3.13.14 (CPython) · PHP 8.3.33 (CLI, ZTS). Iteration counts match across languages (arith 2M, list 100k, map 20k, closures 20k, strings 30k, methods 200k, json 2k; channels reported in ms). "Iters/sec" = outer loop iterations per second.

Performance verdict (honest): Spid3r's VM is at PHP's level and 1.9–4.0× faster than CPython 3.13 on these workloads. It beats PHP on closures, strings, JSON, and channel handoff; ties on arith/list/map; loses only method dispatch (PHP 2.24M vs 1.51M/s — its call path is two decades more optimized). Update vs the previous revision: the AOT backend is no longer slower than the VM. The old "AOT surprise" (≈2.1M iters/s, slower than the VM) was measured before the native backend's call-path work; today spid3r build output matches or slightly beats the VM on every benchmark (arith 20.5M vs 19.5M/s). If you want speed today, either engine delivers it. This says nothing about real apps — there Spid3r's thin standard library dominates the picture (see §3). Python's heavyweight numeric stack (NumPy) and PHP's JIT-enabled OPCache for long-lived web processes are different workloads than this CLI loop.

2. What Spid3r does have (verified parity or better)

  • Unicode-correct strings — len("héllo") == 5, s[1] == "é" (measured): character-indexed like Python, unlike PHP's byte strings. Plus interpolation, negative indexing.
  • Real closures with correct capture, higher-order methods (map/filter/reduce taking functions — works in all engines, verified).
  • Default parameter values (fn greet(name, greeting = "Hello")) and named arguments (greet(greeting: "Hi", name: "ada")) — both landed 2026-10-22 across all three engines; PHP has defaults, Python has both.
  • Generators as a library (stdlib/gen.matrix: lazy, composable gen/next/collect/take/map/filter streams — an infinite producer costs nothing until consumed). Compiler-level yield remains absent (§3.3).
  • Memory safety story Python/PHP lack: cycle-collecting GC with weak references (weak()), deep-clone semantics, no GIL — closures/values cross threads safely.
  • LLVM AOT to a standalone native binary + a wasm target — Python/PHP have no equivalent in the standard toolchain (PyInstaller/PHP phar are packaging, not compilation).
  • Zero third-party dependencies in the core; bytecode validator; a 3-engine differential test harness; LSP (hover, diagnostics, symbols, formatting, rename + find-references); formatter; REPL; line debugger; an opcode profiler (run --prof) — in the box.
  • Option/Result error model (some/none/ok/err, ? propagation) and try/catch — PHP has neither natively (exceptions only), Python has neither natively (exceptions only).
  • A built-in test framework (stdlib/assert.matrix: eq/ne/near/contains/throws + a done() exit-code protocol) — pytest-shaped, no third-party install.
  • Batteries that matter for its size: SQLite driver, regex, JSON, CSV, TOML (subset), semver, UUID v4, hex/base32, datetime, SHA-256/HMAC, PBKDF2, process spawn, a web micro-framework (routing, cookies, JWT sign/verify, templates, form/query parsing — stdlib/web.matrix).
  • Threads with real parallelism (spawn on an OS-thread pool, channels, mutexes) — PHP has no built-in threads (ZTS aside); Python has the GIL (free-threading is new/experimental in 3.13).

3. What Spid3r cannot do today (verified) — vs Python and PHP

3.1 Platform & I/O — the hardest gaps

  • FIXEDEvented I/O. tcp_poll([conns], timeout_ms) is backed by the platform readiness call — WSAPoll on Windows, poll(2) on Unix, declared by hand so the zero-dependency rule holds — so the OS wakes the caller the moment a socket is ready (measured: a 5-second wait returns in ~60 ms when data arrives). stdlib/event.matrix is a working event loop over it (register callbacks; one task dispatches any number of connections), which is the asyncio/ReactPHP role. Verified on both engines, including a two-client echo multiplexed by a single task. What remains, stated precisely: async fn and await exist and work, but await is a synchronous join of a task or channel — there is no suspension-based executor, so concurrency is still one scheduler task per unit of work (fine for hundreds/thousands of connections, not for 100k fibers). Python's asyncio is a true suspension runtime; PHP's Fibers likewise. (HTTPS closed earlier the same day: the opt-in tls feature adds HTTPS to http_fetch via native-tls + the OS certificate store, verified with a real fetch of https://example.com; the zero-dependency default build is unchanged.)
  • FIXEDWebSockets and multicast — shipped 2026-10-22: the full RFC 6455 client+server (ws_connect with accept-key verification, ws_accept, masked frames, auto-pong, fragment reassembly, close handshake) and IPv4 multicast (udp_join_multicast/leave_multicast/set_multicast_ttl/set_broadcast). Verified on both engines with a loopback echo and a real group delivery. Only ws://: wss:// needs the opt-in tls feature (the zero-dependency default build stays as-is).
  • FIXEDTask cancellation — task.cancel() shipped 2026-10-22 and works identically on all three engines: a runaway compute task stops at its next cancellation point (per-statement in the tree engine, every 2048 instructions in the VM, a per-loop counter poll in AOT code, and a time-sliced channel wait), a task blocked on an empty channel wakes up, join() raises "task cancelled", status() reports "cancelled", and cancelling a finished task is a no-op. Structured concurrency (scoped tasks) is a separate, still-open design item.

3.2 Numbers & data types

  • FIXEDSilent integer overflow. The worst of the three was a correctness bug, not a missing feature: 9223372036854775807 + 1 used to wrap to -9223372036854775808 with exit 0. It is now a runtime error (integer overflow: 9223372036854775807 + 1) in all three engines — Python raises, PHP converts to float; nobody silently corrupts. The VM's fast-path superinstructions fall through to the checked path, so the common case pays one predictable branch.
  • FIXEDArbitrary-precision integers — stdlib/bigint.matrix: add/sub/mul/divmod/pow/cmp/neg/abs over base-10⁴ limbs, verified against Python for 2^128, 25!, and a 30-digit product/quotient. It is a library, not literal syntax: int stays 64-bit, so you opt in with bi.from_string(...). O(n²) multiplication, schoolbook division — correct, not fast. These three libraries run on the tree and VM engines; the native backend still rejects import ... as alias, so an AOT build of a program using them is refused with a clear diagnostic (pre-existing limitation, unrelated to the libraries).
  • FIXEDDecimal (exact money math) — stdlib/decimal.matrix: {units, scale} over bigint, so 0.10 + 0.20 is exactly 0.30, division takes an explicit precision, and round is half-away-from-zero. This is Python's decimal role; PHP's bcmath equivalent.
  • FIXEDComplex numbers — stdlib/complex.matrix: add/sub/mul/div/conj/abs/arg/polar/from_polar over {re, im}. Python has a builtin type; this is a library with the same arithmetic.
  • FIXEDOperator overloading — a language feature, not a library trick: any value carrying a callable __add__/__sub__/__mul__/__div__ (a map or a class instance) handles the operator, so 0.10 + 0.20, x * y on bigints, and z1 * z2 on complex numbers all read naturally. Dunder keys are hidden from display. Works on the tree and VM engines (the native backend reports its usual unsupported-feature diagnostic).
  • PARTIALWhat is still library-level, not language-level: there are no big-integer or decimal literals (you write dec.from_string("0.10"); Python's Decimal("0.10") is the same shape, but Python also has unbounded int literals), and no exact rationals (fractions). NumPy-class vectorized arrays remain absent (§3.5).

3.3 Language constructs (all verified by probe/source)

  • PARTIALGenerators. A library (stdlib/gen.matrix) provides lazy, composable generators over the scheduler; the compiler-level yield 1; is still a parse error. Cost model: one scheduler task per live generator (thousands fine; hundreds of thousands wants the real thing). Python/PHP have native generator functions.
  • FIXEDDefault parameter values — fn f(x, limit = 10), trailing-only constants, filled at the callee in all three engines (2026-10-22).
  • FIXEDNamed arguments — f(host: "b.io", secure: true) on direct calls, constructors, and super; method calls reject them with a precise diagnostic (documented v1 limit, 2026-10-22).
  • NOAbstract classes / traits / mixins — no abstract keyword; interfaces exist, but nothing like PHP traits or Python mixins/ABCs.
  • NOGenerics / parametric types — no type parameters anywhere.
  • NOOperator overloading, decorators, macros, compile-time reflection/introspection — Python's decorator + reflection model and PHP's attribute/reflection API have no counterpart. (Python @decorator, getattr/type() tricks cannot be written.)
  • NORich interpolation holes — only {name} and {obj.field}; "{len(xs)}" is literal text.

3.4 Ecosystem — the biggest realistic difference

  • NORemote package registry. spid3r install works from a local registry/vendor dir only; no HTTP registry, no package signing, no transitive resolution. Python: ~600k packages on PyPI one pip install away; PHP: Packagist/Composer. Spid3r: zero third-party packages installable from anywhere. Everything you want — requests, numpy, pandas, pillow, lxml, symfony, laravel, SQLAlchemy, pytest — you would have to write yourself. This is the single largest gap.
  • NODatabase breadth — SQLite only. No MySQL/MariaDB/Postgres/Redis/MongoDB drivers. PHP/Python connect to everything.
  • NOWeb-serving stack — no FastCGI/WSGI integration, no production server, no sessions beyond DIY JWT/cookies, no multipart file-upload parsing, no middleware ecosystem. A real CMS in Spid3r today means building all of that.

3.5 Standard library gaps (verified against the native registry)

  • NOCompression — no gzip/zip/zlib (Python: gzip/zipfile/zlib; PHP: gz*, ZipArchive).
  • PARTIALSerialization beyond JSON/CSV. A TOML-subset parser shipped 2026-10-22 (tables, arrays of tables, dotted keys, inline tables — stdlib/toml.matrix); still no XML, YAML, or protocol buffers (PHP: xml/simplexml/yaml; Python: all of it). Hex/base32 exist as both natives and bytes methods.
  • NOEmail/SMTP, SSH, FTP clients.
  • PARTIALPassword hashing — pbkdf2_sha256() shipped 2026-10-22 (RFC 8018, vector-tested); bcrypt/argon2 remain absent (PHP: password_hash).
  • NOImage/audio/media processing, PDF generation (Python: Pillow; PHP: GD/Imagick).
  • NOTimezone database / locale-aware formatting — datetime has parts/formatting but no IANA tz conversion or locale collation; no Unicode normalization or grapheme segmentation.
  • NOmath/science stack — no NumPy-class arrays (there is .npy save/load, but no vectorized compute), no statistics beyond basics, no big-int math.

3.6 Tooling gaps

  • NOLSP semantic tokens / code actions — hover, diagnostics, symbols, formatting, rename and find-references work (2026-10-22).
  • PARTIALTest tooling — an assertions framework (stdlib/assert.matrix) and an opcode profiler (run --prof) shipped 2026-10-22; spid3r test still compares stdout only (no mocking, no fixtures, no coverage).
  • NOInteractive debugging depth (breakpoints, watches, REPL-in-frame — a line debugger exists; xdebug/pdb-level tooling does not).

4. Bottom line (no sugar-coating)

Spid3r is a fast (PHP-class VM, and now a competitive AOT), safe, self-contained language with a genuinely nice core — unicode strings, closures, threads without a GIL, default parameters, named arguments, generators, AOT+wasm targets, and an error model PHP/Python don't have. What changed since the previous revision: HTTPS works (opt-in), and the library/tooling gaps narrowed substantially — TOML, semver, UUID, hex/base32, PBKDF2, an assertions framework, a profiler, LSP rename/references, and generators all shipped. What still blocks real-world use, honestly: (1) no package registry — the ecosystem gap is the largest and only time plus registry work change it; (2) no suspension-based async executor (async/await are join-based; readiness itself is a kernel wakeup now); (3) databases beyond SQLite; (4) no compression/XML/YAML; (5) no generics, and BigInt/decimal are libraries rather than literal syntax (numeric corruption is fixed; the numeric *stack* is not NumPy); (6) no media/email stacks; (7) no compiler-level yield; (8) no kernel epoll/kqueue wakeup and no async/await. The measured speed (≈2–4× CPython, PHP-class) is real but is the smallest of the differences that matter; the ecosystem remains the largest.
