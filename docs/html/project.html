Step-by-Step: Architecting a Spid3r Service

Follow this 8-step breakdown to learn how to scaffold, model, test, and compile real-world software using Spid3r.

1

Project Scaffolding & Manifest (spider.toml)

Every professional Spid3r service starts with a reproducible package layout and lockfile.

Use the Spid3r Package Manager (SPM) to initialize a new project workspace. Spid3r's core toolchain is zero-dependency, meaning our E-Commerce service requires no heavy external frameworks to run.

Terminal Shell 
$ spid3r init ecommerce
$ cd ecommerce
$ tree
.
├── spider.toml      # Package manifest (name, version, entrypoint)
├── spider.lock      # Deterministic SHA-256 tree hash verification
├── src/
│   └── main.matrix  # Application entrypoint
└── tests/
    └── store_test.matrix

In spider.toml, specify the package identity and entry point:

spider.toml 
[package]
name = "spid3r_ecommerce"
version = "1.0.0"
entry = "src/main.matrix"

# Zero dependencies required: Spid3r standard library includes
# collections, http, json, crypto, and thread-safe primitives.
[dependencies]
2

Domain Modeling with Object-Oriented Spid3r

Model real-world entities using classes, public field visibility, and constructors.

Spid3r supports class declarations with optional type annotations, explicit constructors (fn new), and member method receivers. We model Product, CartItem, and Order:

src/models/product.matrix 
class Product {
    public let id: int;
    public let name: string;
    public let price: float;
    public let stock: int;
    public let category: string;

    fn new(id: int, name: string, price: float, stock: int, category: string) {
        self.id = id;
        self.name = name;
        self.price = price;
        self.stock = stock;
        self.category = category;
    }

    public fn to_string(self) -> string {
        return "#" + string(self.id) + " " + self.name + " ($" + string(self.price) + ")";
    }
}

class CartItem {
    public let product: Product;
    public let quantity: int;

    fn new(product: Product, quantity: int) {
        self.product = product;
        self.quantity = quantity;
    }

    public fn line_total(self) -> float {
        return self.product.price * float(self.quantity);
    }
}
3

Inventory Management & In-Memory Data Store

Utilizing high-performance native maps and thread-safe mutex guards.

Spid3r provides 20+ native data structures in value::collections. We store our catalog in a map() keyed by string IDs. For multi-threaded concurrency (such as when handling concurrent HTTP requests), we guard inventory updates with mutex().

src/services/store.matrix 
class Store {
    public let catalog;
    public let orders;
    public let next_id;
    private let lock;

    fn new() {
        self.catalog = map();
        self.orders = list();
        self.next_id = 1001;
        self.lock = mutex(0); // Thread-safe concurrency guard
    }

    public fn add_product(self, p: Product) {
        self.catalog[string(p.id)] = p;
    }

    public fn find_product(self, id: int) {
        let key = string(id);
        if self.catalog.has(key) {
            return some(self.catalog[key]); // Option type: some(v)
        }
        return none;
    }
}
4

Cart Engine & Discount Calculation Rules

Implementing coupon codes, progressive shipping tiers, and sales tax.

E-Commerce platforms require strict mathematical pricing pipelines. Here is the pricing logic encapsulated into pure Spid3r functions:

src/services/pricing.matrix 
fn calculate_discount(subtotal: float, coupon: string) -> float {
    if coupon == "SPID3R20" {
        return subtotal * 0.20; // 20% discount
    } elif coupon == "SAVE10" {
        if subtotal < 10.0 { return subtotal; }
        return 10.0;           // Fixed $10 off
    } elif coupon == "CYBER50" {
        return subtotal * 0.50; // 50% discount
    }
    return 0.0;
}

fn calculate_shipping(discounted_subtotal: float) -> float {
    // Free shipping threshold for orders >= $50.00
    if discounted_subtotal >= 50.0 or discounted_subtotal == 0.0 {
        return 0.0;
    }
    return 5.99; // Standard flat rate
}
5

Transactional Checkout & Result Types

Using two-phase verification and ok(...) / err(...) types to prevent negative inventory.

In Spid3r, operations that can fail return Result values: ok(receipt) or err(error_msg). This ensures error cases are typed and handled explicitly without unexpected runtime crashes.

src/services/checkout.matrix 
public fn checkout(self, customer: string, cart_items, coupon: string) {
    if cart_items.len() == 0 {
        return err("Cannot checkout an empty shopping cart");
    }

    // Phase 1: Verify all products have sufficient stock
    for item in cart_items {
        let p = item.product;
        if p.stock < item.quantity {
            return err("Insufficient inventory for: " + p.name);
        }
    }

    // Phase 2: Atomic stock deduction & subtotal accumulation
    let subtotal = 0.0;
    for item in cart_items {
        let p = item.product;
        self.catalog[string(p.id)].stock = self.catalog[string(p.id)].stock - item.quantity;
        subtotal = subtotal + item.line_total();
    }

    // Financial calculations
    let discount = calculate_discount(subtotal, coupon);
    let discounted = subtotal - discount;
    let shipping = calculate_shipping(discounted);
    let tax = discounted * 0.085;
    let total = discounted + shipping + tax;

    let order_id = self.next_id;
    self.next_id = self.next_id + 1;

    let receipt = map(
        "order_id", order_id,
        "customer", customer,
        "subtotal", subtotal,
        "discount", discount,
        "shipping", shipping,
        "tax", tax,
        "total", total,
        "status", "CONFIRMED"
    );

    self.orders.push(receipt);
    return ok(receipt); // Returns ok(receipt)
}
6

Background Workers with Concurrency (spawn & channel)

Offload asynchronous tasks like invoice generation or receipt emails to OS worker threads.

Spid3r features true multi-threaded concurrency. The spawn keyword runs tasks on an OS thread pool, and channel() enables thread-safe message passing between producers and background workers:

src/services/workers.matrix 
let email_channel = channel();

// Spawn asynchronous background worker
spawn fn() {
    while true {
        let order = email_channel.recv();
        println("[WORKER] Dispatching receipt email to: " + order["customer"]);
        sleep_ms(50); // Non-blocking task sleep
    }
};

// In checkout completion:
email_channel.send(receipt);
7

Automated Differential Testing

Guarantee behavioral parity across the Tree-Walker, Bytecode VM, and LLVM Native backend.

Spid3r includes built-in test assertions (assert and assert_eq). Running spid3r test executes the tests across all backends to ensure the Oracle (tree interpreter) and VM produce byte-for-byte identical results:

tests/store_test.matrix 
import "assert";

fn test_coupon_discount() {
    let d = calculate_discount(100.0, "SPID3R20");
    assert_eq(d, 20.0, "SPID3R20 should yield 20% off");

    let s = calculate_shipping(65.0);
    assert_eq(s, 0.0, "Orders > $50 must have free shipping");
}

fn main() {
    test_coupon_discount();
    println("All e-commerce tests passed!");
    return 0;
}
8

Compiling & Shipping to Production

Deploy your application 5 ways: Bytecode, Native Machine Code, WASM, or Standalone Bundle.

When ready to deploy, choose the optimal target for your infrastructure:

Build Commands 
# 1. Run directly on the Bytecode VM during development
$ spid3r run src/main.matrix

# 2. Compile to self-contained bytecode (.matrixc) for instant startup
$ spid3r compile src/main.matrix -o target/store.matrixc
$ spid3r exec target/store.matrixc

# 3. Compile to standalone Native Machine Code (.exe / ELF) via LLVM AOT
$ spid3r build src/main.matrix -o store --release
$ ./store

# 4. Verify package integrity against spider.lock
$ spid3r verify
Production Tip: Compiling with spid3r build --release performs aggressive LLVM optimizations, producing a standalone binary with zero external runtime dependencies that runs at native C speed.
