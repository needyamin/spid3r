Spid3r — Complex Application Field Test

Application: Nebula Bank Core (examples/complex_app/nebula_core.matrix)  ·  Date: 2026-10-25  ·  Build: current tree (debug)
Engines exercised: tree interpreter · bytecode VM · LLVM native (AOT)  ·  Probes: probes.matrix, probes2.matrix, probes3.matrix, probes4.matrix
Method: write one deterministic 560-line application covering the whole language surface, run it on all three engines, require byte-identical stdout, then probe every semantic edge the application did not touch.

Bottom line. The application runs byte-identically on all three engines (exit 0, verified) after two portability adjustments that are themselves recorded findings — and the probe rounds found 9 issues: 3 High, 1 Medium, 5 Low. The two most serious were (a) the regex engine silently treating {n}/{n,m} quantifiers as literal braces and (b) the native backend's try/catch failing to intercept two runtime error paths. F-1, F-9 and F-4 were all fixed on 2026-10-25 (F-1: engine + lexer layers; F-9: native runtime error channel; F-4: ?. now reads a missing map key as null — the m?.k ?? fallback idiom works), and F-3 was resolved the same day by adopting the GC observability policy (ENGINE_CONTRACT exemption #4). The low batch has started too: F-5 (trailing commas) and F-2 (-o extension + alias-rejection shape) are fixed/addressed. The rest remain open. The 39-check probe battery is otherwise identical on tree, VM and native — including dunders, inheritance, interfaces, enums/match guards, closures, checked arithmetic, unicode handling, insertion-ordered maps and deterministic concurrency.

1. The application

Nebula Bank Core is a deterministic banking-core simulation: a Money value type with all five arithmetic dunders, an Account → Savings/Checking hierarchy with an Auditable interface and an overridden withdraw, a Bank registry over insertion-ordered maps, enum + match compliance rules with guards, hand-rolled merge sort with a comparator closure, a BST, memoized recursion, ok/err results with try/catch/finally, four concurrent branch workers (spawn + channel + mutex) whose aggregation is order-independent by construction, a JSON round trip, regex validation, ref/ weak cells, a 150 000-cycle garbage churn, and bigint arithmetic (2^96, 30!). Every value printed derives from fixed seeds and insertion-ordered containers — no host clock, no scheduler-order dependence.

3. Findings

F-1  High  Regex bounded-repeat quantifiers are silently treated as literal braces  Fixed 2026-10-25

src/stdlib/regex.rs — RegexNode (9–23), parse_piece (100–117), literal Char arm (242) · src/lexer/mod.rs — try_interp_expr (digit-hole rejection)
Symptom
regex_match("^[0-9]{4}$", "5555") returned false; regex_match("a{2}", "a{2}") returned true — the pattern {4} matched the four literal characters { 4 }, so every pattern using {n} or {n,m} silently validated the wrong thing. No error, no warning, all three engines agreed on the wrong answer.
Repro
Found by the field-test app: its ID validator (^ACC-[0-9]{4}$) rejected every ID including valid ones; minimized with ^[0-9]{4}$ on "5555" → false, while ^[0-9]+$ → true and a{2} vs a{2} → true (literal).
Root cause
Two layers. (1) The regex AST had only Star/Plus/Quest nodes; parse_piece consumed * + ? and nothing else, so { fell through to the literal-character arm. (2) The string layer treated bare-integer braces as interpolation holes — "A{2}B" printed A2B — so even a fixed engine could never receive {4} from source, and there is no brace escape to work around it.
Fix
(1) parse_piece now parses {n}, {n,}, {n,m}, {,m} and expands them at AST level (a{2,4} → aa(a(a)?)?), with a 1000-count cap (RE2-style) that errors instead of blowing up, and PCRE-style literal fallback for malformed braces (a{, a{x}, a{2, {}). (2) The lexer's try_interp_expr rejects bare-integer holes ({2} stays literal text), restoring the ability to write quantifier braces while keeping {name}, {f(x)}, {-1}, {arr[0]} holes working. Behavior change: "A{2}B" now prints A{2}B (it printed A2B).
Tests
Five new unit tests in src/stdlib/regex.rs (exact/range/open/zero repeats, groups and classes under repeat, malformed-brace fallback, limit errors); lib suite 140/140, lexer_tests 19/19 (S-25 pins intact), parser/fmt/diagnostics/match/engine_matrix 48/48. End-to-end on all three engines (examples/complex_app/f1_verify.matrix): every repro line now correct and byte-identical on tree, VM and native — ^ACC-[0-9]{4}$ accepts ACC-1001/rejects ACC-12, (ab){3} matches, regex_replace("o{2}", …) works, and the field-test app's validator (nebula_core.matrix §8, restored to {4}) runs 3-engine byte-identical with correct accept/reject results.

F-9  High  Native backend: two runtime errors escape try/catch and abort the process (exit 70)  Fixed 2026-10-25

src/native/rt.rs — abort() (~55–59, ends in process::exit(70)), safe-dot missing-key path at rt.rs:1010 (None => abort(...))
Symptom
On the native backend, m?.missing and call-depth overflow raised inside a try block are not caught: stdout stops mid-program, stderr shows one error[runtime] line, exit code 70. The same programs on tree and VM catch both errors and exit 0.
Repro
probes4.matrix: 7 error paths in individual try/catch blocks. tree and VM catch all 7 and print end reached. Native catches 4 (user throw, json_parse, none.unwrap(), map.get("missing")), then dies at m2?.nope with error[runtime]: missing key 'nope', exit 70. A separate probe (deep(50000) in a try) dies identically at the stack-overflow error on native while tree/VM catch it.
Root cause
The native runtime's null-safe-dot/field path calls abort(&format!("missing key '{}'", name)) directly instead of routing the error through the runtime's catchable error channel; abort() prints and std::process::exit(70)s. Tree and VM raise the same message as a normal VmError/RuntimeError (src/vm/mod.rs:1850, src/interpreter/mod.rs:1378) that catch receives.
Impact
Same program, different error semantics per engine — a direct violation of the engine contract's "same exit code / never silent divergence" rule, and a fatal DoS for native servers that guard untrusted-map access with try/catch. Distinct exit codes (1 vs 70) also break scripts.
Fix (2026-10-25)
All script-level abort() sites in src/native/rt.rs were routed through the catchable pending-throw channel (rt_throw), which the generated spid3r_threw guards already intercept: (a) spid3r_field_get/spid3r_field_set — missing map key ("missing key 'x'", the m?.x path), missing instance field (wording switched to the tree engine's exact no_field_error text); (b) call-depth overflow — enter_call() now returns bool and every call site raises the catchable "stack overflow: call depth limit reached" without entering generated code, and the depth counter unwinds normally as frames return (recursion works again after a catch); (c) same class, same channel: "int is not callable" in the call dispatcher, wrong-arity callbacks (check_arity now returns Option<String>), and constructor arity errors (new X expects ...). abort() (exit 70) is now reserved for genuinely unrecoverable internal states: null value/string/upvalue pointers, unknown opcodes, class-registration races.
Verification
probes4.matrix: all 7 paths caught on native, exit 0, stdout byte-identical to tree/VM. New end-to-end probe examples/complex_app/f9_verify.matrix (8 checks: safe-dot miss, plain-dot miss, recursion overflow caught, depth counter unwound and reusable after the catch, non-callable, instance-field read + write): byte-identical on all three engines, exit 0. New regression pin tests/native_catchability.rs asserts exit codes and byte-identical stdout on tree + VM + native (native arm skipped without LLVM). Suites: lib 140/140, native_tests 7/7, engine_matrix 5/5 (AOT arms), clippy + rustfmt clean; nebula_core.matrix re-verified byte-identical exit 0 on all three engines.

F-3  High  gc_live_cells() is engine-divergent and the native arena never collects cycles mid-run  Resolved 2026-10-25 (policy adopted)

src/value/gc.rs (gc_live_cells) · native arena model (docs/NATIVE.md, audit §5 residual risk)
Symptom
The identical workload (150 000 abandoned two-node cycles, one kept cycle, no explicit gc_collect()) reports live cells: tree 380 → 128 after collect; VM 159 → 45; native 300 462 → 300 462. On native, gc_collect() completes but reclaims nothing: cyclic garbage is only released at process exit. A program that prints gc_live_cells() — a public builtin — can never satisfy the byte-identical-stdout contract.
Repro
Run nebula_core.matrix section 10 on all three engines (numbers above); the app now prints only portable verdicts, with this finding referenced inline.
Root cause
Live-cell counts are per-implementation bookkeeping (refcount + mark-sweep cells on tree/VM vs arena allocations on native), and the native backend's arena design (an accepted residual risk in the audit) has no mid-run cycle reclamation by construction. Mechanically: every native value handle is a Box<Value> leaked for the whole process, and each handle's inner Arc is a strong reference from outside the tracked set — so on native every cell has external > 0, every cell is a root, and the shared external-reference mark-sweep correctly keeps everything alive. The collector is not broken; there is nothing it is allowed to free.
Impact
(a) Contract conflict: gc_live_cells() is unusable in any cross-engine program or benchmark; (b) long-running native services that allocate cyclic garbage (object graphs, parent/child links) grow without bound until exit — the exact leak S-17 fixed for the VM; (c) misleading parity-test failures for anyone asserting on it.
Resolution (2026-10-25)
Policy decided and adopted, per this card's original recommendation. Decision: gc_live_cells() and the swept count are engine-internal memory observability, exempt from byte-parity as ENGINE_CONTRACT exemption #4. The portable subset — both builtins exist on every engine and return int, gc_collect() completes safely (on native it reclaims nothing by construction), and live data always survives a collection — is the parity bar for programs using these builtins. Documented in docs/GC.md (new "The native backend" section, including why mid-run reclamation requires handle-lifetime management in codegen before the existing collector can reclaim — the recorded design path for future work), docs/NATIVE.md (memory model), and docs/STANDARD_LIBRARY.md (builtin rows rewritten). Not done: native arena reclamation itself (out of scope without the codegen handle-lifetime work; documented as future work, not a flag).
Verification
New pin tests/gc_portability.rs: the churn probe (20 000 abandoned cycles + kept cycle) prints only portable facts and its stdout is byte-identical on tree, VM and native, exit 0. Live probes confirmed the documented semantics: gc_collect()/gc_live_cells() return int and complete safely on all three engines; the kept cycle survives everywhere. nebula_core.matrix re-verified byte-identical on all three engines after the section-10 comment update.

F-4  Medium  ?. on a missing map key throws — the m?.k ?? fallback idiom does not protect reads  Fixed 2026-10-25

src/lower/mod.rs (was: rewrote OptField away) · src/interpreter/mod.rs · src/vm/compiler.rs + bytecode.rs (new FieldGetSoft opcode) + src/vm/mod.rs · src/native/ir.rs + rt.rs (spid3r_field_get_soft) · docs/STANDARD_LIBRARY.md (m?.k "null-safe dot")
Symptom
m?.x on a map without key x raised error[runtime]: missing key 'x' instead of evaluating to null, on all three engines. Consequently m?.x?.y ?? default, the idiom users reach for, still threw. ?? only coalesces null, and none ?? 5 stays none (PHP-style), so neither operator rescued a missing key.
Repro
let m = map("a", 1); println(m?.x ?? -1); → uncaught missing key 'x'. Contrast m.get("a") → 1, and m?.a?.b works when every key exists.
Root cause
?. guarded only a null receiver: lower rewrote obj?.field to if obj != null { t = obj.field } — and the inner read was a plain field access, so key lookup ran the same throwing path as get. The docs' phrase "null-safe dot" invited the wrong expectation.
Impact
False sense of safety in exactly the code shape (untrusted map access) where it matters; combined with F-9 it turned a lookup miss on native into a process kill.
Fix (2026-10-25)
Semantics decision: ?. now guards a null receiver and a missing map key — both read as null, so m?.k ?? fallback and chains (m?.a?.b) work. Everything else keeps plain-. semantics: an instance without the field and a non-fieldable type still raise the same catchable errors, and m.get(k) still throws — a missing key is normal data variation for a map, a missing field is still a loud bug. Implementation: Expr::OptField is now a first-class operation instead of being lowered away — the tree interpreter evaluates it directly; the VM compiles it to the new additive FieldGetSoft opcode (byte 58, no format-version bump per docs/BYTECODE_STABILITY.md); native calls the new spid3r_field_get_soft trampoline (null/map arms soften, everything else delegates to spid3r_field_get). Behavior change: m?.missing reads null on every engine (was: throw); probes pinning the old throw (probes3/4, f9_verify, native_catchability) were updated.
Verification
New end-to-end probe examples/complex_app/f4_verify.matrix (12-row semantics table: exists/missing/idiom/null/chains + the four still-throwing paths): byte-identical on tree, VM and native, exit 0. New pin tests/f4_opt_field.rs asserts the table on all three engines. Prior pins re-verified: stage2b_hoisting (receiver evaluated once, chains with ??), language_surface, engine_matrix — all green. Full parity protocol re-run: nebula_core + all probes byte-identical on three engines.

F-2  Low  Native backend gaps: aliased imports rejected; compile -o writes an extensionless bytecode blob on Windows  Addressed 2026-10-25 — (b) fixed; (a) contract-shaped + documented

src/cli.rs (compile_file -o handling) · src/native/modules.rs (alias rejection) · docs/BUILDING.md · docs/NATIVE.md
Symptom
(a) import "bigint" as bi; fails under AOT: 'import as alias' is not supported by the native backend yet; run it with --engine vm — a clean, honest diagnostic, but the plain-import route silently changes call sites (bi.mul → mul), and the rejection was phased error[semantic] (exit 1) instead of the contract's error[usage] (exit 2) for unsupported constructs. (b) spid3r compile -o out writes an extensionless PE-less blob (header SPID3R\x02…, 362 856 bytes) that Windows refuses to execute until renamed; compile (bytecode) vs build (native) is easy to confuse, and docs' ./out flow only works on Unix.
Repro
App runbook: spid3r build nebula_core.matrix -o x.exe succeeds; spid3r compile … -o x yields the bytecode blob. Aliased import verified with the native build.
Fix (2026-10-25)
(b) fixed: compile -o appends the canonical .matrixc extension when the given path has none (-o x writes x.matrixc); an explicit extension is used verbatim; the resolved path is printed. Works on every platform. (a) reshaped + documented: a full AOT module-namespace implementation (mangled globals + a scope-aware rename pass + a frozen-map constructor) is a feature-sized change, so the documented-gap route was chosen — which is what the engine contract prescribes ("a construct a backend cannot run must be rejected at compile time with a clean error[usage] diagnostic"). The rejection now uses Phase::Usage (error[usage], exit 2, matching class-in-function), names the exact import ('bigint as bi' is not supported…), and the gap is documented in docs/NATIVE.md (Modules + the rejected-constructs table) and docs/BUILDING.md (new "compile vs build" + "Native backend limits" sections).
Verification
New pin tests/f2_cli_outputs.rs: extensionless -o produces <out>.matrixc (not a blob), prints the resolved path, and the artifact runs under exec; an explicit extension is verbatim; the aliased-import program runs on --engine vm (exit 0) and is rejected by build with exit 2 + error[usage] + the documented message. Live probes confirmed both before pinning.

F-5  Low  Trailing commas: allowed in match arms, rejected in call arguments  Fixed 2026-10-25

src/parser/mod.rs — parse_args (calls, incl. map(...)/tuple(...) constructors and named arguments), list-literal loop, parse_let_tuple destructuring
Symptom
map("a", 1, "b", 2,) → error[parser]: unexpected ')' while match arms accept a trailing comma. Multi-line constructors — the natural place to leave one — are exactly where the parser refuses.
Fix (2026-10-25)
Every comma-separated parse loop now follows the match-arm policy — a trailing comma before the closer is accepted and ignored: call arguments (positional and named), list literals, and let-destructuring (the tuple literal already allowed it). No grammar ambiguity: the closer token () / ]) cannot start an expression, so the lookahead is exact.
Verification
New pin tests/f5_trailing_comma.rs (calls incl. multi-line map(...), list literals, destructuring, tuple, single-element [9,], and no-trailing-comma calls): byte-identical on tree, VM and native, exit 0. Parser/fmt/lib suites and the full parity protocol re-run green.

F-6  Low  list.join refuses non-string elements

stdlib list methods — join
Symptom
[1, 2, 3].join(",") → error[runtime]: join needs strings, found int. Every program that prints an int list needs a to_strs shim (the field-test app needed one; both probe files needed one).
Suggested fix
Auto-stringify elements via the shared display function (consistent with string(x)) or add join_any/fmt_join. Keep a strict variant if the type discipline matters for embedded use.

F-7  Low  No \u escape in string literals

lexer — string escape scan
Symptom
"\u{1F600}" → error[lexer]: unknown escape '\u'. The JSON parser accepts \uXXXX with surrogate pairs, yet source code cannot spell a non-ASCII character without pasting raw UTF-8 — awkward in editors/CI with ASCII-only policies.
Suggested fix
Support \u{1F600} (and/or \uXXXX with surrogate pairing) in the lexer's escape scan; low risk, closes a surprising asymmetry with the JSON layer.

F-8  Low  json_parse end-of-input diagnostic leaks Rust internals

src/stdlib — JSON reader
Symptom
json_parse("{\"broken\": ") → json_parse: unexpected character None. "None" is Rust's Option::None Debug formatting; the message should say "unexpected end of input". Similar phrasing appears for truncated arrays.
Suggested fix
Map the None EOF case to a dedicated message in the JSON reader's error constructor.
