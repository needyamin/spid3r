Spid3r Documentation / Developer Manual & Language Specification

Spid3r Developer Portal & Complete Language Reference

Welcome to the official developer manual for Spid3r. This guide explains every single detail of the language: how it works, its grammar, type system, object-oriented model, data structures, concurrency runtime, standard library, and how to execute code directly in your browser.

01. Introduction to Spid3r

Spid3r is a modern, high-performance, memory-safe, embeddable general-purpose programming language with a zero-dependency core toolchain (--no-default-features), a self-hosted LLVM 23 AOT compiler, and a WebAssembly runtime.

It combines clean, expressive C/JavaScript-style syntax with the safety guarantees of managed memory, the mathematical power of NumPy/BLAS-style contiguous matrices and vectors, the concurrency model of Erlang/Go channels, and an instant WebAssembly compiler that lets you run complete programs inside any browser.

📖 How to read this manual

Each chapter gives you the essentials up front — what it is, how to use it, and what matters. Dense reference material (full contracts, wire formats, security models, build internals) is collapsed into deep-dive blocks marked ▸ Deep dive — …: the main topic stays visible, and the complete detail is one click away. Nothing is left out; it is just not in your face. All code samples are runnable as shown.

💡 Key Design Tenets
  • Zero-Dependency Core Toolchain: The core compiler, bytecode virtual machine, AST interpreter, and standard library (26 embedded modules and 254 built-in natives) compile with zero external dependencies via --no-default-features. Three optional Cargo features add native (LLVM 23 AOT), gui (wry/tao), and tls (OS-backed native-tls).
  • Three Native Execution Engines + WebAssembly: Run programs on the default pre-decoded --engine vm (bytecode VM with general fused superinstructions), the pure reference --engine tree (AST tree-walk oracle), the LLVM 23 ahead-of-time native compiler (spid3r build / self-hosted spid3r-self), or wasm32 in the browser — all pinned to identical stdout, error phase, and exit code.
  • Compact 16-Byte Value & Bounded Memory: Deterministic reference counting with 8-byte ThinArcStr, lock-free single-threaded FastMutex, a mark-and-sweep cycle collector (30 GcTrace implementations with automatic registry pruning), and bounded ValueV2/AOT_HEAP reclamation with precise frame roots and loop safepoints on native AOT builds.
  • Native WebAssembly Core: Zero-dependency wasm32-unknown-unknown build exportable as a self-contained linear-memory engine running in web browsers, Node.js, Deno, and Edge Workers.

Spid3r is lightweight and self-contained: one binary, no runtime to install, and no Visual C++ Redistributable (the C runtime is linked statically). Only GUI mode borrows the system webview — WebView2 on Windows, WebKit on macOS/Linux. You can install it on Windows, Linux, or macOS in under a minute:

02. How Spid3r Works: Compiler & VM Pipeline

Understanding the Spid3r internal execution pipeline helps you write highly optimized code and leverage both the VM and AOT native backends.

Phase Component Responsibility Output Artifact
1. Lexical Analysis src/lexer/mod.rs DFA-based tokenizer recognizing radix literals (0x, 0o, 0b), scientific float notation (1.5e3), Unicode escapes (\u{1F600}), and desugaring string interpolation holes ({var}). Stream of Token structs with line/col spans
2. Syntax Parsing src/parser/mod.rs Top-down recursive descent + Pratt precedence parser with statement-level error recovery (parse_recovering reports up to 25 syntax errors in check/lsp, while run/build fail fast on the first). Enforces strict 64-level nesting depth. Abstract Syntax Tree (ast::Program)
3. Semantic Analysis src/semantic/mod.rs Scope resolution, constant folding, flow-sensitive nullability narrowing (T? → T), scrutinee-driven enum match exhaustiveness, member visibility checks (public / private), interface compliance, lints, and E1xxx codes with end spans. Validated AST or coded compiler diagnostic
4. Lowering Pass src/lower/mod.rs Desugars high-level syntax into core primitives: converts ?? into null checks, value-position if into branch blocks, for (k, v) in map into iterator lookups, and destructuring tuples into temporary bindings. Desugared Low-level AST
5. Execution Backends src/vm/, src/interpreter/ & src/native/ Bytecode VM (default): 60-opcode bytecode with compile-time optimizer, pre-decoded 16-byte fixed-width instruction stream (src/vm/decode.rs), pure-leaf fast call dispatch, general fused superinstructions, and per-opcode + per-function self-time profiler.
Tree Interpreter: Reference AST oracle for differential parity.
Native AOT (LLVM 23): 16-byte ValueV2 inline scalars & SSO strings, hoisted 2D row handles (ptr, len, gen) and dense SSO map views with bounds-check elimination (BCE), direct field GEPs, split staticlib registration (spid3r_reg_core + 10 opt-in groups), and precise-root AOT_HEAP safepoint reclamation.		 Live execution, captured stdout, exit status
6. Memory Management src/value/gc.rs, src/value/mod.rs & src/native/rt.rs Compact 16-byte Value (8-byte ThinArcStr, boxed Result), lock-free single-threaded FastMutex, deterministic reference counting + mark-and-sweep cycle collector (30 GcTrace impls, non-blocking REGISTRY dead-entry pruning), and bounded worker-pool / AOT_HEAP sweeping on native builds. Reclaimed heap cells & bounded RSS

Module Resolution

Every backend resolves import "name" through one implementation, so the tree interpreter, the bytecode VM and the AOT compiler cannot disagree about which file an import names. The search order is fixed, and spid3r modules prints which root won:

# Root Origin label
1 The importing file's own directory disk
2 SPID3R_PATH (a ;-separated list) disk
3 ./stdlib, relative to the working directory disk
4 stdlib/ beside the executable, or above it disk
5 vendor/ from the nearest enclosing package vendor
6 The stdlib table compiled into the binary embedded

Each candidate is tried as written and then with a .matrix suffix. Disk always wins over the embedded table, which is what lets a project pin a patched stdlib/semver.matrix; the embedded table is the last resort that makes a single-file app work on a machine with no stdlib/ at all. An import spec may not escape these roots: an absolute path, a drive letter, angle brackets or a .. component is rejected with error[semantic]: invalid module path on every backend. (Only the tree walker enforced that before resolution was unified, so import "../x" used to load on two engines and fail on the third.)

A vendored package is a directory: vendor/mathlib/lib.matrix is imported as import "mathlib/lib". Which root a module came from — and therefore how much you should trust it — is the subject of the next section.

The Ecosystem: Packages and Trust

Third-party code reaches a program through four supported core routes, and they do not carry the same authority. Rust host applications embed via spid3r_lang::embed::Engine, and external CLI extensions run as spidr-<name> executables on PATH; anything not on this list is not an extension point.

Tier What Guarantee Status
T0 Built-in stdlib Embedded (26 modules, 254 native builtins), immutable, no disk override from the install tree shipped
T1 Project .matrix files Same trust as the project's own source shipped
T2 Vendored packages Checksummed against spider.lock; spid3r verify re-checks shipped
T5 FFI (extern fn) Trusted code, AOT-only; spid3r run rejects it at compile time shipped

Two things this page will not overstate. Capability filtering is a policy filter, not a sandbox: it replaces known builtin natives with stubs that return a catchable capability denied error for script engines, and a host function registered through spid3r_lang::embed::Engine::register keeps whatever authority the host gave it. And dependency installation never executes package code — there are no build scripts, unlike Cargo — which is a real security advantage and is deliberate.

Packages

A package is a directory with a spider.toml and a src/ tree. spid3r add declares it and vendors it in one step, spid3r tree shows what that resolved to, spid3r verify proves the vendored bytes are the ones the lock file describes, and spid3r publish --to-dir writes a registry entry with package.tar, index.txt, sha256.txt, and an Ed25519 signature sha256.txt.sig (registry.pub). spid3r install supports both local directory mirrors and remote http(s):// registries (SPID3R_REGISTRY / packages.registry, cached under .spid3r/registry/), verifies SHA-256 and Ed25519 signatures (pinned via packages.trust_pk / SPID3R_TRUST_PK), intersects compatible diamond semver ranges across both single-project and workspace dependency graphs, and never executes package code. Note: release tarballs built without tls support http:// mirrors and local directories; enable --features tls (included in Windows installers) for https:// registries.

Registry deep dive — resolution, layout, integrity, remote mirrors & signing

The full registry contract: a registry dependency pulls a package by name + version constraint (strlib = { version = "^1.2" }, optionally registry = "internal"), reusing the same vendoring and spider.lock machinery as path/git dependencies — only resolution is new. spid3r install vendors the resolved src/ tree into vendor/<name>/ and pins source = "registry+<resolved-version>" plus the content SHA-256; re-running install is idempotent. A registry is a directory named by SPID3R_REGISTRY (or packages.registry) — local files, a committed index, or a shared drive; there is no default remote registry in the base build, and an unset variable fails with a message telling you to set it.

Version constraint Meaning
^1.2 / ^1.2.3 same major, at least the given minor/patch
>=1.2.3 at least this version
=1.2.3 or bare 1.2.3 exactly this version

The chosen directory's spider.toml version must also satisfy the constraint (checked after resolution). The layout is $SPID3R_REGISTRY/<name>/<version>/ with a spider.toml, a src/ tree, and a required sha256.txt; version directories are major.minor.patch (or major.minor) and the highest satisfying version wins. Named sub-registries put packages under $SPID3R_REGISTRY/<name-from-registry-key>/<package>/<version>/. The sha256.txt hash covers every file under src/ over raw bytes — for each file in sorted order, relative/path + 0x00 + contents + 0x00, concatenated and hashed once, with / separators on every platform — and install refuses a missing, unreadable, empty or mismatched file. spid3r publish --to-dir <dir> writes the layout offline and refuses to republish an existing name/version (a registry entry is immutable; bump the version instead).

Integrity: spid3r verify re-hashes every vendored tree against the sha256 in spider.lock — a lock entry with no recorded hash also fails, and so does an undeclared directory under vendor/. Editing one vendored file therefore fails the build gate (exit 1) instead of being silently compiled. spid3r search <query> --local matches package names in SPID3R_REGISTRY and vendor/ without network access.

Remote registries, signing & dependency unification (R8.1–R8.4): SPID3R_REGISTRY / packages.registry also accept http:// / https:// URLs serving <base>/<name>/index.txt, package.tar and sha256.txt, cached under .spid3r/registry/<url-hash>/<name>/<version>/ after verifying tree hashes and path-traversal safety. Portable Unix tarballs are built without tls (so they support http:// mirrors and local directories but diagnose https:// clearly); Windows installers enable tls. publish --to-dir writes an Ed25519 sha256.txt.sig plus registry.key/registry.pub; when packages.trust_pk / SPID3R_TRUST_PK is set, install verifies the signature and refuses unsigned or tampered packages, otherwise it verifies against registry.pub or warns. Diamond dependencies across single-project and [workspace] manifests intersect all semver constraints per package name and re-select the highest satisfying version (e.g. ^1.0 + =1.2.0 → 1.2.0), reporting conflicts cleanly. No semver pre-releases or build metadata — plain major.minor.patch. A spider.lock entry records name, version, source, used-by (the workspace members that depend on it), files and sha256.

# Which file does `import "semver"` actually name?
spid3r modules src/main.matrix --tree
# Declare, inspect, then prove the tree is intact
spid3r add mathlib --path ../mathlib
spid3r tree
spid3r verify
# Publish into a static registry directory
spid3r publish --to-dir ../registry

Native Machine-Code Compilation (AOT)

Spid3r includes an Ahead-Of-Time (AOT) native compiler powered by LLVM 23 (available via both Stage 0 spid3r build and the self-hosted spid3r-self build). Release builds link a split runtime staticlib (spid3r_rt_start_slim + spid3r_reg_core plus only the opt-in subsystem groups your program calls, dead-stripping unused stdlib and scheduler code) and default to --target-cpu x86-64-v3 on AVX2/BMI2/FMA hosts:

# Compile script to a native standalone executable
spid3r build examples/hello.matrix -o hello.exe
# Run the generated native binary
./hello.exe
// Output: hello

Desktop Executables: Custom Icon, No Terminal

A plain spid3r build produces a console binary: on Windows it allocates a terminal window for the process, and the file carries the default toolchain icon. Three flags turn that into an ordinary desktop application (a fourth adds version metadata):

# Windowed desktop build with an embedded icon
spid3r build app.matrix -o App.exe --release --icon app.ico --subsystem windows
Flag Effect
--icon <path.ico> Embeds the icon into the PE resource directory as RT_ICON plus RT_GROUP_ICON. Every size stored in the .ico is preserved, so Explorer, the taskbar and Alt-Tab each pick the resolution they need. Without the flag the icon shipped beside spid3r.exe is embedded, so a build started from any directory still gets one; SPID3R_ICON overrides that default.
--subsystem windows Passes -subsystem:windows and pins the entry point with -entry:mainCRTStartup, setting the PE optional header's subsystem field to 2 (GUI) instead of 3 (console). Windows then allocates no console for the process. --subsystem console is the default. Windows-only; ignored by the ELF and Mach-O linkers.
--allow-gui Permits a build of a program that calls GUI natives even though the AOT runtime does not link the GUI bridge. Without it the compiler rejects such a program before linking.
--embed <path> Appends a file or directory to the finished executable, after linking, so --icon and --version still apply. Paths stay relative to the source file, and the body is XOR-obfuscated — obfuscation, not encryption. spid3r gui --payload <exe> runs the result with no sidecar files. Repeatable.
--bytecode <file.matrixc> Ships a compiled program instead of its source: appends the .matrixc to the payload and compiles the launcher from a three-line run_payload_strict() stub, so no application code, symbol names or string literals reach the native image. The strict form refuses to run when the payload is missing or truncated instead of falling back to an installed toolchain. gui --payload prefers a .matrixc entry and runs it on the VM.
--bundle-runtime Also appends the running spid3r.exe to the payload, so the built app starts its own runtime copy and runs on a machine with no Spid3r installed. Extracted to %LOCALAPPDATA%\Spid3r\runtime\<hash>\ on first launch. Implies a payload.
--product-name / --version Writes RT_VERSION metadata, displayed in the file's Properties → Details tab.

--allow-gui exists because the AOT runtime registers the standard library natives but not the GUI bridge, so gui_on, gui_eval and friends resolve to null in a native binary. The supported pattern is a launcher: the executable does its startup work, then hands the program off to the installed toolchain's spid3r gui runtime. One native call does all of it — run_payload() finds a runtime (payload first, then %SPID3R_EXE%, the normal install, PATH), extracts the embedded copy when there is one, anchors the working directory to the executable's folder, and starts gui --payload hidden. Writing the handoff by hand is only necessary for custom startup behaviour.

# The whole launcher: one call. It finds a runtime, extracts the
# embedded copy if there is one, anchors the working directory and
# starts `gui --payload` with no console.
fn main() {
return run_payload();
}

Two entry points, and the difference matters for a self-contained build. run_payload() falls back to an installed spid3r when the executable carries no payload at all — which is what a hand-written launcher that expects a global install wants. run_payload_strict() treats a missing payload as a hard error ("payload is missing or truncated; rebuild it"); it is what --bytecode generates, and what a launcher should call when the build is supposed to carry its own runtime, so that deleting the trailer cannot redirect the launch to whatever spid3r.exe is on PATH.

⚠️ Two details that decide whether the window ever appears

run_payload() already does both. They matter when you write the handoff yourself, which is only necessary for custom startup behaviour.

  • Working directory ≠ program folder. Windows starts a process with an inherited directory, so a shortcut, the Run dialog, a scheduled task or Start-Process all begin somewhere else. Relative paths like ui/index.html then miss, and a GUI-subsystem process exits with no visible message because it has no console to print to. Call exe_path() and chdir(dirname(exe_path())) first.
  • The handoff inherits the console. Spawning without map("hidden", true) opens a terminal window for the child. That option passes CREATE_NO_WINDOW on Windows; on other platforms it is ignored.

Shipping a Single File

Two flags turn a build into one self-contained executable: --bundle-runtime appends the running spid3r.exe to the payload, so the target machine needs no Spid3r install, and --bytecode ships the compiled program instead of its source.

# 1. compile the program
spid3r compile app.matrix -o app.matrixc
# 2. one executable: icon, no terminal, bytecode, UI, runtime
spid3r build app.matrix -o App.exe --release --icon app.ico \
--subsystem windows --bytecode app.matrixc \
--embed ui --bundle-runtime
Payload entry What it is
app.matrixc The compiled program. No .matrix is shipped.
ui/index.html, ui/app.js, ui/styles.css The interface, served from memory — nothing is unpacked to disk.
__spid3r_runtime/spid3r.exe The runtime, extracted to %LOCALAPPDATA%\Spid3r\runtime\<hash>\ on first launch and reused afterwards.

--allow-gui is not needed with --bytecode: the launcher is compiled from the three-line run_payload() stub above, which mentions no GUI natives. It is only required when the application itself is compiled into the binary (--embed app.matrix).

⚠️ What --bytecode does and does not buy
  • It removes the source text. With --embed app.matrix the payload carries your source, and the obfuscation is not encryption — anyone can read it back out. With --bytecode the payload carries bytecode, and the launcher carries no application code, symbol names or string literals.
  • It is not secrecy. The VM is open source, so a determined person can write a decompiler for the bytecode. It raises the cost from "open a text file" to "reverse-engineer a bytecode format". Do not put secrets in a client binary.
  • One system dependency remains. The WebView2 runtime (default on Windows 11, on Windows 10 via Edge) — and the matching system webview on macOS/Linux. Everything else is self-contained: the toolchain and every executable spid3r build produces link the C runtime statically and import only system DLLs, so no Visual C++ Redistributable is needed. LLVM-C.dll is delay-loaded and is only touched by spid3r build, so a GUI app never needs it.

10. Object-Oriented Programming (OOP)

Spid3r provides first-class object-oriented programming: classes, single inheritance (extends), constructor and method delegation (super), encapsulation (public / private), and interfaces (implements).

Core OOP Rules & Visibility

  • Constructors: The constructor is declared as public fn new(params) { ... }. Inside the constructor, self is implicitly bound to the newly allocated instance.
  • Explicit Receiver: Instance methods explicitly take self as their first parameter: public fn method(self, arg) { ... }.
  • Default Visibility is Private: Any member without an explicit public keyword is private to the defining class. The checker enforces this whenever the receiver's class is statically known — an annotated binding (let c: C = C()), new C(), or self — and leaves a receiver whose class is only known at run time unchecked, the same gradual rule the rest of the checker follows. Annotate the binding when you need the guarantee: let c = C(); c.secret is accepted, let c: C = C(); c.secret is rejected.
  • Single Inheritance: Classes inherit from a single parent class using class Sub extends Parent.
  • Super Delegation: Subclasses call super(args) in their constructor to initialize the parent fields, and super.method(args) to delegate to the parent method.
  • Abstract Classes & Static Methods: Declared with abstract class Base, abstract classes define method contracts that cannot be instantiated directly. Classes may also declare class-level methods with public static fn name(args) { ... } (called directly on the class as ClassName.name(args) without self).
⚡ Example: Classes, Inheritance & Super Delegation

(Breed: " + self.breed + ")"; } } let pet = new Dog("Rex", "German Shepherd"); println(pet.speak()); println("Initial Energy: " + string(pet.get_energy())); println("After playing: " + string(pet.play(25)));

Generics, Constraints & AOT Monomorphization

Functions, classes, and interfaces support multi-argument generic type parameters (such as <T> or <K, V>) with optional trait/interface constraints:

  • Built-in & Interface Constraints: <T: Numeric>, <T: Comparable>, <T: Printable>, any declared interface <T: Drawable>, or intersection bounds with + (<T: Numeric + Comparable>).
  • Explicit & Inferred Type Arguments: Call sites and constructors accept explicit type arguments (identity<int>(42), new Box<string>("hi")) or infer them from value arguments. Unannotated generic parameters stay backward-compatible via type erasure in the Tree and VM engines.
  • AOT Monomorphization & Unboxed Collections: When compiling natively with spid3r build, concrete generic specializations are monomorphized (spid3r_mono_*) and homogeneous numeric lists (list<int>, list<float>) use unboxed i64/f64 storage backed by 12 specialized runtime trampolines (spid3r_ulist_i64_*, spid3r_ulist_f64_*).
Generics & unboxing internals (R10 · DP-1) — 16-byte Value / ValueV2, monomorphization & loop hoisting

Shipped implementation (DP-1 Option A): Runtime Value is pinned to 16 bytes (size_of::<Value>() == 16 in src/value/mod.rs) via 8-byte ThinArcStr pointers, boxed Result, and lock-free single-threaded FastMutex containers (upgrading to synchronized locking only after the first spawn). Across the native AOT C-ABI boundary, values pass as 16-byte ValueV2 { tag: u64, payload: u64 } structs carrying inline Null, Bool, Int, Float, and short SSO strings with zero heap allocation, thread-local rope slices (TAG_ROPE), or reclaimable TAG_HEAP pointers tracked by AOT_HEAP. All pointer/tag unsafe blocks remain audited with written // SAFETY: invariants inside src/native/rt.rs and src/value/mod.rs.

Erased-syntax backward compatibility. Existing programs use erased generic syntax with no explicit type arguments (class Box<T>, fn first<T>(xs), fn identity<T>(x), fn head<T>(xs) -> T). Type arguments at call and construction sites (identity<int>(7), new Box<int>(7)) remain optional; when omitted the checker infers concrete arguments from call arguments where possible or falls back to Any (dynamic Value). Unconstrained <T> with untyped parameters keeps type-checking and executing identically across Tree, VM, WASM and AOT.

Parser & AST. TypeExpr carries args: Vec<TypeExpr> so multi-parameter types (map<string, int>, result<int, string>, Pair<int, bool>) are represented directly; TypeParam { name, bound, span } records optional bounds (<T>, <T: Comparable>, <K, V>), and explicit type arguments on calls and constructors are disambiguated from less-than by lookahead (< followed by a type list then >().

Checker instantiation & constraints. Declared TypeParams bind with their optional Comparable/Numeric/Printable/interface bound during function/class checking; at instantiation the checker verifies each concrete type satisfies the bound and emits a Phase::Semantic diagnostic on mismatch or wrong arity. A deduplicated InstantiationSet records MonoFnKey { name, type_args }, MonoClassKey { name, type_args } and typed container annotations propagated to local, parameter and return type tables. Sorting with a Comparator & Float Precision

xs.sort_by(cmp) sorts in place (returns null), xs.sorted_by(cmp) returns a new list, and xs.argsort() returns the original indices in ascending order (list(30, 10, 20).argsort() → [1, 2, 0]). A comparator cmp(a, b) returns either a bool (true = a before b) or a number (negative/0/positive = before/equal/after). Sorts are stable: the list is snapshotted before comparison, no lock is held while a comparator runs, and the sorted snapshot is written back after the last call — so a comparator that throws, mutates the receiver or touches a self-referential list gets a clean result, never a deadlock or host panic. Because false cannot distinguish "after" from "equal", the mirrored question cmp(b, a) is asked whenever cmp(a, b) is false; keep comparators side-effect free. Non-bool/int/float or NaN returns throw a catchable error.

A format placeholder may carry precision {:.N} for N in 0..=15 — "{:.2}".format(88.6875) → "88.69", "{:.0}".format(2.5) → "2" (tie-to-even, unlike round(x), which rounds halves away from zero). An int is widened to fixed point; precision > 15, a non-number placeholder, or a malformed spec such as {:.}/{:x} is a catchable error. Methods validate arguments and throw on violation (empty stack.pop(), out-of-range get(i), a method the collection does not have); these are ordinary catchable thrown values.

Matrix Indexing Architecture

  • 2-D Indexing: Use m.get(row, col) and m.set(row, col, value) to address cells by row and column.

13. Concurrency, Tasks & Message Channels

Spid3r runs tasks on an M:N scheduler: a lazily initialized pool of OS threads (starting on the first spawn, growing on demand up to SPID3R_MAX_WORKERS, default 256) pulling from one shared ready queue, with no global interpreter lock — two CPU-bound tasks really do run at the same time. Single-threaded scripts stay on the lock-free FastMutex container fast path (and AOT binaries without spawn dead-strip the scheduler pool cleanly); spawned workers sweep and trim thread-local AOT_HEAP state on exit to keep long-running concurrent servers memory-bounded.

Tasks, Join, and Async-Await

  • Task Spawning: spawn fn() { ... } spawns a concurrent task and immediately returns a task handle.
  • Joining Tasks: task.join() blocks until the task finishes and returns its result (or throws if the task encountered an unhandled exception).
  • Async / Await: Functions marked async fn name() { ... } can use await task or await channel.
  • Channels: let ch = channel(); creates a buffered message channel — an unbounded FIFO queue. ch.send(val) appends and returns immediately (it never blocks, so a producer cannot deadlock on a full queue), and ch.recv() blocks until a value is available. Values are dynamically typed, like every other Spid3r binding.
  • Mutex: let mu = mutex(initial_value); guards critical sections with mu.lock() and mu.unlock().
  • Atomic Integers: let a = atomic_int(0); (argument defaults to 0) provides lock-free 64-bit atomic operations across tasks: .load(), .store(val), .exchange(val), .cas(expected, desired), .fetch_add(delta), and .fetch_sub(delta).

⚠️ Cryptography & TLS Trust Statement (R12.1)

Encrypted transport (https:// in http_fetch, plus tls_listen / tls_accept in src/stdlib/net.rs) is provided by the vetted native-tls crate behind the optional tls Cargo feature — delegating TLS handshakes and certificate validation to the OS TLS stack (Schannel on Windows, OpenSSL on Linux, Security.framework on macOS) and the OS certificate store, never hand-rolled TLS. By contrast, the built-in hashing, KDF, and signature primitives (sha256, sha512, hmac_sha256, pbkdf2_sha256, ed25519_*, bcrypt_*, argon2) are self-contained pure-Rust implementations with zero external dependencies and have not yet undergone an independent third-party cryptographic audit. They are verified by internal RFC test vectors and negative/malleability tests — Ed25519 uses a constant-time cswap Montgomery ladder with canonical S < L and small-order-key rejection — but are not formally proven side-channel hardened, and R12.1 remains open pending an external review report. For high-stakes production workloads or side-channel-hostile environments, run secret-key operations behind an audited proxy or HSM. Cryptographic randomness comes only from random_bytes(n) (OS CSPRNG: /dev/urandom, RtlGenRandom); random_int/random_float/random_normal are clock-seeded xorshift and never suitable for tokens. jwt_verify is constant-time with a 60-second exp/nbf skew but checks HS256 only and does not pin alg to a policy — do not feed it tokens from an issuer you do not control.

The spid3r.ini File

A single INI file configures the runtime. The discovered candidates are tried in this order (first hit wins) — except for the authoritative SPID3R_INI pin described below:

  1. $SPID3R_INI — when set and non-empty, the only ini candidate
  2. spid3r.ini next to the spid3r executable
  3. platform config dir (%APPDATA%\Spid3r, $XDG_CONFIG_HOME/spid3r, ~/.config/spid3r)
  4. ./spid3r.ini

SPID3R_INI is authoritative: when it is set and non-empty it is the only ini candidate. If that path is missing or unreadable the loader uses compiled defaults only (it never falls through to the machine or working-directory ini), records a typed pin failure for local diagnostics, and program-executing commands (run, check, compile, exec, test, bench, debug, gui, repl, magic) refuse to start with exit 1. --version, help, info, config path and config validate remain usable to diagnose the pin — the local control config set / spid3r config init paths are how an operator repairs it. Restart a long-lived process that initialized its policy while the pin was broken; its fail-closed policy remains sticky until restart. spid3r config validate reports a broken pin as a problem (exit 1) and treats an unknown flag as a usage error (exit 2); local diagnostics keep policy values raw so the bad entry is visible. spid3r control config validate exits 1 with errors on stderr when valid:false.

Precedence, highest first: process environment → [env.<name>] (selected by SPID3R_ENV or [spid3r] env) → the INI file → compiled defaults. Every layer is validated with the same rules: a value that fails its type/range check is ignored with a note and the compiled default stays in effect (a bool must be true/false/1/0/on/off/yes/no; a typo like ture is an error, not a silent true). A UTF-8 BOM at the start of the file is tolerated. Unknown keys are reported by spid3r config validate and never abort a run. Live reload: spid3r config reload or SIGHUP on Unix. The [logging] keys enabled, file and audit are honored (the SPID3R_LOG/SPID3R_LOG_FILE env vars override the INI). Config and state files are written atomically (temp file + rename).

Operator Reference: Limits, Diagnostics and Cross-Platform Details

Run-time limits. runtime.wall_clock_limit_ms arms a wall-clock deadline for spid3r run — expiry is a fatal, uncatchable wall-clock limit exceeded (N ms) error on the tree and VM engines, checked at statement boundaries, at the VM's instruction poll, and around blocking native calls (residual granularity is one blocking operation). The native AOT backend is not wired to it. Deadline and cap are Arc-shared with spawned tasks and module interpreters, and config reload applies new values live. runtime.memory_limit_mb is a catchable soft cap on total script-value heap (out of memory: script exceeded memory_limit_mb (N) — a program may catch it, drop the offending container, and continue). Accounting covers every tracked heap cell (containers, instances, closures, classes), counts strings by byte length and containers by element count, ignores free-standing scalars/strings in untracked environments, and refreshes at most every 25 ms — so the cap is approximate by design. runtime.timezone sets the datetime default: UTC, a fixed offset like +06:00, or an IANA name from tz_names(); anything else is rejected at load with a note and UTC stays in effect.

15. Virtual Machine Internals, GC & WebAssembly

Spid3r has three execution engines — a tree-walking interpreter, a bytecode VM, and an LLVM ahead-of-time compiler — built on one parser and one semantic checker. This chapter is about what the VM does with your program, how the cycle collector reclaims memory that reference counting cannot, and how the same VM runs inside a browser.

Three Engines, One Front End

Every engine consumes the same parsed and checked program, so anything that type-checks runs on all three. spid3r test is what keeps them honest: it runs every example on the tree interpreter, the VM, and the compiled .matrixc artifact, and fails if the output differs.

🧬 Self-hosting status

The compiler and core developer tools are written in Spid3r across 17 compiler/CLI modules (21 .matrix files) in selfhost/: lexer, parser, semantic checker & lints, lowering, bytecode compiler (.matrixc), LLVM-C codegen (with default<O3> PassBuilder optimizations), cross-OS linker/driver, and the test, fmt, and package tools (pack/unpack/verify/dist). Compiled via Stage 0 (spid3r build selfhost/main.matrix -o selfhost/main_native.exe), spid3r-self reaches a bit-identical Stage 1 → Stage 2 → Stage 3 object fixed point across the 136-program frozen corpus, verifies a SHA-256-pinned runtime staticlib (spid3r-self verify-runtime, RUNTIME_ABI.md), and links split runtime units (spid3r_reg_core plus 10 opt-in subsystem groups) alongside compact 16-byte Value/ThinArcStr representations and pre-decoded VM superinstructions. See the self-hosting hub, ADR, Language Specification, Concurrency Model, and Stability Report.

Self-Hosted Compiler Architecture & Bootstrap Boundary

Rebuilding selfhost/ or running compiler and dev-CLI commands with spid3r-self requires zero cargo or rustc calls. Rust Stage 0 (src/) stays in place permanently as the cold bootstrap seed, differential oracle (src/oracle.rs), pinned runtime staticlib (117 spid3r_* C-ABI trampolines — including split spid3r_reg_* registration, unboxed spid3r_ulist_*/row/SSO-map views, and frame/safepoint GC hooks — plus 254 stdlib natives), and host for non-AOT engines/tools (tree, vm, repl, debug, lsp, spid3r-control, gui, wasm32).

What a Compiled Chunk Holds

Each function compiles to a Chunk: a Vec<u8> of encoded instructions, a constant pool, the prototypes of every nested function, and the class descriptors. Two parallel arrays map instruction indices to byte offsets and source spans, which is how a runtime error can point at the exact line that raised. Nested prototypes are shared through Arc, so creating a closure at run time is a refcount bump rather than a copy of the function's code.

The instruction set is 60 opcodes, from Constant and GetLocal up through the object-model and concurrency additions (SuperCtor, SuperMethod, CaptureSync, FieldGetSoft). Opcodes are byte-encoded, and OpCode::from_u8 rejects any value it does not know.

A .matrixc file is that chunk graph serialized. Loading it is defensive by construction: a magic check, a format-version check, a bounds-checked deserializer, and validate_chunk all run before the first instruction executes, so a corrupt or truncated artifact is a clean error and never a misread. The compatibility promise is one-directional: an artifact written by any 1.x build loads on every later 1.x build, while an older build reading a newer artifact must reject it cleanly rather than guess.

Frames, Calls and Unwinding

A CallFrame holds the function being run, its instruction pointer, its local slots, a display name used in stack traces, and — deliberately — its own globals map: name resolution uses the module that defined the function, not the caller's. Method frames carry the qualified Class::method form and constructors Class::new, so a trace reads the same on the VM as on the tree interpreter.

Call depth is capped at 1,000 frames. Exceeding it produces an ordinary runtime error (stack overflow: call depth limit reached) with a source span, not a host crash — a runaway recursive function is a diagnosable mistake rather than a dead process.

try/catch/finally is not host unwinding. Each handler records the catch target, the finally target, the catch slot, and the operand-stack length and frame depth that were live when it was pushed. On a throw the VM restores both to exactly those values before jumping, so a handler sees a clean stack no matter how deep the failure happened.

The Optimizer

After compilation and before serialization, every reachable chunk is optimized: constant folding, peephole rewrites, and dead-code removal. The design rule is that no transformation may change observable behaviour, and the implementation enforces it three ways:

  • Folding uses the interpreter's own helper. Constant a; Constant b; <binop> is evaluated through the same vm_eval_binary the dispatch loop calls, so numeric promotion and string concatenation produce byte-identical results.
  • Failing operations are not folded. 1 / 0 and "a" - 1 stay in the bytecode, so the error still fires at run time with the same message and span.
  • Jumps win over folding. A fold is skipped when any jump or handler target points into the middle of the sequence being folded — a target must keep landing on a real instruction.

A fourth pass rotates canonical while loop back-edges. A loop emitted as <cond>; JumpIfFalse end; <body>; Jump start; end: becomes <cond>; JumpIfFalse end; <body>; <cond>; JumpIfTrue body_start; end:. The condition is duplicated, never reordered, so evaluation count, order and stack effect are unchanged; steady-state iterations simply skip one unconditional jump. The pass lives only in src/vm/opt.rs, so --no-opt never sees it. It adds no opcode and does not change the .matrixc format, and it is skipped for chunks containing Try, for conditions with internal jumps or side effects, and when a jump from outside could land inside the loop. Because it removes work at compile time, --prof on the default path reports exactly one fewer executed instruction per loop iteration than --prof --no-opt; the runtime fused superinstructions remain disabled under instrumentation and, since Phase 5, under --no-opt as well (Vm::set_opt_enabled gates the VM peeks); per-VM inline caches are memoization and stay on. In both cases no opcode is hidden.

Pre-decoded instruction stream & benchmark integrity (src/vm/decode.rs). On disk, .matrixc chunks remain compact byte streams using the 60 stable OpCode discriminants so --prof, --coverage, debugger stepping, --no-opt, and selfhost/vmc.matrix parity stay untouched. On first execution of an uninstrumented chunk, DecodedChunk::compile translates the validated bytecode once into 16-byte fixed-width DecodedInst records with direct jump targets, general multi-opcode superinstructions, and pure-leaf fast call dispatch (exec_pure_leaf_1). All optimizations are strictly general-purpose; tests/vm_integrity_guard.rs enforces that no workload-specific bytecode fingerprints exist in the VM.

The Execution Budget

Embedders that run untrusted code can set a step allowance. It is a shared, saturating counter: the tree engine charges a step per statement and per loop iteration, the VM charges in batches at its instruction poll, and spawned tasks draw from the same allowance as the code that spawned them. When it runs out, the error is fatal — it bypasses try/catch in both engines, so a script cannot swallow the stop and keep running. On the native AOT backend, budget enforcement is off by default (for zero counter overhead) and opt-in at compile time via spid3r build --enforce-budget <N>; embedders running untrusted code with dynamic capability filtering use the tree or VM engine.

The budget bounds time; a separate policy bounds authority. An embedding host can deny whole capabilities, and each native the capability covers is replaced by a stub that raises a catchable error instead of reaching the OS:

let engine = Engine::new().deny(Capability::FileSystem);
let engine = Engine::new().deny_all();
# Capability::FileSystem | Process | Network | Environment

Garbage Collection: Cycles & Bounded AOT Reclamation

Values are reference-counted using a compact 16-byte Value layout (8-byte ThinArcStr pointers, boxed Result, and lock-free single-threaded FastMutex prior to the first spawn). That handles the common case for free: the moment the last reference to an acyclic list drops, its memory is gone, with no collector involved. What reference counting cannot do is reclaim a cycle — two values pointing at each other, or a value that contains itself — because every member of the cycle keeps the next one's count above zero. Those cells would leak until the process exits.

The collector is a mark-sweep that deliberately never enumerates roots. Enumerating every place a live value can hide — interpreter environments, VM frame slots, globals, upvalue cells, task captures — is exactly where a collector gets it wrong, and one missed root means a use-after-free. Instead it computes, for each tracked cell, how many references come from outside the tracked set:

external(cell) = strong_count(cell) - internal_edges_into(cell)
# saturating at zero; internal_edges is counted by tracing every tracked cell

Anything holding a strong reference from outside the tracked set — an environment binding, a Rust local mid-expression, a global, a captured upvalue — shows up as extra strong_count, so that cell has external > 0 and is a root. The collector marks everything reachable from a root, then sweeps what is left: those cells are reachable only from each other, which is the definition of a closed cycle.

⚠️ The safety asymmetry that makes this correct

If tracing misses an edge, internal_edges comes out too small, external too large, and the cell is treated as a root and kept — a leak, never a crash. If tracing ever over-counted an edge, a live cell could compute external = 0 and be swept while still in use. So the rule is absolute: count each strong child exactly once, never count weak references, and leave a container untraced if you are unsure of its children. Being conservative costs memory; being optimistic costs correctness.

Reading strong_count is only sound while nothing else is mutating it, so collection runs only when no other thread is executing Spid3r code. Tasks parked in a blocking wait (recv, join, mutex.lock, sleep) do not count as running — their values sit on their own stacks and are therefore roots. If you call gc_collect() while another thread is running, it fails with a clean message naming how many threads are in the way, rather than collecting under a race.

Systems FFI, POD Structs & Freestanding AOT

The LLVM AOT backend (src/native/ir.rs) supports systems-level C interop and bare-metal code generation:

  • Static & Shared Linking: Pass --link-lib <name|path> to spid3r build (repeatable) so extern fn declarations resolve against system libraries (-l<name> on Unix, <name>.lib under MSVC).
  • Variadic FFI, Callbacks & POD Structs: extern fn supports C variadics, ffi_callback(fn, "fn(...)->...") generates C-ABI trampolines for passing Spid3r functions to C APIs, and POD structs marshal by value across the FFI boundary.
  • Runtime dlopen Gate & Freestanding Mode: Dynamic loading primitives (dl_open, dl_sym, dl_close, dl_call) are gated off by default unless --allow-dlopen (BuildOptions.allow_dlopen) is enabled, and --freestanding (with optional --emit-obj, --entry <sym>, and --sysroot <dir>) emits host-independent IR/objects without linking the standard runtime.
