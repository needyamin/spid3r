Spid3r Documentation / Developer Manual & Language Specification

Spid3r Developer Portal & Complete Language Reference

Welcome to the official developer manual for Spid3r. This guide explains every single detail of the language: how it works, its grammar, type system, object-oriented model, data structures, concurrency runtime, standard library, and how to execute code directly in your browser.

01. Introduction to Spid3r

Spid3r is a modern, high-performance, memory-safe, embeddable general-purpose programming language built from scratch in Rust with zero external dependencies.

It combines clean, expressive C/JavaScript-style syntax with the safety guarantees of managed memory, the mathematical power of NumPy/BLAS-style contiguous matrices and vectors, the concurrency model of Erlang/Go channels, and an instant WebAssembly compiler that lets you run complete programs inside any browser.

💡 Key Design Tenets
  • Zero External Dependencies: The entire compiler, bytecode virtual machine, AST interpreter, standard library (including cryptographic primitives, regex engines, date-time calendars, and compression algorithms) is written in pure, self-contained Rust.
  • Dual Execution Engines: Run programs with the high-speed --engine vm (bytecode register/stack virtual machine) or the pure reference --engine tree (AST tree-walk interpreter) with 100% byte-for-byte behavioral parity (program stdout, exit codes, and side effects).
  • Zero-Leak Tracing Garbage Collection: Deterministic mark-and-sweep cycle collector with interior-mutable cell headers and weak references.
  • Native WebAssembly Core: Zero-overhead compilation target exportable as a 100% self-contained linear-memory engine running in web browsers, Node.js, Deno, and Edge Workers.

02. How Spid3r Works: Compiler & VM Pipeline

Understanding the Spid3r internal execution pipeline helps you write highly optimized code and leverage both the VM and AOT native backends.

Phase Component Responsibility Output Artifact
1. Lexical Analysis src/lexer/mod.rs DFA-based tokenizer recognizing radix literals (0x, 0o, 0b), scientific float notation (1.5e3), Unicode escapes (\u{1F600}), and desugaring string interpolation holes ({var}). Stream of Token structs with line/col spans
2. Syntax Parsing src/parser/mod.rs Top-down recursive descent + Pratt precedence parser. Enforces strict maximum statement nesting of 64 levels to prevent call stack exhaustion. Abstract Syntax Tree (ast::Program)
3. Semantic Analysis src/semantic/mod.rs Scope resolution, variable declaration verification, constant folding, class member visibility checking (public / private), interface contract compliance, and dead code detection. Validated AST or descriptive compiler diagnostic
4. Lowering Pass src/lower/mod.rs Desugars high-level syntax into core primitives: converts ?? into null checks, value-position if into branch blocks, for (k, v) in map into iterator lookups, and destructuring tuples into temporary bindings. Desugared Low-level AST
5. Dual Execution src/vm/ & src/interpreter/ Bytecode VM: Compiles AST to compact bytecode (.matrixc) and runs on a fast register-stack virtual machine.
Tree Interpreter: Walks the AST directly for reference parity and differential audit testing.		 Live execution, captured stdout, exit status
6. Memory Management src/value/gc.rs & src/value/mod.rs Tracing mark-and-sweep garbage collection with cell tracking, weak references, and zero-leak cyclic object reclamation. Reclaimed heap cells

Module Resolution

Every backend resolves import "name" through one implementation, so the tree interpreter, the bytecode VM and the AOT compiler cannot disagree about which file an import names. The search order is fixed, and spid3r modules prints which root won:

# Root Origin label
1 The importing file's own directory disk
2 SPID3R_PATH (a ;-separated list) disk
3 ./stdlib, relative to the working directory disk
4 stdlib/ beside the executable, or above it disk
5 vendor/ from the nearest enclosing package vendor
6 The stdlib table compiled into the binary embedded

Each candidate is tried as written and then with a .matrix suffix. Disk always wins over the embedded table, which is what lets a project pin a patched stdlib/semver.matrix; the embedded table is the last resort that makes a single-file app work on a machine with no stdlib/ at all. An import spec may not escape these roots: an absolute path, a drive letter, angle brackets or a .. component is rejected with error[semantic]: invalid module path on every backend. (Only the tree walker enforced that before resolution was unified, so import "../x" used to load on two engines and fail on the third.)

A vendored package is a directory: vendor/mathlib/lib.matrix is imported as import "mathlib/lib". Which root a module came from — and therefore how much you should trust it — is the subject of the next section.

The Ecosystem: Packages, Plugins and Trust

Third-party code reaches a program through seven routes, and they do not carry the same authority. The tiers below are the whole trust model; anything not on this list is not a supported extension point.

Tier What Guarantee Status
T0 Built-in stdlib Embedded, immutable, no disk override from the install tree shipped
T1 Project .matrix files Same trust as the project's own source shipped
T1 Spid3r plugins (kind = "matrix") Written in the language and loaded from disk; script authority, like your own source shipped
T2 Vendored packages Checksummed against spider.lock; spid3r verify re-checks shipped
T3 WASM plugins Sandboxed — no ambient authority, manifest-declared permissions, fuel-limited shipped
T4 Host plugins Trusted code. Not sandboxed, and cannot be shipped
T5 FFI (extern fn) Trusted code, AOT-only; spid3r run rejects it at compile time shipped

Two things this page will not overstate. Capability filtering is a policy filter, not a sandbox: it replaces known builtin natives with stubs that return a catchable capability denied error, and a host function a plugin registers keeps whatever authority it was given — no filter can take that back. And dependency installation never executes package code — there are no build scripts, unlike Cargo — which is a real security advantage and is deliberate.

Packages

A package is a directory with a spider.toml and a src/ tree. spid3r add declares it and vendors it in one step, spid3r tree shows what that resolved to, spid3r verify proves the vendored bytes are the ones the lock file describes, and spid3r publish --to-dir writes a static registry entry with a checksum. None of it touches the network, and none of it runs the package's code.

# Which file does `import "semver"` actually name?
spid3r modules src/main.matrix --tree
# Declare, inspect, then prove the tree is intact
spid3r add mathlib --path ../mathlib
spid3r tree
spid3r verify
# Publish into a static registry directory
spid3r publish --to-dir ../registry

Plugins

Host plugins work today. A plugin declares itself in a plugin.toml, implements one trait, and is registered by its host at startup. There is no dynamic loading: a plugin is compiled into the host that uses it, because a native function is a Rust function pointer over Value, and Value has no stable representation that could cross a C ABI boundary.

The payoff of the design is that registration merges the plugin's functions into stdlib::native_defs() — the one list the tree interpreter, the bytecode VM and the AOT backend all install from. A plugin function needs no per-engine code.

# plugin.toml — the manifest is the contract
[plugin]
name = "hello"
abi = "spid3r-plugin-abi-1"
capabilities = ["environment"]
# one block per function, with its arity and permission
[[function]]
name = "hello_env"
arity = 1
permission = "environment"

register rejects, before any plugin code runs: an abi that is not exactly spid3r-plugin-abi-1; a function the manifest never declared, or one whose arity disagrees; a permission the manifest's capabilities does not announce; a duplicate name; and a function that would shadow a builtin — write_file must not be interceptable. A plugin whose start() fails is recorded as Failed and simply never offers its functions, so one broken plugin cannot take the host down.

The permission gate is the same mechanism as for builtins: Engine::deny(Capability::Environment) replaces hello_env with a stub returning a catchable capability denied error, while the plugin's other functions keep working.

A complete sample lives at examples/plugins/hello-host/ — a manifest, a PluginHost implementation, a host binary and two scripts, including one that demonstrates the gate. See docs/PLUGINS.md for the full contract.

WASM plugins: the sandboxed route

A WASM plugin is the opposite of a host plugin: it exists only as a file. The toolchain reads plugin.toml and plugin.wasm from the plugin search path and interprets the module, so spid3r run can call it without the binary being rebuilt.

# discovery order
SPID3R_PLUGINS · ./plugins · <exe>/plugins · ~/.spidr/plugins
# run a program that calls a sandboxed plugin
SPID3R_PLUGINS=examples/plugins spid3r run app.matrix
# the guest must export its memory and two helpers
memory · alloc(i32) -> i32 · dealloc(i32, i32)

Each manifest function is one export with the signature (i32, i32) -> i64: the host writes the arguments into linear memory, calls the export, and reads the result back. There is no dispatch table inside the guest. The wire format is a small typed binary encoding — null, int, float, bool, string, list — rather than JSON, so a plugin author does not have to ship a JSON parser into the sandbox.

The sandbox is structural: the host builds an empty linker, so a module that imports anything — fd_write, a clock, randomness — fails to instantiate. Nothing is revoked at run time, because nothing was ever granted. Every call also carries a fuel budget, so a loop {} traps instead of hanging the interpreter; that is the one place a limit is enforceable below the language, and it is what makes running an untrusted plugin safe.

spid3r build and spid3r dist deliberately do not load plugins: a standalone native executable cannot link one. A program that calls a plugin function is rejected at compile time, with a note explaining why — not compiled into a binary that throws at run time.

Route Status
Spid3r plugins (kind = "matrix", loaded from disk) works — no feature flag, no build step
Host plugins (compiled into the host) works
WASM plugins (kind = "wasm", loaded from disk) works — wasmi, behind the default plugins-wasm feature
FFI (extern fn) works — AOT only; spid3r run rejects it at compile time
spid3r plugin abi|list|check works — abi prints the version, list reports the search path, check validates a directory against ABI v1
spid3r plugin enable/disable not implemented — a plugin is discovered per run, so there is no persistent enable list
Dynamic loading of native code (dlopen) deliberately not implemented — there is no stable ABI to load against

The distinction that matters: a host plugin is trusted code — same address space, same authority, and no filter can revoke what it already has. A WASM plugin is the only route that can be sandboxed, and it is the one to prefer for anything you did not write. Both samples are in the repository: examples/plugins/hello-host and examples/plugins/hello-wasm.

Native Machine-Code Compilation (AOT)

Spid3r includes an Ahead-Of-Time (AOT) native compiler powered by LLVM. With spid3r build, any .matrix script can be compiled directly into a standalone machine-code executable that runs natively without any external runtime dependencies:

# Compile script to a native standalone executable
spid3r build examples/hello.matrix -o hello.exe
# Run the generated native binary
./hello.exe
// Output: hello

Desktop Executables: Custom Icon, No Terminal

A plain spid3r build produces a console binary: on Windows it allocates a terminal window for the process, and the file carries the default toolchain icon. Three flags turn that into an ordinary desktop application (a fourth adds version metadata):

# Windowed desktop build with an embedded icon
spid3r build app.matrix -o App.exe --release --icon app.ico --subsystem windows
Flag Effect
--icon <path.ico> Embeds the icon into the PE resource directory as RT_ICON plus RT_GROUP_ICON. Every size stored in the .ico is preserved, so Explorer, the taskbar and Alt-Tab each pick the resolution they need. Without the flag the icon shipped beside spid3r.exe is embedded, so a build started from any directory still gets one; SPID3R_ICON overrides that default.
--subsystem windows Passes -subsystem:windows and pins the entry point with -entry:mainCRTStartup, setting the PE optional header's subsystem field to 2 (GUI) instead of 3 (console). Windows then allocates no console for the process. --subsystem console is the default. Windows-only; ignored by the ELF and Mach-O linkers.
--allow-gui Permits a build of a program that calls GUI natives even though the AOT runtime does not link the GUI bridge. Without it the compiler rejects such a program before linking.
--embed <path> Appends a file or directory to the finished executable, after linking, so --icon and --version still apply. Paths stay relative to the source file, and the body is XOR-obfuscated — obfuscation, not encryption. spid3r gui --payload <exe> runs the result with no sidecar files. Repeatable.
--bytecode <file.matrixc> Ships a compiled program instead of its source: appends the .matrixc to the payload and compiles the launcher from a three-line run_payload_strict() stub, so no application code, symbol names or string literals reach the native image. The strict form refuses to run when the payload is missing or truncated instead of falling back to an installed toolchain. gui --payload prefers a .matrixc entry and runs it on the VM.
--bundle-runtime Also appends the running spid3r.exe to the payload, so the built app starts its own runtime copy and runs on a machine with no Spid3r installed. Extracted to %LOCALAPPDATA%\Spid3r\runtime\<hash>\ on first launch. Implies a payload.
--product-name / --version Writes RT_VERSION metadata, displayed in the file's Properties → Details tab.

--allow-gui exists because the AOT runtime registers the standard library natives but not the GUI bridge, so gui_on, gui_eval and friends resolve to null in a native binary. The supported pattern is a launcher: the executable does its startup work, then hands the program off to the installed toolchain's spid3r gui runtime. One native call does all of it — run_payload() finds a runtime (payload first, then %SPID3R_EXE%, the normal install, PATH), extracts the embedded copy when there is one, anchors the working directory to the executable's folder, and starts gui --payload hidden. Writing the handoff by hand is only necessary for custom startup behaviour.

# The whole launcher: one call. It finds a runtime, extracts the
# embedded copy if there is one, anchors the working directory and
# starts `gui --payload` with no console.
fn main() {
return run_payload();
}

Two entry points, and the difference matters for a self-contained build. run_payload() falls back to an installed spid3r when the executable carries no payload at all — which is what a hand-written launcher that expects a global install wants. run_payload_strict() treats a missing payload as a hard error ("payload is missing or truncated; rebuild it"); it is what --bytecode generates, and what a launcher should call when the build is supposed to carry its own runtime, so that deleting the trailer cannot redirect the launch to whatever spid3r.exe is on PATH.

⚠️ Two details that decide whether the window ever appears

run_payload() already does both. They matter when you write the handoff yourself, which is only necessary for custom startup behaviour.

  • Working directory ≠ program folder. Windows starts a process with an inherited directory, so a shortcut, the Run dialog, a scheduled task or Start-Process all begin somewhere else. Relative paths like ui/index.html then miss, and a GUI-subsystem process exits with no visible message because it has no console to print to. Call exe_path() and chdir(dirname(exe_path())) first.
  • The handoff inherits the console. Spawning without map("hidden", true) opens a terminal window for the child. That option passes CREATE_NO_WINDOW on Windows; on other platforms it is ignored.

Shipping a Single File

Two flags turn a build into one self-contained executable: --bundle-runtime appends the running spid3r.exe to the payload, so the target machine needs no Spid3r install, and --bytecode ships the compiled program instead of its source.

# 1. compile the program
spid3r compile app.matrix -o app.matrixc
# 2. one executable: icon, no terminal, bytecode, UI, runtime
spid3r build app.matrix -o App.exe --release --icon app.ico \
--subsystem windows --bytecode app.matrixc \
--embed ui --bundle-runtime
Payload entry What it is
app.matrixc The compiled program. No .matrix is shipped.
ui/index.html, ui/app.js, ui/styles.css The interface, served from memory — nothing is unpacked to disk.
__spid3r_runtime/spid3r.exe The runtime, extracted to %LOCALAPPDATA%\Spid3r\runtime\<hash>\ on first launch and reused afterwards.

--allow-gui is not needed with --bytecode: the launcher is compiled from the three-line run_payload() stub above, which mentions no GUI natives. It is only required when the application itself is compiled into the binary (--embed app.matrix).

⚠️ What --bytecode does and does not buy
  • It removes the source text. With --embed app.matrix the payload carries your source, and the obfuscation is not encryption — anyone can read it back out. With --bytecode the payload carries bytecode, and the launcher carries no application code, symbol names or string literals.
  • It is not secrecy. The VM is open source, so a determined person can write a decompiler for the bytecode. It raises the cost from "open a text file" to "reverse-engineer a bytecode format". Do not put secrets in a client binary.
  • One system dependency remains. The WebView2 runtime (default on Windows 11, on Windows 10 via Edge) — and the matching system webview on macOS/Linux. Everything else is self-contained: the toolchain and every executable spid3r build produces link the C runtime statically and import only system DLLs, so no Visual C++ Redistributable is needed. 10. Object-Oriented Programming (OOP)

Spid3r provides first-class object-oriented programming: classes, single inheritance (extends), constructor and method delegation (super), encapsulation (public / private), and interfaces (implements).

Core OOP Rules & Visibility

  • Constructors: The constructor is declared as public fn new(params) { ... }. Inside the constructor, self is implicitly bound to the newly allocated instance.
  • Explicit Receiver: Instance methods explicitly take self as their first parameter: public fn method(self, arg) { ... }.
  • Default Visibility is Private: Any member without an explicit public keyword is private to the defining class. The checker enforces this whenever the receiver's class is statically known — an annotated binding (let c: C = C()), new C(), or self — and leaves a receiver whose class is only known at run time unchecked, the same gradual rule the rest of the checker follows. Annotate the binding when you need the guarantee: let c = C(); c.secret is accepted, let c: C = C(); c.secret is rejected.
  • Single Inheritance: Classes inherit from a single parent class using class Sub extends Parent.
  • Super Delegation: Subclasses call super(args) in their constructor to initialize the parent fields, and super.method(args) to delegate to the parent method.
  • Abstract Classes & Static Methods: Declared with abstract class Base, abstract classes define method contracts that cannot be instantiated directly. Classes may also declare class-level methods with public static fn name(args) { ... } (called directly on the class as ClassName.name(args) without self).
⚡ Example: Classes, Inheritance & Super Delegation

(Breed: " + self.breed + ")"; } } let pet = new Dog("Rex", "German Shepherd"); println(pet.speak()); println("Initial Energy: " + string(pet.get_energy())); println("After playing: " + string(pet.play(25)));

13. Concurrency, Tasks & Message Channels

Spid3r runs tasks on an M:N scheduler: a pool of OS threads (sized to the machine, growing on demand up to SPID3R_MAX_WORKERS, default 256) pulling from one shared ready queue, with no global interpreter lock — two CPU-bound tasks really do run at the same time. Spawn background tasks, communicate over buffered channels, and synchronize with mutexes.

Tasks, Join, and Async-Await

  • Task Spawning: spawn fn() { ... } spawns a concurrent task and immediately returns a task handle.
  • Joining Tasks: task.join() blocks until the task finishes and returns its result (or throws if the task encountered an unhandled exception).
  • Async / Await: Functions marked async fn name() { ... } can use await task or await channel.
  • Channels: let ch = channel(); creates a buffered message channel — an unbounded FIFO queue. ch.send(val) appends and returns immediately (it never blocks, so a producer cannot deadlock on a full queue), and ch.recv() blocks until a value is available. Values are dynamically typed, like every other Spid3r binding.
  • Mutex: let mu = mutex(initial_value); guards critical sections with mu.lock() and mu.unlock().
⚡ Example: Spawn, Task Joining & Channels
// 1. Spawning a concurrent background task: fn main() { let worker = spawn fn() { let acc = 0; for let i = 1; i <= 100; i += 1 { acc += i; } return acc; }; // Wait for task completion: let result = worker.join(); println("Sum 1..100 from worker task: " + string(result));return 0; }

14b. Runtime Configuration & Remote Management

Spid3r has spid3r.ini, spid3rinfo(), and an encrypted management agent. One installed binary can be inspected, reconfigured, and operated from another machine — without a shell.

The spid3r.ini File

A single INI file configures the runtime. The discovered candidates are tried in this order (first hit wins) — except for the authoritative SPID3R_INI pin described below:

  1. $SPID3R_INI — when set and non-empty, the only ini candidate
  2. spid3r.ini next to the spid3r executable
  3. platform config dir (%APPDATA%\Spid3r, $XDG_CONFIG_HOME/spid3r, ~/.config/spid3r)
  4. ./spid3r.ini

SPID3R_INI is authoritative: when it is set and non-empty it is the only ini candidate. If that path is missing or unreadable the loader uses compiled defaults only (it never falls through to the machine or working-directory ini), records a typed pin failure for local diagnostics, and program-executing commands (run, check, compile, exec, test, bench, debug, gui, repl, magic) refuse to start with exit 1. --version, help, info, config path and config validate remain usable to diagnose the pin, and remote config.set refuses to persist while it is broken — the local control config set / spid3r config init paths are how an operator repairs it. Restart a long-lived process that initialized its policy while the pin was broken; its fail-closed policy remains sticky until restart. spid3r config validate reports a broken pin as a problem (exit 1) and treats an unknown flag as a usage error (exit 2); local diagnostics keep policy values raw so the bad entry is visible. spid3r control config validate exits 1 with errors on stderr when valid:false.

Precedence, highest first: process environment → [env.<name>] (selected by SPID3R_ENV or [spid3r] env) → the INI file → compiled defaults. Every layer is validated with the same rules: a value that fails its type/range check is ignored with a note and the compiled default stays in effect (a bool must be true/false/1/0/on/off/yes/no; a typo like ture is an error, not a silent true). A UTF-8 BOM at the start of the file is tolerated. Unknown keys are reported by spid3r config validate and never abort a run. Live reload: spid3r config reload, SIGHUP on Unix, or the agent's reload operation. The [logging] keys enabled, file and audit are honored (the SPID3R_LOG/SPID3R_LOG_FILE env vars override the INI). Config and state files are written atomically (temp file + rename).

The Management Agent

spid3r agent start listens on [agent] bind:port and speaks spid3r-agent/1 over TCP. There is no unrestricted shell. Every operation is a predefined name checked against the caller's role. The same protocol runs on Windows, Linux and macOS with no certificate store and no third-party crates.

⚡ Example: Pair and Operate Another Host
# On the host that will be managed: $ spid3r agent start $ spid3r agent pair --role operator --name laptop-1 pairing code (operator): 9f2c… # 48 hex chars, single use, short TTL # On the administrator's machine: $ spid3r admin pair 192.168.1.10:9527 9f2c… --name laptop-1 $ spid3r admin --host laptop-1 ping $ spid3r admin --host laptop-1 status $ spid3r admin --host laptop-1 info $ spid3r admin --host laptop-1 config.get --key agent.port $ spid3r admin --host laptop-1 config.set --key agent.name --value web-1 $ spid3r admin --host laptop-1 logs.tail --lines 80 $ spid3r admin --host laptop-1 modules.list $ spid3r admin --host laptop-1 devices.list $ spid3r admin --host laptop-1 ops.run --op-name self_test $ spid3r admin --host laptop-1 reload

Predefined operations (ops.run --name …): ping, reload_config, rotate_log, gc_collect, self_test, dump_diagnostics, restart_runtime. restart_runtime acknowledges the caller first, then exits and spawns the same executable; the new process retries its bind for a few seconds so the handover cannot lose the port. Run the agent under a service manager (Windows service, systemd) in production.

Wire Protocol

Pairing is out-of-band: the host prints a one-time code; the client sends it once. Both sides derive the long-term shared key as SHA-256(code). The shared key never crosses the wire. After pairing, every data frame is:

magic "SPID3R01" | version | kind | device[16] | nonce[12] | len u32 | payload

kind = pair is plaintext JSON (the code is the secret). kind = data is ChaCha20 encrypted and HMAC-SHA256 authenticated (encrypt-then-MAC). Subkeys come from HKDF-SHA256. The frame header is AAD, so a swapped payload fails the tag. Nonces are random 96-bit values; the server keeps a server-wide replay window (device + nonce, entries expire after ~1 hour, capped at 4096 frames) — a captured frame cannot be replayed on a fresh connection or after a restart. A frame whose declared size exceeds agent.max_body (+16 bytes of tag) is rejected straight after the header, before the body is read.

Pair on a network you trust: the code is high-entropy and short-lived, but it is not a PAKE.

One more pairing rule for operators: security.basedir confines only the guarded path-taking natives. A script with Process capability reaches arbitrary paths through spawn_process/exec_capture no matter what basedir says — deny those natives (disable_natives = spawn_process, exec_capture, run_payload, run_payload_strict) or run under --sandbox for a meaningful jail.

15. Virtual Machine Internals, GC & WebAssembly

Spid3r has three execution engines — a tree-walking interpreter, a bytecode VM, and an LLVM ahead-of-time compiler — built on one parser and one semantic checker. This chapter is about what the VM does with your program, how the cycle collector reclaims memory that reference counting cannot, and how the same VM runs inside a browser.

Three Engines, One Front End

Every engine consumes the same parsed and checked program, so anything that type-checks runs on all three. spid3r test is what keeps them honest: it runs every example on the tree interpreter, the VM, and the compiled .matrixc artifact, and fails if the output differs.

Engine Selected by What it does
Tree interpreter spid3r run (default) Walks the AST directly. The reference semantics: every other engine is expected to match it.
Bytecode VM spid3r run --engine vm, spid3r exec app.matrixc, spid3r gui --engine vm Compiles to bytecode, optimizes it, and runs a dispatch loop. This is the engine inside .matrixc artifacts and inside the WebAssembly build.
Native (AOT) spid3r build LLVM compiles to machine code. Two documented trades: the GUI bridge is not linked, and the execution budget is not enforced (a counter in generated code is not free).

What a Compiled Chunk Holds

Each function compiles to a Chunk: a Vec<u8> of encoded instructions, a constant pool, the prototypes of every nested function, and the class descriptors. Two parallel arrays map instruction indices to byte offsets and source spans, which is how a runtime error can point at the exact line that raised. Nested prototypes are shared through Arc, so creating a closure at run time is a refcount bump rather than a copy of the function's code.

The instruction set is 60 opcodes, from Constant and GetLocal up through the object-model and concurrency additions (SuperCtor, SuperMethod, CaptureSync, FieldGetSoft). Opcodes are byte-encoded, and OpCode::from_u8 rejects any value it does not know.

A .matrixc file is that chunk graph serialized. Loading it is defensive by construction: a magic check, a format-version check, a bounds-checked deserializer, and validate_chunk all run before the first instruction executes, so a corrupt or truncated artifact is a clean error and never a misread. The compatibility promise is one-directional: an artifact written by any 1.x build loads on every later 1.x build, while an older build reading a newer artifact must reject it cleanly rather than guess.

Frames, Calls and Unwinding

A CallFrame holds the function being run, its instruction pointer, its local slots, a display name used in stack traces, and — deliberately — its own globals map: name resolution uses the module that defined the function, not the caller's. Method frames carry the qualified Class::method form and constructors Class::new, so a trace reads the same on the VM as on the tree interpreter.

Call depth is capped at 1,000 frames. Exceeding it produces an ordinary runtime error (stack overflow: call depth limit reached) with a source span, not a host crash — a runaway recursive function is a diagnosable mistake rather than a dead process.

try/catch/finally is not host unwinding. Each handler records the catch target, the finally target, the catch slot, and the operand-stack length and frame depth that were live when it was pushed. On a throw the VM restores both to exactly those values before jumping, so a handler sees a clean stack no matter how deep the failure happened.

The Optimizer

After compilation and before serialization, every reachable chunk is optimized: constant folding, peephole rewrites, and dead-code removal. The design rule is that no transformation may change observable behaviour, and the implementation enforces it three ways:

  • Folding uses the interpreter's own helper. Constant a; Constant b; <binop> is evaluated through the same vm_eval_binary the dispatch loop calls, so numeric promotion and string concatenation produce byte-identical results.
  • Failing operations are not folded. 1 / 0 and "a" - 1 stay in the bytecode, so the error still fires at run time with the same message and span.
  • Jumps win over folding. A fold is skipped when any jump or handler target points into the middle of the sequence being folded — a target must keep landing on a real instruction.

The Execution Budget

Embedders that run untrusted code can set a step allowance. It is a shared, saturating counter: the tree engine charges a step per statement and per loop iteration, the VM charges in batches at its instruction poll, and spawned tasks draw from the same allowance as the code that spawned them. When it runs out, the error is fatal — it bypasses try/catch in both engines, so a script cannot swallow the stop and keep running. The native backend does not enforce it at all, which is why embedders running untrusted code use the tree or VM engine.

The budget bounds time; a separate policy bounds authority. An embedding host can deny whole capabilities, and each native the capability covers is replaced by a stub that raises a catchable error instead of reaching the OS:

let engine = Engine::new().deny(Capability::FileSystem);
let engine = Engine::new().deny_all();
# Capability::FileSystem | Process | Network | Environment

Garbage Collection: Cycles

Values are reference-counted. That handles the common case for free: the moment the last reference to an acyclic list drops, its memory is gone, with no collector involved. What reference counting cannot do is reclaim a cycle — two values pointing at each other, or a value that contains itself — because every member of the cycle keeps the next one's count above zero. Those cells would leak until the process exits.

The collector is a mark-sweep that deliberately never enumerates roots. Enumerating every place a live value can hide — interpreter environments, VM frame slots, globals, upvalue cells, task captures — is exactly where a collector gets it wrong, and one missed root means a use-after-free. Instead it computes, for each tracked cell, how many references come from outside the tracked set:

external(cell) = strong_count(cell) - internal_edges_into(cell)
# saturating at zero; internal_edges is counted by tracing every tracked cell

Anything holding a strong reference from outside the tracked set — an environment binding, a Rust local mid-expression, a global, a captured upvalue — shows up as extra strong_count, so that cell has external > 0 and is a root. The collector marks everything reachable from a root, then sweeps what is left: those cells are reachable only from each other, which is the definition of a closed cycle.

⚠️ The safety asymmetry that makes this correct

If tracing misses an edge, internal_edges comes out too small, external too large, and the cell is treated as a root and kept — a leak, never a crash. If tracing ever over-counted an edge, a live cell could compute external = 0 and be swept while still in use. So the rule is absolute: count each strong child exactly once, never count weak references, and leave a container untraced if you are unsure of its children. Being conservative costs memory; being optimistic costs correctness.

Reading strong_count is only sound while nothing else is mutating it, so collection runs only when no other thread is executing Spid3r code. Tasks parked in a blocking wait (recv, join, mutex.lock, sleep) do not count as running — their values sit on their own stacks and are therefore roots. If you call gc_collect() while another thread is running, it fails with a clean message naming how many threads are in the way, rather than collecting under a race.

Detail Behaviour
Automatic collection On by default. Checked at statement boundaries and at the VM's dispatch point, but triggered by allocation count: the first pass runs after 1024 tracked allocations, then at the number of cells that survived the previous pass. SPID3R_GC=0 turns it off.
Manual control gc_collect() runs a collection; gc_live_cells() reports the tracked cell count and doubles as a leak probe.
Coverage 27 GcTrace implementations: every container type, class and function objects, class instances on both engines, and the environment itself. Containers register through the single allocation choke point value::new_ref, so a new one is tracked by construction.
Cost The next threshold is the surviving cell count (never below 1024), and the registry-prune watermark starts at 8192 and doubles. A linear build therefore costs O(log N) collections instead of O(N) at a fixed threshold; a test pins the linear behaviour.
On the native backend gc_collect() reclaims nothing by construction (the AOT runtime uses an arena) and the builtins report engine-internal numbers. That is a documented trade, not a collector failure.
