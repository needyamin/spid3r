Spid3r · Developer documentation

Spid3r

A small, dynamically typed programming language with optional static types, written in Rust. Programs run on a tree-walking reference interpreter or a bytecode compiler + stack VM, and both engines are differentially tested to agree.

two engines: tree-walk & VM self-contained bytecode gradual typing task-based concurrency zero-dependency core 282 tests · 23/23 examples agree
Get started Cheat sheet CLI reference Standard library

Overview

Spid3r uses plain lowercase keywords (fn, let, class, spawn, import) on top of real semantics: dynamic types, closures with upvalues, single-inheritance classes with interfaces, structured error handling, modules with visibility, task-based concurrency, a standard library, and a suite of 20+ built-in data structures. The language core has no third-party dependencies; the webview GUI and the LLVM backend are Cargo features, both on by default.

Two engines, one front endThe lexer, parser, and semantic checker are shared. Run on the tree-walk interpreter or compile to bytecode for the VM.
Self-contained bytecodecompile embeds every imported module, so exec runs a .matrixc with no source on disk.
Differentially testedEvery example runs three ways (tree, VM, compile + exec) and must print identical output.
Gradual typingOptional annotations on variables, parameters, returns, and fields, checked before the program runs.
Task concurrencyspawn / async / await, channels, mutexes, and shared cells on a threaded scheduler.
Batteries includedFormatter, REPL, line debugger, benchmark runner, package manager, a webview GUI backend, and an LLVM AOT compiler for native executables.

Installation

Spid3r builds from source with a recent stable Rust toolchain (edition 2021) and, for the default build, LLVM 18.1+. From the repository root:

cargo build                 # debug binary     -> target/debug/spid3r(.exe)
cargo build --release       # optimized binary -> target/release/spid3r(.exe)
cargo test                  # unit, integration, and differential tests

Linux / macOS installer

On Linux and macOS you can skip the build entirely and use the one-line installer (plain POSIX sh; curl or wget is the only requirement):

curl -fsSL https://raw.githubusercontent.com/needyamin/spid3r/main/install.sh | sh

The script detects your architecture (x86_64 / aarch64), downloads the matching release tarball from GitHub, installs spid3r into ~/.spid3r/bin, and adds that directory to your PATH in ~/.bashrc, ~/.zshrc, and ~/.profile (it never writes a line that is already there). Supported options:

sh install.sh --version 0.1.0   # pin a release instead of latest
sh install.sh --dir ~/.local/bin
sh install.sh --source          # build from source via cargo (no release needed)

--dir and the SPID3R_INSTALL_DIR environment variable override the install location. If no release asset exists for your platform yet, --source builds the toolchain from the Git repository with cargo install --git.

Backends

Both backends, the webview GUI (gui) and the LLVM compiler (native), are default Cargo features:

cargo build --release                                        # core + spid3r gui + spid3r build (needs LLVM 18.1+)
cargo build --release --no-default-features --features gui   # core + GUI, no LLVM needed
cargo build --release --no-default-features                  # zero-dependency core only

Without the feature, spid3r build / spid3r gui exit with a usage error explaining how to enable it. LLVM discovery is described in docs/BUILDING.md and under Environment & exit codes.

Windows installer

On Windows, cargo build --release also writes Spid3r-Setup-<version>.exe to the repository root. build.rs builds a release binary with the same features into target/installer/ and runs NSIS on packaging/nsis/spid3r.nsi, packing the binary with README.md, docs/, examples/, and the calculator demo. With the native backend it also ships LLVM-C.dll, LLVM-C.lib, and the spid3r.lib runtime library that spid3r build links into programs; users need MSVC Build Tools with the Windows SDK to link. NSIS 3.x is taken from packaging/nsis/nsis/nsis-3.10/ or PATH; without it the step is skipped with a warning. Set SPID3R_NO_INSTALLER=1 to skip it.

Quick start

Create hello.matrix:

fn main() {
    println("Hello, Spid3r!");
    return 0;
}

Run it on either engine, or compile it to bytecode and execute that:

spid3r run hello.matrix                 # tree-walk interpreter (default)
spid3r run --engine vm hello.matrix     # bytecode VM, same output
spid3r compile hello.matrix             # writes hello.matrixc
spid3r exec hello.matrixc               # runs the bytecode; no source needed
Hello, Spid3r!

A slightly bigger taste: closures, collections, and error handling.

fn make_counter() {
    let count = 0;
    return fn() {          // the closure captures `count`
        count += 1;
        return count;
    };
}

fn main() {
    let tick = make_counter();
    tick();
    println(tick());                                         // 2

    let xs = list(1, 2, 3, 4, 5);
    println(xs.filter(fn(x) { return x % 2 == 0; }));        // [2, 4]
    println(xs.reduce(0, fn(acc, x) { return acc + x; }));   // 15

    try { println(10 / 0); } catch (e) { println("caught: " + e); }   // caught: division by zero
    return 0;
}
TipUse spid3r repl to try snippets interactively, and spid3r check file.matrix to type- and visibility-check without running.

Program structure

  • A source file has the extension .matrix. It starts with any import statements, followed by declarations (fn, class, interface, let, const) and statements.
  • A program defines fn main(). spid3r run executes the top-level code in order, then calls main; a file without main is rejected with a program run by `spid3r run` needs fn main().
  • If main returns an int, that becomes the process exit code; any other return value exits with 0. An uncaught error exits with 1.
  • A file without main is a library module. It can be imported, and check / compile accept it.
import "math_util";          // imports come first

const GREETING = "hi";       // top-level declarations

fn main() {
    println(GREETING);
    return 0;                // process exit code
}

Syntax basics

  • Comments: // line comment and /* block comment */ (block comments do not nest). A UTF-8 BOM at the start of a file is tolerated.
  • Identifiers are ASCII and case-sensitive: a letter or _, then letters, digits, or _.
  • Variables: let x = 1; declares a mutable binding (the initializer is optional); const LIMIT = 3; declares an immutable one, and assigning to it is a semantic error (cannot assign to const 'LIMIT').
  • Statements end in ;, except block forms (if/elif/else, while, for, try, bare blocks) and fn / class / interface declarations. import "name"; ends in ;.
  • String escapes: \n \t \\ \". Any other escape is a lexer error.
Local functionsNamed fn helper(x) { … } declarations work both at the top level and inside any block without needing a trailing semicolon, and support local recursion. You can also bind anonymous function literals with let f = fn(x) { … };.

Reserved keywords

Keywords are lowercase and case-sensitive:

fn let const if elif else while for in break continue return
true false null and or not import try catch finally throw
class interface new self public private spawn async await extends implements

Type and constructor names (list, map, heap, …) and builtin functions are not keywords. They are ordinary globals and can be shadowed. See docs/KEYWORDS.md.

Values & types

Primitives: int (64-bit signed), float (64-bit IEEE), bool, string (immutable UTF-8), and null. Everything else is a built-in object: collections, option/result, class instances, functions, tasks, channels, and so on. type_of(x) returns a value's type name and string(x) converts it to text.

Truthiness

Used by if, while, and/or/not, and bool():

Numeric semantics
  • int + float promotes to float; int / int truncates toward zero (7 / 2 is 3, -7 / 2 is -3).
  • Integer arithmetic wraps on overflow (i64): 9223372036854775807 + 1 is -9223372036854775808.
  • Division or modulo by zero throws division by zero.
  • 1 == 1.0 is true. An integer literal outside the i64 range is a lexer error.

Precedence, tightest first: postfix (call, index, field, method) → unary not / - / await / spawn → * / % → + - → comparisons → and → or → assignment. Comparison chains are left-associative (a < b < c parses as (a < b) < c), so write a < b and b < c instead.

fn main() {
    println(10 + 0.5);        // 10.5   int + float -> float
    println(7 / 2);           // 3      int / int truncates
    println(7.0 / 2);         // 3.5    a float operand -> float
    println(7 % 3);           // 1
    println(2 * (3 + 4));     // 14
    println(true and false);  // false
    println(not true);        // false
    println(1 < 2 or 9 < 3);  // true
    let a = 5;
    a += 3;
    println(a);               // 8
    return 0;
}

Control flow

if / elif / else, while, two forms of for (collection iteration and a C-style header), plus break and continue in every loop form. else always binds to the nearest unfinished if.

fn main() {
    for x in [1, 2, 3] { println(x); }                 // 1 2 3
    for let k = 0; k < 3; k = k + 1 { println(k); }    // 0 1 2

    let i = 0;
    while i < 2 { println(i); i += 1; }                // 0 1

    let n = 2;
    if n == 2 { println("two"); }
    elif n == 1 { println("one"); }
    else { println("other"); }                         // two
    return 0;
}

Functions & closures

Functions are first-class values. Anonymous fn(x) { … } literals nest and capture their surrounding bindings, and recursion is supported. async fn marks a function that may await; using await elsewhere is a semantic error.

fn make_adder(base) {
    return fn(x) { return x + base; };   // captures `base`
}

fn fact(n) {
    if n <= 1 { return 1; }
    return n * fact(n - 1);
}

fn main() {
    let add100 = make_adder(100);
    println(add100(5));   // 105
    println(fact(5));     // 120
    let g = fact;         // functions are values
    println(g(4));        // 24
    return 0;
}

Capture rules

These rules are identical on both engines and pinned by regression tests:

  • Closures capture bindings, not values. A write through one closure is visible to every other closure over the same binding.
  • for x in … creates a fresh binding per iteration. Closures made in iteration N see that iteration's value.
  • while and C-style for share one binding. Closures created there observe the variable's final value; bind a fresh let inside the body if you need a snapshot.
  • Every activation is isolated. Recursive functions and factories such as make_adder never leak state between calls.
fn main() {
    let fs = list();
    for x in [0, 1, 2] { fs.push(fn() { return x; }); }
    println(fs.map(fn(f) { return f(); }));    // [0, 1, 2]

    let gs = list();
    let i = 0;
    while i < 3 { gs.push(fn() { return i; }); i += 1; }
    println(gs.map(fn(f) { return f(); }));    // [3, 3, 3]
    return 0;
}

Classes & interfaces

  • Single inheritance with extends; methods resolve through the parent chain, so overrides dispatch polymorphically.
  • Visibility: members are private by default; mark them public to expose them. The semantic checker rejects out-of-class access to private members (field 'x' of class 'A' is private).
  • Receiver: self is an explicit parameter of every method.
  • Constructor: the method named new, invoked as new Class(…). The shorthand member new(params) { … } is also accepted.
class Animal {
    public let name;
    private let noise;
    fn new(name, noise) { self.name = name; self.noise = noise; }
    public fn speak(self) -> string { return self.name + " says " + self.noise; }
}

class Dog extends Animal {
    fn new(name) { self.name = name; self.noise = "woof"; }
    public fn fetch(self) -> string { return self.name + " fetches"; }
}

fn main() {
    let d = new Dog("Rex");
    println(d.speak());    // Rex says woof   (inherited from Animal)
    println(d.fetch());    // Rex fetches
    // println(d.noise);   // semantic error: private member
    return 0;
}

Interfaces declare method signatures (each ending in ;), and classes opt in with implements A, B. Dispatch is by method name, so a variable may hold any implementation.

interface Named {
    fn name(self) -> string;
}

class Team implements Named {
    public let label;
    fn new(label) { self.label = label; }
    public fn name(self) -> string { return "team-" + self.label; }
}

fn main() {
    println(new Team("core").name());   // team-core
    return 0;
}

Printing an instance shows its class and field map, e.g. Dog {name: Rex, noise: woof}. Field order in that output is not guaranteed.

Error handling

Errors are values. throw raises any value, and try / catch (e) / finally handles it. At least one of catch or finally is required. An uncaught error prints its message, source position, and a call-stack trace, then exits with code 1:

error[runtime]: uncaught throw (thrown: bad)
  --> app.matrix:1:13
  stack trace (most recent call first):
    at boom (app.matrix:1:13)
    at main (app.matrix:3:5)

Option and result

Two sum types model expected failure without throwing:

TypeConstructorsMethods
optionsome(v), noneis_some, is_none, unwrap (throws on none), unwrap_or(d)
resultok(v), err(e)is_ok, is_err, unwrap (throws on err), unwrap_or(d), unwrap_err
fn parse_age(s) {
    let n = int(s);
    if n < 0 { return err("age cannot be negative"); }
    return ok(n);
}

fn main() {
    try { println(10 / 0); }
    catch (e) { println("caught: " + e); }       // caught: division by zero
    finally { println("done"); }                 // done

    let r = parse_age("42");
    if r.is_ok() { println("ok: " + string(r.unwrap())); }   // ok: 42
    println(parse_age("-1").unwrap_err());       // age cannot be negative
    println(parse_age("-1").unwrap_or(0));       // 0

    let none_val = none;
    try { none_val.unwrap(); }
    catch (e) { println("caught: " + e); }       // caught: unwrap on none
    return 0;
}
ConventionFile and process builtins (read_file, write_file, spawn_process) return result values instead of throwing, so branch with is_ok/is_err. Argument and type errors (e.g. write_file(1, "x")) still throw.
Engine parity: finally always runsOn both the tree-walk interpreter and the bytecode VM, finally blocks execute deterministically on normal completion, on thrown errors, and on early exits (return, break, and continue) out of a try or catch block.

Strings

Strings are immutable UTF-8. Lengths and indexes count characters, not bytes. Indexing s[i] returns a one-character string. + concatenates two strings only; convert other values with string(x) or use format ("a" + 1 throws cannot add string and int).

    println("a={} b={}".format(1, "two"));        // a=1 b=two
    println("{{literal}} {}".format(5));          // {literal} 5
    println("  pad  ".trim().pad_left(8, "."));   // .....pad

    println("héllo"[1]);                          // é
    println("hello".slice(1, 3));                 // el
    println("abc".reverse());                     // cba
    return 0;
}

Data structures

Every container is created by calling a global constructor. Most share a common verb set: len, is_empty, clear, contains, and clone. Misuse, such as pop on an empty stack, an out-of-range index, a missing map key, or a duplicate bst key, throws a descriptive, catchable error. Full details are in docs/DATA_STRUCTURES.md.

Higher-order list methods

Lists (and vecs) accept Spid3r functions as callbacks. The list is snapshotted first, so a callback that mutates the list cannot corrupt the iteration.

MethodMeaningOn an empty list
xs.map(f)new list of f(x)empty list
xs.filter(f)new list of each x where f(x) is truthyempty list
xs.reduce(init, f)left fold with f(acc, x)init
xs.for_each(f)call f(x) for side effectsno-op
xs.all(f) / xs.any(f)every / some result truthytrue / false
fn main() {
    let xs = list(10, 20, 30);
    xs.push(40);
    xs.remove_at(1);
    println(xs);                                            // [10, 30, 40]
    println(xs.map(fn(x) { return x * 2; }));               // [20, 60, 80]
    println(xs.reduce(0, fn(acc, x) { return acc + x; }));  // 80

    let m = map("a", 1, "b", 2);
    m["c"] = 3;
    println(m.items());                                     // [(a, 1), (b, 2), (c, 3)]

    let pq = priority_queue();
    pq.push("low", 5);
    pq.push("urgent", 0);
    println(pq.pop());                                      // urgent

    let g = graph("undirected");
    g.add_node("a"); g.add_node("b"); g.add_node("c");
    g.add_edge("a", "b");
    g.add_edge("b", "c", 2.5);
    println(g.find_path("a", "c").unwrap());                // [a, b, c]

    let mx = matrix(2, 2, 1.0);
    mx.set(0, 1, 5);
    println(mx.row(0));                                     // [1.0, 5.0]
    return 0;
}

Modules

import "name"; loads name.matrix. Only members marked public are exported, and the semantic checker enforces privacy. Imports must appear before any other declaration (import must appear before other declarations).

// math_util.matrix: a library module (no fn main)
public fn square(x) { return x * x; }
public const LIMIT = 3;
fn secret() { return 42; }      // private: not exported

// modules.matrix: the program
import "math_util";

fn main() {
    println(square(5));   // 25
    println(LIMIT);       // 3  (still const: assigning to it is a semantic error)
    return 0;             // calling secret() here fails: unknown name 'secret'
}

Resolution order

  1. The directory of the importing file.
  2. Each directory listed in SPID3R_PATH.
  3. ./stdlib (relative to the working directory).
  4. The nearest vendor/ directory at or above the working directory (populated by spid3r install).
  • One instance per file. Modules are keyed by their canonical path, so "lib/util" and "./lib/util" share one instance and its top-level code runs exactly once.
  • Cycles are detected with a diagnostic that prints the full chain, e.g. circular import of 'a' (chain: a.matrix -> b.matrix -> a). They never hang.
  • A missing module is a semantic error with a source position.
Self-contained bytecodespid3r compile resolves, checks, and embeds every imported module (transitively) into the .matrixc file, keyed by resolved path. spid3r exec therefore needs no .matrix sources on disk.

Concurrency

spawn fn() { … }; runs a function literal as a task on a threaded scheduler and returns a task. await joins a task or receives one message from a channel, and is only legal inside an async fn.

Tasks

MemberBehavior
await t (in async fn)Join the task and return its value; a failed task re-raises its error to the awaiter.
t.join()Block until finished and return the value (or re-raise the error). Repeatable: joining twice returns the same value.
t.status()"running", "done", or "failed". Never blocks.
t.is_done()Non-blocking completion check.

A task that throws does not crash the program. The error is stored, status() becomes "failed", and the error is re-raised on join/await, so the joining side can try/catch it.

mutex(v)lock() blocks until the mutex is free, then returns the inner value (collections are aliased, so mutations stick). Release it explicitly with unlock().
ref(v)A shared mutable cell: get(), set(v).
async fn settle(t) { return await t; }

fn main() {
    let ch = channel();
    spawn fn() { ch.send(1); ch.send(2); };
    println(ch.recv());                   // 1
    println(ch.recv());                   // 2

    let t = spawn fn() { return 7; };
    println(settle(t));                   // 7

    let bad = spawn fn() { throw "task-error"; };
    sleep_ms(30);
    println(bad.status());                // failed
    try { bad.join(); } catch (e) { println("caught " + e); }   // caught task-error

    let shared = mutex(list());
    let items = shared.lock();
    items.push(1);
    shared.unlock();
    return 0;
}

Related builtins: task_count(), sleep_ms(n), yield(), and spawn_process(cmd, args) (synchronous; see the standard library).

Gradual typing

Annotations are optional everywhere, and unannotated code stays fully dynamic. When present, they are checked by spid3r check and before every run.

fn add(a: int, b: int) -> int {
    return a + b;
}

let count: int = 0;
let name: string = "spid3r";

class Point {
    public let x: float;
    public let y: float;
    fn new(x: float, y: float) { self.x = x; self.y = y; }
}

fn main() {
    let p = new Point(1, 2.5);      // int widens to float
    let anything: any = "text";     // any opts out
    anything = 3;
    println(add(count, 2));         // 2
    return 0;
}
  • Checked positions: let/const bindings, parameters, return types, and class fields.
  • int widens to float; any opts a binding out of checking.
  • Mismatched assignments, call arguments, returns, and field writes are rejected before any code runs, with positions:
error[semantic]: argument 2 of 'add' expects int, got string
  --> app.matrix:3:20

Memory model & GC

Values are reference-counted with Arc/Mutex. Both engines share this representation, which is what lets values cross spawn boundaries. Acyclic garbage is freed as soon as the last reference drops.

Full-container cycle collectionA reference cycle (a list containing itself, an object pointing at itself, a graph or tree storing a parent container, or two maps referencing each other) never reaches a zero refcount on its own. Spid3r's trial-deletion cycle collector automatically tracks and reclaims cycles across all 20+ built-in containers and class instances (list, vec, stack, queue, deque, linked_list, set, map, hash_table, bag, ring_buffer, binary_tree, bst, heap, priority_queue, graph, trie, matrix, ref, option/result wrappers, and class instances). It runs automatically at statement boundaries (on by default; set SPID3R_GC=0 to disable). gc_collect() forces a pass, gc_live_cells() inspects the tracked heap, and weak(v) / deref(w) provide explicit non-owning references when desired. Design notes: docs/GC.md.
fn main() {
    let before = gc_live_cells();
    {
        let l = list(1, 2, 3);
        l.push(l);                           // a cycle
    }
    gc_collect();
    println(gc_live_cells() <= before);     // true: the cycle was reclaimed
    return 0;
}

Projects & dependencies

spid3r init myproj creates a project; spid3r run with no file then runs its entry.

# spider.toml
[package]
name = "myproj"
version = "0.1.0"
entry = "src/main.matrix"      # what `run` (no file) and `dist` use

[dependencies]
mathlib = { path = "../mathlib" }                            # path dependency
extras  = { git = "https://example/extras", rev = "main" }   # git dependency
serde   = { version = "^1.0" }                               # local registry ($SPID3R_REGISTRY)
  • Install: spid3r install vendors each dependency's sources into vendor/<name>/ and writes a deterministic spider.lock. Git dependencies are pinned to the resolved commit, and every vendored tree has a SHA-256 hash. Re-running is idempotent; a tampered or stale vendor/ tree is re-synced.
  • Version constraints: ^1.0 (same major), >=1.2, =1.2.3, or an exact version, checked against the dependency's own manifest.
  • Local registry: { version = "…" } resolves from $SPID3R_REGISTRY, an offline directory of <name>/<version>/ packages. A package may ship dist/sha256.txt; install verifies the vendored tree against it, and spid3r pack prints the matching line.
  • Workspaces: [workspace] members = […] share one vendor/ and lockfile, with name-conflict detection.
  • Distribution: dist builds a self-contained target/<package>.matrixc; pack/unpack move source projects as deterministic POSIX ustar tarballs (supporting long paths via the 155-byte ustar prefix and GNU @LongLink headers, with header checksum verification).
  • Tests: inside a project, spid3r test differentially runs tests/*.matrix per member. Use assert/assert_eq so failures explain themselves.

There is no remote/HTTP registry, and registry packages' own dependencies are not resolved transitively, so declare everything you use. See docs/REGISTRY.md.

Architecture

Both engines share one front end and one value layer, which is what keeps them behaviorally identical.

.matrix source→ lexer→ parser → AST→ semantic checker→ tree-walk interpreter  or  compiler → optimizer → bytecode VM
ModuleResponsibility
src/lexer · src/parser · src/astTokens, Pratt parser, syntax tree (grammar in docs/GRAMMAR.md)
src/semanticNames, arity, visibility, main rule, gradual types
src/interpreter · src/environmentTree-walk reference engine
src/vmBytecode compiler, optimizer, serializer, stack VM, debugger
src/valueValue representation, collections, cycle collector
src/sched · src/stdlib · src/modulesTask scheduler and channels, builtins, import resolution
src/pkg · src/fmt.rs · src/repl · src/cli.rsPackage manager, formatter, REPL, command line
src/native · src/guiLLVM AOT backend (native feature) and webview GUI (gui feature, default)
  • value::collections implements every value operation (construction, method dispatch, indexing, iteration, equality, display) once, and both engines call it.
  • The compiler emits a clox-style Chunk. The VM is a register-free stack machine in which each call frame's slots serve as both operand stack and locals.

Bytecode VM & .matrixc

The compiler lowers the checked AST into a compact Chunk: code bytes plus constant, function, and class pools, with per-instruction spans for error messages. Closures carry heap upvalue cells: captured locals route reads and writes through a shared cell created fresh per activation, loop iterations re-capture per-iteration bindings, and scope exits release the routing. Together these keep closures correct across recursion, loops, and spawned tasks.

File format

compile writes a serialized script function (little-endian) that starts with a magic header, so foreign or corrupt files are rejected with a clean diagnostic:

.matrixc       ::= b"SPID3R"  version:u16  VmFunc        # current version: 1

VmFunc         ::= name:str?  arity:u64  is_async:u8
                   upvalue_slots:u8[]  own_upvalues:u8  Chunk
Chunk          ::= code:bytes
                   constants:value[]          # scalars only: 0=int 1=float 2=string
                   functions:VmFuncProto[]
                   classes:VmClassProto[]
                   inst_offsets:u64[]   inst_spans:Span[]
                   modules:embedded[]         # imports, keyed by resolved path
EmbeddedModule ::= key:str  public:str[]  VmFunc
SafetyBefore a chunk runs, it is validated. Opcodes are decoded through a safe lookup (no mem::transmute), and the validator rejects invalid opcodes, truncated instructions, out-of-range constant/function/class references, and jump targets that miss an instruction boundary. Pool reads and jumps are also bounds-checked at run time, so bad bytecode becomes a runtime error, never a panic.

Optimizer

On by default (--no-opt disables it):

  • Constant folding reuses the interpreter's own arithmetic, so folded results and errors match exactly (1/0 is never folded).
  • Peephole cleanup: Jump +0, push-then-pop.
  • Static branch folding and dead-code elimination (skipped inside try chunks).

Full reference: docs/BYTECODE.md.

Testing & QA

Because correctness means the engines agree, Spid3r is verified differentially. As of this revision, cargo test passes 282 tests (272 with --no-default-features plus 10 GUI tests) and spid3r test reports 23 ok, 0 failed.

  • spid3r test classifies each examples/*.matrix by its parsed AST (a file with fn main is a program, anything else is a library). Programs run on the tree interpreter, the VM, and compile + exec, and all three stdout streams must match. Libraries are semantic-checked.
  • cargo test runs unit tests per subsystem, integration tests, the differential harness (tests/difftest.rs), property/mutation fuzz suites (tests/fuzz_tests.rs), and dedicated engine-parity regressions (tests/audit_regressions.rs). The regressions cover closure capture, per-iteration loop bindings, scope-exit slot release, nested upvalue descriptors, local named fn declarations, finally on return/break/continue, cycle-safe container display/equality/cloning, full-container cycle collection, self-argument collection operations, map index assignment, file-op results, the task API, JSON round-trips, ustar long-path archiving, and RNG bounds.
  • tools/difftest.sh is a standalone shell version of the three-way comparison.
  • Bytecode safety & fuzzing are tested automatically: invalid opcodes, truncation, huge count headers, out-of-range pool references, negative jumps, and off-boundary jumps are all rejected cleanly, backed by deterministic mutation tests (tests/fuzz_tests.rs) and cargo-fuzz targets (fuzz/).
  • GUI is tested headlessly: IPC decoding, JSON escaping and round-trips, event ordering, unknown-event dropping, payload fidelity, and queued JS (bridge unit tests plus the spid3r gui --dry-run replay). The native window itself is exercised manually.
  • 2026-10 audit & CI. A full-repository audit probed edge semantics across all engines and hardened the lexer, parser, semantic checker, bytecode format, VM closure/finally semantics, collections, cycle GC, and packaging security, enforced in cross-platform GitHub Actions CI (.github/workflows/ci.yml). Limitations & roadmap

Known limitations

  • Lexer: float literals use decimal syntax (1.5, not scientific notation 1.5e3), and -9223372036854775808 cannot be written as a positive integer literal before unary negation.
  • Native backend: a class declared inside a function is rejected, and higher-order collection methods (list.map(f) etc.) require --engine vm or --engine tree.
  • Dependencies: local only (path, git, or offline registry); no transitive resolution of registry packages.
  • Documented design choices: integer overflow wraps silently, int / int truncates, err(…) is truthy, comparison chains are left-associative, and assignments are legal in if/while conditions.
