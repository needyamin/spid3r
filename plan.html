1Executive Summary

An independent, five-track audit (front end · execution engines · runtime & security · build/test validation · market analysis) combined code reading with executed probes, then fixed what was safe to fix. Nothing in this report is asserted without evidence.

✅ What is strong VERIFIED

  • Validation claims are true. Every quantitative claim in the docs was re-measured and holds exactly: 300 core tests (now 310 total), 10/10 GUI, 23/23 three-engine differential, clippy -D warnings clean, both feature builds compile and link LLVM.
  • Engine parity is real and enforced by a shared value layer plus a differential harness — all executed parity probes produced identical output on tree, VM, and compiled bytecode.
  • Security hardening holds. Package-name allowlist, tar unpack containment, git-argument guards, string/allocation caps, and the bytecode validator all behaved correctly under 4 hand-crafted mutations and 15+ edge probes. No host panic was produced by any probe.
  • Rare engineering rigor for a v1.0 language: dual differential-tested engines, optimizer-vs-no-optimizer checks, deterministic fuzz suites, and honest known-limitation docs.

⚠️ What needs work VERIFIED

  • Two new P1 VM-compiler bugs were found and fixed in this round: list literals >255 elements corrupted the VM value stack silently, and a 129th captured variable silently aliased the first capture's cell. Both produced wrong behavior with no error; compile even wrote the broken bytecode to disk with exit 0. Both now fail with clean diagnostics, pinned by regression tests.
  • The remaining P1 is now fixed too: four plain-Spid3r constructs (e.g. a list containing itself, iterated with for) used to hang both engines forever with no diagnostic — deterministic, user-reachable deadlocks. Fixed in the fix round via snapshot-under-lock in the shared value layer (5 deadline-guarded regression tests).
  • Enforcement gaps (P2) — all fixed in the fix round: gradual typing was bypassable through rebound function values; privacy was not enforced on computed receivers (new C().hide()) or field writes; REPL :reset kept const sets.
  • Market reality (P2): no ecosystem, no LSP, no TLS/regex/date-time. The realistic niche is education/teaching + an embedding layer for Rust applications — not general scripting. See §8.
Bottom line: Spid3r v1.0 is in unusually good shape for its stage — the documentation's claims survived a hostile re-measurement, every audit finding was fixed and pinned by regression tests, and the embedding API (R7) shipped with tests and docs. The next highest-impact step is the LSP foundation (R8), then the stdlib gap fills (R9: regex, date-time, TLS decision). RECOMMENDATION

Detail — P1 findings

F1 · List literal >255 elements corrupted the VM stack P1 FIXED

Evidence MEASURED — pre-fix probes (audit_notes\probes\list256/list300.matrix): tree prints 256/300; VM fails with misleading error[vm]: int has no length (argc byte wrapped to 0 / 44). compile exited 0 and wrote the broken .matrixc. Root cause: src\vm\compiler.rs Expr::List emitted items.len() as u8 into Construct with no check_argc (Call/Method/New all had the guard; the list literal was the only unguarded emission).

Impact — silent wrong behavior or stack corruption from an innocent literal; broken artifacts shipped to disk. A 256-element data table in source code is realistic.

Fix applied — clean compile-time diagnostic too many elements in list literal (max 255, got N); compile now exits 1 and writes nothing. Regression test vm_rejects_more_than_255_element_list_literals (tree still runs 300 → documents the engine-encoding limit; same precedent as the existing 255-locals limit).

Post-fix — VM: error[vm]: too many elements in list literal (max 255, got 300); tree unchanged; 3-engine differential still 23/23. MEASURED

F2 · ≥129 captured variables silently aliased cells P1 FIXED

Evidence MEASURED — pre-fix probes (cap128/129/130.matrix): 128 captures agree (9256 both engines); 129 captures: tree 9385 vs VM 10257; 130: tree 9515 vs VM 10259 — exactly the predicted & 0x7f aliasing arithmetic (capture #129 read capture #1's cell). Root cause: capture_local (compiler.rs:1205) let own_upvalues exceed the 7-bit upvalue descriptor encoding; resolve_upvalue masked with & 0x7f (:1232).

Impact — silently wrong program results; heavy data-closure builders (large generated closures) would be corrupted without any error.

Fix applied — 128-capture limit enforced at both function-finalization sites (compile_function, compile_one): too many captured variables in one function (max 128, got N). Regression test vm_rejects_more_than_128_captured_variables pins both the rejection and the clean 128-capture boundary on both engines.

Post-fix — cap130 VM: clean diagnostic; cap128: 9256 on both engines; full suite 300/300 green; clippy clean. MEASURED

F3 · Self-referential containers hang both engines, no diagnostic P1 FIXED

Evidence MEASURED — four probes hang on both engines and must be killed externally (audit_notes\probes\): p01 for-in over a self-containing list; p03 set.union with itself; p05 map.values() where the map contains itself; p06 linked_list.to_list() of a self-referencing list. Root cause pattern: the operation holds the container's mutex while recursing into values that re-lock the same (or a partner) mutex — the exact hazard sitemap §5.3 warns about; json_write and deep_clone were fixed for this in earlier audits (p02 proves .clone() is cycle-safe), but these four paths were not covered.

Impact — plain, innocent-looking user code wedges the runtime deterministically with no error and no timeout. Worst open finding.

Recommended fix — apply the established clone-out-under-lock pattern (snapshot under lock, recurse without) or add reentrancy/cycle detection per container operation, in the shared value::collections layer so both engines are fixed at once. Complexity: Medium. Risk: hot-path overhead — benchmark after (bench --compare).

Acceptance — all four probes exit <1 s with clean catchable errors on both engines; new regression tests; full suite + differential stay green; map bench within noise of pre-change numbers.

Result FIXED — snapshot-under-lock in the shared value layer; all four probes exit cleanly on both engines; 5/5 deadline-guarded regression tests; differential and full suite green. See the fix-round table below.

Detail — P2 findings

F4 · Deep-nesting build stall (GC interaction suspected) P2 FIXED

Evidence MEASURED — p07/p07b: building a ~4-million-deep nested list stalls both engines >150 s during the build loop alone (never reaches the clone/print phase). The behavior (hang-class symptom, allocation-bound related) is verified; the root cause is not.

Hypothesis — statement-boundary auto-GC performs a full-graph rescan per collection window; on a linear chain of N nodes that is O(N²) total. Consistent with the documented "auto-GC gated on live_tasks()==0" design but unproven.

Recommended fix — measure first (GC-off via SPID3R_GC=0 vs on, at 100k/400k/1M depths), then either incrementelize the trigger or add a chain-depth-aware bound. Complexity: Medium-High. Acceptance: 4M build completes (or fails cleanly) in <10 s; measurement table recorded in docs.

Result FIXED — measurement confirmed TWO quadratic cost centers (auto-GC rescans AND the track() registry prune, the latter GC-independent); both amortized in gc.rs. Fixing them exposed a second defect: teardown of a deep chain overflowed the host stack — solved with iterative Drop for list/vec/map/set. After: 100k 0.6 s, 400k 2.4 s, 1M 6.5 s, 4M 27.3 s (debug build, all exit 0).

F5 · Gradual typing bypassable P2 FIXED

Evidence VERIFIED — fn f(x: int) then let g = f; g("hello") runs and prints 42 on both engines (probe p02); a nested fn h(a: int) is likewise unchecked (p03b). src\semantic\ty.rs:1-9 states the checker is compile-time only.

Impact — docs present annotations as enforced; indirect calls silently bypass them. Erodes trust in the "gradual typing" feature.

Recommended fix — make a decision, either: (a) runtime arg/return type checks in the shared call layer (parity-tested, small perf cost, honest gradual typing), or (b) document precisely which annotation paths are enforced. Complexity: Medium (a) / Low (b). Acceptance: an enforced/bypass matrix in the docs + tests pinning every row.

F6 · Privacy unenforced on computed receivers P2 FIXED

Evidence VERIFIED — new C().hide() on a private method runs and prints 1 on both engines; new C().secret silently prints null (probes p05/p05b). The semantic checker validates privacy only when the receiver is a bare Ident (semantic\mod.rs Method/Field arms).

Impact — the module privacy guarantee has a hole exactly where encapsulation matters (method chains, constructor results).

Recommended fix — enforce on the receiver's resolved type rather than its syntactic form, in the shared semantic pass. Complexity: Medium. Acceptance: both probes rejected with a clean diagnostic on both engines + regression tests.

F7 · REPL :reset keeps const sets P2 FIXED

Evidence VERIFIED — const c=1; → :reset → let c=2; → c=3; → error[runtime]: cannot assign to const 'c' (repl\mod.rs:46-50 clears only the name list).

Fix — rebuild the environment and its const sets on :reset. Complexity: Low. Acceptance: the sequence above works; repl tests extended.

F8 · VM Import drops const-ness P2 FIXED

Evidence VERIFIED — vm\mod.rs:1492-1493 inserts exported bindings with g.insert(n, v) discarding _is_const, while the tree uses define_const (interpreter\mod.rs:335-340). The semantic pass masks the difference for normal source; it is observable only through a crafted .matrixc executed via exec (re-assigning an imported const: tree rejects, VM accepts).

Impact — an engine-parity hole reachable only from hostile bytecode; matters for the "validator + parity" security story.

Fix — route imported bindings through the VM's const mechanism. Complexity: Low-Medium. Acceptance: hand-built chunk test — re-assigning an imported const errors on VM exactly like on tree.

Assessment

Both fixed bugs were VM-compiler encoding bugs — the tree engine (reference) was always correct, and the divergences were invisible to the differential harness because the corpus (examples + 310 tests) contains no >255-element literal or ≥129-capture function. That is the parity lesson of this round:

Structural gap: parity is only as good as the corpus. The two P1s lived exactly where no test looked — single-byte encoding limits in emission code. Recommended countermeasure: add limit-boundary probes (255/256/300 elements; 128/129/130 captures — now in tests\audit_regressions.rs) and keep a generated "stress corpus" in the differential harness, not just hand-written examples.

Engine-specific limits with clean diagnostics have precedent in this codebase (255 locals, 255 call args, native backend's class-in-fn rejection). The two new limits follow the same contract and are documented in sitemap §12.

Where Spid3r is behind — do not fight RECOMMENDATION

  • Ecosystem: decades behind; unfixable by code — only by years of users. Do not attempt general-purpose adoption.
  • Performance at scale: no specializing JIT; "1.3× over CPython on cherry-picked micro-workloads" is same-class evidence, not LuaJIT class.
  • Real-world scripting walls: no regex, no date-time, no TLS — hit within the first hour of any serious script.
  • Editor experience: no LSP is table-stakes disqualifier for dynamic-language adoption.

Genuine advantages — lean in VERIFIED capabilities

  • Zero-dependency pure-Rust core → one auditable static binary, trivial supply chain; embeds into Rust apps far more naturally than C-based Lua or CPython. In-Rust rivals (Rhai, Rune) are expression-oriented and lack classes/modules/tasks — Spid3r's surface is broader.
  • Dual differential-tested engines + optimizer + fuzzing — rare rigor; a living "Crafting Interpreters".
  • 20+ built-in collections incl. trees/graphs with cycle-safe GC → teach data structures with zero setup.
  • Built-in tasks/channels/mutexes, WASM playground, single-binary distribution, unusually careful Windows installer.
