0 · Method & Team — test, analyze, then plan

The plan was produced in three stages, in this exact order:

  1. Test — five verification engineers re-checked the audit's claims against the actual source (Part A verdict tables in §1), and ran the built-in bench on the current tree to confirm the starting point is green.
  2. Analyze — the same engineers feasibility-checked every planned change against the real code and API surface: inkwell 0.11 registry source (attributes, metadata, target-cpu, PassBuilderOptions), native-tls 0.2.18, the hand-extern precedents (net.rs sys module, shutdown.rs signal, db.rs kernel32), the exhaustive-match cost of new Value variants, the scheduler's GC-quiescence contract, and the phase0 bench wiring (Part B in §1).
  3. Plan — only then were steps written. Where analysis contradicted the audit, the plan follows the analysis; every such change is logged in Appendix D.

2.5 · Agent Execution Contract — strict role set for any AI agent

ROLE. You are the executing engineer for this plan. You implement one step at a time, in dependency order, on the real repository. You are the operator of this plan, not its designer: you do not redesign, reorder, or reinterpret steps. When reality contradicts the plan (S0 analysis), you stop, record the finding, and amend this document first — exactly how Appendix D came to exist. You never "improve" scope silently.
HARD RULES — a violation makes the step INVALID and must be reverted.
  1. No fake implementations. No stubs, no placeholders, no "temporary" shortcuts that pretend to work, no mocked-out gates. A step that cannot be completed is left OPEN in the ledger with the exact reason — that is a valid outcome; a pretended completion is not.
  2. No fake results. Never claim a gate passed that did not run. Never quote a number that was not produced by the named command on this tree, this commit. Never edit historical benchmark artifacts or ledger rows — the ledger is append-only; corrections are new rows.
  3. Tick discipline. A checkbox (sb-<step>) is set only when (a) the step's GATE commands ran and passed on the real repo, (b) the ledger row is appended, and (c) the checked attribute is added — all in the same commit. Leaving a box unticked is always acceptable. A falsely ticked box never is.
  4. No performance claims without measurement. Never write or say "X is now as fast as Rust/Node" without a phase0 measurement under the pinned protocol (Appendix A) proving it, on the commit that claims it. Comparisons are same-host, same-protocol; absolute ms are ADVISORY_ONLY; ratios are the portable truth. Tier-B targets bind only after their first measurement; unreachable targets are retired openly (docs/PERF_TARGET_RETIREMENT.md style) — never quietly dropped, never quietly declared met.
  5. Scope lock. Touch only the files listed for the step (Appendix B). No drive-by refactors, no dependency additions, no feature creep, no "while I'm here". If an unrelated bug blocks you: record it in the ledger, route around it, and ask the owner before fixing anything outside the step.
  6. Contract lock. After every code step: tools/gate.sh 9/9, tools/difftest.sh ALL MATCH, cargo fmt --check, cargo clippy --all-targets --features native, plus the step's specific gates. Any red = the step is not done, no matter how small the diff.
  7. Decision lock. Steps marked owner/DP (R0.4; R2.3 needs DP-2; R10.x needs DP-1; runtime-loading FFI needs DP-5) are executed only after the owner's recorded confirmation in the ledger. You may prepare their analysis; you may not implement them.
  8. Safety lock (SEC-A…D). No new unsafe outside src/native/rt.rs; every new extern declaration follows the hand-FFI precedents (net.rs sys, shutdown.rs signal, db.rs kernel32) with a written safety comment; compiler operations perform no network access; exit codes stay 0/1/2/4 per README.md; every artifact keeps its SHA-256 integrity story.
  9. Truth lock. Report failures verbatim with the command output. A flake is proven in isolation and re-run — never absorbed into a green summary, never "fixed" by touching unrelated code (the known tests/phase2_net_limits.rs flake is the canonical example). Negative results get ledger rows, not silence.
  10. Memory lock. AGENTS.md + the full_plan.html ledger are the memory. Read the step's GR-n/SEC-n context before starting. Never ask the owner to re-explain what the ledger already records.
  11. Environment lock. tools/*.sh under Git Bash with < /dev/null; strictly sequential cargo builds (feature configs collide on target/debug/spid3r); edit .matrix/.sh files with editor tools only (PowerShell 5 re-encodes UTF-8).
  12. Commit lock. One commit per step: code + docs + plan tick + ledger row together. Push only when the owner said to; ask before committing if the owner hasn't.
What "fast like Rust or Node.js" honestly means here — the measured trajectory. This plan does not promise parity; it sequences the engineering that closes the gap and binds every claim to a measurement:
  • R1–R4 horizon (no owner decision needed): Tier-B targets are set at first measurement, then met or retired openly — prime AOT currently 4.23× off Rust → target ≤3.0×; json 8.46× off Node → ≤5.0×; map 17.93× → ≤6.0×; proposed selfhost lex target ≥2.0 MB/s (current 0.733 MB/s at benchmark.html:942, Tier-A floor 0.192 MB/s); AOT RSS measured on the request-loop workload (R4.2; reclamation itself is DP-1-gated because the hazard analysis killed per-call arenas — see R4).
  • DP-1 horizon (owner decision): Value v2 (tagged pointers / inline scalars) is the path to ≤2–3× off Rust/Node on compute and to unboxed containers (R10.3). Without it the plateau is real and permanent; with it, R10.3's monomorphizer is the biggest single lever.
  • Node-level web capability: R2 (evented I/O) + R5 (TLS server, keep-alive, chunked, streaming) deliver the capability; its performance is whatever http_echo/http_json measure on the same host against the Node baseline — first measured, then floored, then improved.
  • The anti-fake rule governing all of it: every speed statement in the ledger must be reproducible by the commands in Appendix A on the commit that claims it. A claim that cannot be reproduced is treated as a false result (Rule 2) and reverted.
Production-grade bar — identical for every track (web, daemon/CLI, container, OS). A track is production when ALL of the following hold, verified by objective commands — never by narrative: (1) CI-objective tests (for containers: real image pulled from a fixture registry, run, killed, removed, exit codes exact; for the OS: deterministic QEMU boots with serial-output assertions); (2) checksummed artifacts (SEC-B); (3) a written threat model + security review for every privileged operation (DP-7 surface); (4) fuzz targets over every parser touching untrusted bytes (SEC-C); (5) docs whose claims pass verify_doc_claims.js; (6) zero stubs/placeholders, verified by the no-fake rules above; (7) an append-only ledger trail for every step. Nothing in this plan is labeled an experiment; later sequencing means more prerequisites, not a lower bar.
