0. PURPOSE & SCOPE
--------------------------------------------------------------------------------
You asked for (a) a scalable system architecture for a large-scale programming
language, (b) long-term development planning, and (c) the full set of issues
that should be fixed. This document is the deliverable.

It is based on a direct read of the repository at commit state 2026-10-22:
  - 44,797 lines of Rust across 49 source files (single crate `spid3r`,
    library target `spid3r_lang`).
  - 680 automated tests, 25 differential examples, 3 fuzz targets, a 3-engine
    differential gate, and an LLVM AOT + webview GUI + wasm target.
  - A recent (2026-10-18 → 10-21) multi-round audit that fixed ~80 critical/
    high bugs and left a small, well-documented residue (A-13 closure-cycle
    leak now closed; a few parity/feature gaps remain — see §5 / ISSUE_BACKLOG).

This report does NOT re-litigate the already-fixed bugs. It assesses
ARCHITECTURE-LEVEL scalability and prescribes the structure and sequencing to
take Spid3r from "a solid single-crate interpreter + VM + AOT" to "a language
platform that can absorb many backends, a package ecosystem, web/CMS/ERP
workloads, and untrusted-script embedding without N-fold re-implementation
cost."

1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
Strengths to preserve (do not regress):
  - The `lower` seam (src/lower/mod.rs) is the correct idea: one place where
    syntactic sugar is desugared before ANY backend runs. Keep investing here.
  - `value::collections` (9,284 LOC — the largest module) is the single source
    of truth for data semantics. Both engines + AOT delegate to it. This is the
    right pattern and is why tree/vm parity is tractable today.
  - The differential test harness (tree == vm == exec) is excellent. It must
    become the GATING contract for ALL backends, not just two.
  - Zero third-party-dependency core policy is a real asset for embedding and
    supply-chain trust. Keep it, but make dependencies opt-in behind features.

Top 5 recommendations (highest leverage first):
  R1. MAKE THE BYTECODE `Chunk` THE ONE PORTABLE IR. Today the Native/AOT
      backend consumes the AST and re-implements control flow, closures,
      classes, `super`, error propagation (5,159 LOC, AST→LLVM). Every new
      backend therefore re-implements the whole semantics. Converge everything
      on `AST → lower → Chunk`, then have Native/LLVM, wasm, and any future
      backend consume `Chunk`. This is the single highest-leverage change:
      it turns "N backends × full semantics" into "1 frontend + N thin codegens."
  R2. SPLIT THE MONOLITH INTO A WORKSPACE OF CRATES. A single 45k-LOC crate
      couples compile units, slows iteration, and lets subsystems leak into
      each other. Decompose into frontend / value / vm / codegen / stdlib /
      runtime / pkg / lsp / cli with strict public-API boundaries. This also
      makes the embedding API depend only on what it needs.
  R3. REPLACE THE BLOCKING, TLS-LESS NETWORKING with an async I/O core before
      advertising CMS/ERP/web-server usage. Blocking TCP/HTTP with no TLS is a
      non-starter for production web workloads and is the biggest mismatch
      between the new `web.matrix` framework and real deployment.
  R4. PLAN THE GC FOR CONCURRENCY. The current collector quiesces all threads
      (statement-boundary, single-global mark-sweep). As task counts grow, the
      global stop-the-world gate is a throughput ceiling. Budget a generational
      / per-heap design before it bites.
  R5. ADD RESOURCE METERING + A SANDBOX CONTRACT for the embedding API. The
      embed API runs host scripts on a 512 MiB worker but has NO CPU-time,
      instruction-count, or syscall budget. For untrusted plugins this is an
      availability/security hole. Make a capability model explicit.

These five are the spine of the roadmap in §4.

2.2 Data / control flow (today)
    source ──▶ lexer ──▶ parser ──▶ semantic ──▶ lower ──▶ AST(lowered)
                                                              │
                  ┌───────────────────────────────────────────┼───────────────┐
                  ▼                       ▼                    ▼               ▼
            tree interpreter      bytecode compiler      NATIVE/AOT          wasm
            (consumes AST)        (AST→Chunk)→VM         (consumes AST →     (reuses
                                   (+optimizer)          IR→LLVM)            tree & VM)
                  │                       │                    │               │
                  └───────────▶ stdout/stderr ◀────────────────┴───────────────┘
                  (each engine independently implements control flow, closures,
                   classes, super, error propagation, `?`, callbacks)

2.3 What is working well (preserve)
    - Single front-end shared by all engines (lexer/parser/semantic/lower).
    - `lower` is the only place sugar is desugared; fast-path returns borrowed.
    - `value::collections` centralizes data semantics → engines stay thin.
    - Differential gate (tree==vm==exec) catches cross-engine drift.
    - Bytecode validator + bounds-checked deserializer (no host panic).
    - Security hardening already strong (path-traversal, archive, git-transport,
      crafted-bytecode rejections).
    - LSP reuses the same checker/formatter → editor cannot disagree with CLI.

2.4 Scalability risks (the core of the review)
    R1 Monolithic crate. One 45k-LOC crate; no enforced API boundaries; a change
       in `value` recompiles everything; embedding consumers pull the whole CLI.
    R2 N-engine semantic multiplication. tree + vm + native + wasm each implement
       control flow / closures / classes / `super` / `?` / callbacks. Language
       feature cost grows ×(number of backends).
    R3 Native re-implements the pipeline. native/ (5,159 LOC) takes the AST and
       emits LLVM IR directly — a second full semantics. `super`, class-in-fn,
       and HOF callbacks are unsupported there (parity gaps that will widen).
    R4 GC global-quiescence ceiling. Collection is safe only when the caller is
       the sole RUNNING thread; under many tasks this serializes progress.
    R5 I/O model mismatch. Blocking TCP/HTTP, no TLS, no async runtime — the
       very thing the new web/CMS framework needs to scale.
    R6 Package ecosystem gaps. Local registry only; no remote/HTTP registry, no
       package signing, no content-addressed storage, no transitive resolution.
    R7 LSP/incremental gaps. Full-document sync (no incremental), missing
       rename/references/semantic-tokens/signature-help/code-actions.
    R8 No resource metering for embedded/untrusted scripts. 512 MiB worker but
       no CPU/instruction/syscall budget → DoS surface.
    R9 Robustness of locking. Pervasive `.lock().unwrap()`; a poisoned mutex or
       panic-under-lock can wedge a long-running host.
    R10 Stdlib monolith + no versioning. `stdlib/mod.rs` is large; stdlib has no
       module namespaces (`import "std/net"`), no per-version compatibility.
    R11 Test/CI matrix growth. Differential correctness is great but perf is
       gated manually; no perf-budget CI; native CI only on one platform/subset.
    R12 No bytecode stability policy. `.matrixc` format promises no cross-release
       compatibility; needed for a deployment/distribution language.
    R13 Observability vacuum. Only `eprint`; no structured logging/metrics/trace
       facade for operators of long-running services.

3. TARGET ARCHITECTURE (TO-BE)
--------------------------------------------------------------------------------
3.1 PRINCIPLE: ONE IR TO RULE THEM ALL
    Promote the bytecode `Chunk` to the project's single PORTABLE INTERMEDIATE
    REPRESENTATION. The front-end produces exactly one artifact; every execution
    target consumes it.

    source ─▶ lexer ─▶ parser ─▶ semantic ─▶ lower ─▶ Chunk (canonical IR)
                                                              │
            ┌─────────────────────────────────────────────────┼───────────────┐
            ▼                  ▼                ▼             ▼                ▼
        tree "oracle"      stack VM        LLVM/AOT       wasm            (future: JIT)
        (debug/ref only)    (default)       codegen        codegen        codegen
                                   all consume `Chunk`, never the raw AST

    Consequence: language features are implemented ONCE (in `lower` + `Chunk`
    compiler + `value`). Each backend is a *code generator over Chunk*, not a
    re-implementation of the language. Native/AOT shrinks from 5,159 LOC of
    parallel semantics to a `Chunk → LLVM` emitter.

3.2 Proposed crate decomposition (workspace)
    spid3r-frontend   lexer, parser, ast, semantic, lower
    spid3r-ir         Chunk, OpCode, validator, serializer (.matrixc), optimizer
    spid3r-value      Value, collections, GC            (the semantic source of truth)
    spid3r-vm         stack VM executing Chunk
    spid3r-codegen-llvm  Chunk → LLVM (feature "native")
    spid3r-codegen-wasm  Chunk → wasm (feature "wasm")
    spid3r-runtime   sched, environment, modules, embed API, resource metering
    spid3r-stdlib    natives, json/csv/datetime/regex/net/db/web
    spid3r-pkg       manifest, install/vendor/registry/lockfile/tar/sha256
    spid3r-lsp       language server (depends on frontend + semantic + stdlib)
    spid3r-cli       subcommand dispatch + binaries
    spid3r (meta)    workspace root; `spid3r_lang` lib re-exported for embedders

    Boundaries enforced by `pub use` of a minimal API per crate; `cargo build`
    of the core stays dependency-free.

3.3 Layered view
    ┌──────────────────────────────────────────────────────────────┐
    │ Tooling:  CLI · LSP · REPL · Debugger · Formatter · Profiler   │
    ├──────────────────────────────────────────────────────────────┤
    │ Libraries: stdlib · pkg/registry · embed API · web framework   │
    ├──────────────────────────────────────────────────────────────┤
    │ Runtime:  scheduler · GC · environments · modules · metering   │
    ├──────────────────────────────────────────────────────────────┤
    │ Execution: tree(oracle) · VM · LLVM-AOT · wasm  — all on Chunk │
    ├──────────────────────────────────────────────────────────────┤
    │ IR:  Chunk (validator · optimizer · serializer)                │
    ├──────────────────────────────────────────────────────────────┤
    │ Frontend: lexer · parser · semantic · lower                    │
    └──────────────────────────────────────────────────────────────┘

3.4 Engine Contract & Conformance Harness
    Define a machine-checked "Engine Contract": for a fixed Chunk, every backend
    MUST produce identical observable behaviour (stdout, stderr phase+message,
    exit code, and a defined side-effect set). `tests/engine_matrix.rs` already
    asserts EXPECTED output; elevate it to the universal gate so adding a backend
    = passing the contract. This caps feature cost at ×1 regardless of backend count.

3.5 Scalable runtime (three workstreams)
    - Async I/O core: an event loop + non-blocking TCP/TLS + async task model;
      the blocking `net` API becomes a sync adapter over it.
    - Generational / per-heap GC: young generation for short-lived values,
      incremental marking to shrink the quiescence window; keep the statement-
      boundary auto-collect as the safe fallback.
    - Resource metering: instruction-count + wall-clock + allocation budgets and
      a capability/sandbox descriptor for the embed API (deny-by-default natives,
      explicit grants). Enables safe untrusted plugins.

3.6 Packaging & distribution
    - Remote registry protocol (HTTP), content-addressed store, signed packages
      (Ed25519), lockfile with hashes (already has git-commit pinning — extend).
    - Multi-arch native binaries; container + system-package (deb/rpm/brew)
      distribution; `dist` produces self-contained artifacts.
    - Bytecode stability: versioned `.matrixc` header; a compatibility promise
      for a major-version window.

3.7 Horizon (research, not committed)
    Tracing/JIT over Chunk for hot loops; distributed/actor deployment; polyglot
    FFI; WASM-component-model target. All become cheap BECAUSE everything is on Chunk.

4. LONG-TERM ROADMAP (phased, with exit criteria)
--------------------------------------------------------------------------------
PHASE A — Consolidate & de-risk  (0–3 months)  [preserve what works]
  Goals:   freeze the Chunk IR as the contract; begin crate split behind the
           existing `spid3r_lang` lib; close known parity/feature gaps; add
           perf-budget CI; write the stability policy.
  Exit:    `lower`+Chunk are the only semantic entry point; native gap issues
           (super/class-in-fn/HOF) either fixed or explicitly scoped & tested;
           perf regression CI green; bytecode version header shipped.
  Issues:  ARC-01..04, PAR-01..06, CI-01..03, DOC-01.

PHASE B — Scale the engine  (3–9 months)  [the R1/R2 payoff]
  Goals:   Native/AOT consumes Chunk (not AST); register/threaded VM experiment;
           generational GC pilot; async I/O core + TLS; resource metering MVP.
  Exit:    adding a language feature touches ≤2 crates; native parity ≥95% of
           examples; a concurrent web server sustains load on async I/O; an
           untrusted embed script is CPU/memory-bounded.
  Issues:  ARC-05..08, PERF-01..05, CONC-01..04, SEC-01..03.

PHASE C — Ecosystem & distribution  (6–15 months)
  Goals:   remote registry + signing + content-addressing; stdlib modularization
           + versioning; full LSP (incremental, rename, refs, semantic tokens,
           signature help, code actions); self-hosted package manager; containers.
  Exit:    `spid3r install <pkg>` from a remote registry with verified signatures;
           LSP feature-complete; stdlib importable by module path with semver.
  Issues:  PKG-01..05, STD-01..04, TOOL-01..05, ARC-09.

PHASE D — Production hardening  (12–24 months)
  Goals:   JIT pilot over Chunk; observability (logging/metrics/trace); fuzzing
           expansion; multi-platform native CI; security audit of sandbox; docs
           generated from source; governance/release process.
  Exit:    a reference web/CMS app runs in production with metrics + safe plugins;
           full differential + fuzz + perf gates on every PR; published stability
           & security policy.
  Issues:  PERF-06, CONC-05, SEC-04..06, CI-04..06, DOC-02..04.

PHASE E — Horizon  (24 months+)
  Goals:   distributed/actor runtime; WASM-component target; polyglot FFI;
           self-hosting compiler.
  Issues:  ARC-10, research track.
