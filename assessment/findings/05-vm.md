## 结论摘要

The backend is in much better shape than a typical hobby VM: every `exec` entry point validates the chunk,
all operand readers are bounds-checked, int arithmetic is deliberately `wrapping_*` in BOTH engines (so the
optimizer's folding and the interpreter agree), and the try/finally unwinding state machine is carefully
engineered. However, the verifier has two holes that let a hostile/corrupt `.matrixc` panic the process
despite the module's own "never a panic" contract, the compiler has one silent-wrap bug class it explicitly
fixed for `patch_jump` but not for `Try` offsets, and jump-target validation is quadratic. Overall: 高置信
on all findings below; none are speculative.

## Findings (ranked by severity × confidence × user impact)

### F1 — HIGH / certain: run loop indexes `code[ip]` unchecked; validator has no "last instruction is a terminator" rule → hostile `.matrixc` panics the VM
- **Evidence:**
  - `src/vm/mod.rs:433`: `let b = self.frames[nf].func.chunk.code[ip];` — direct index, no `ip < code.len()` guard, inside an unconditional `loop`.
  - `src/vm/bytecode.rs:1009-1123` (`validate_chunk_inner`): validates opcodes, operand truncation, constant/function/class refs, and jump targets — but nothing prevents a chunk whose final instruction falls through past the end (e.g. `code = [GetLocal 0]`: decode advances ip 0→2 = len, validate passes).
  - The module's own contract claims otherwise: `src/vm/bytecode.rs:999-1004` — "rejects … all with a clean `Diagnostic` rather than a panic or undefined behaviour."
- **Attack/impact:** `spid3r exec crafted.matrixc` with any chunk ending in a fall-through op → Rust `index out of bounds` panic (process abort-level failure, no Diagnostic). A single-byte truncation of a normal file can also produce this class (chunk ends mid-… no — truncation is caught by the decode loop; only a *well-formed but non-terminated* chunk triggers it).
- **Fix direction:** bounds-check `ip` at the top of `run_loop` (clean `fail("fell off end of bytecode")`), and/or add a terminator rule (last op ∈ {Return, Throw, Jump}) to `validate_chunk_inner`. Note the fast-path jumps (`mod.rs:506-560`) set `ip` to validated targets only, so the loop-head guard is sufficient.
- **Confidence:** certain (both sides read; entry points confirmed: `run_compiled` validates at `mod.rs:274`, `run_module` at `mod.rs:316`, `run_module_from_func` at `mod.rs:2317-2323` — the panic survives validation).

### F2 — HIGH / certain: `span_at` indexes `inst_spans` unguarded; deserializer loads `inst_offsets`/`inst_spans` as independent counts and validate never checks them → error attribution panics on hostile file
- **Evidence:**
  - `src/vm/bytecode.rs:388`: `self.inst_spans[lo - 1].clone()` — binary search walks `inst_offsets`, then indexes `inst_spans` with no length or sort check.
  - `src/vm/bytecode.rs:852-861`: deserializer reads the two counts independently (`r.count(8)` / `r.count(32)`) — a file with `inst_offsets=[0]`, `inst_spans=[]` deserializes fine.
  - `src/vm/bytecode.rs:1009-1123`: `validate_chunk_inner` never inspects either array.
  - Panic reachability: every error funnel calls it — `fail()` → `cur_span()` (`src/vm/mod.rs:2444-2451`, `2437-2443`) and `capture_trace()` per frame (`src/vm/mod.rs:1721-1728`). So: hostile file + *any* runtime error (even `1/0`) → panic instead of the intended VmError/Diagnostic.
- **Secondary:** unsorted `inst_offsets` (not checked) corrupts span attribution silently (wrong line in errors/traces) even when lengths match.
- **Fix direction:** in validate: `inst_offsets.len() == inst_spans.len()`, `inst_offsets` strictly increasing, `inst_offsets[0] == 0`, last offset < code.len(); or make `span_at` use `inst_spans.get(lo-1).unwrap_or(pending_span)`.
- **Confidence:** certain.

### F3 — MEDIUM / high: `compile_try` patches Try handler offsets with unchecked `as i16` casts — the exact bug `patch_jump` was fixed for
- **Evidence:**
  - `src/vm/compiler.rs:840`, `:843`, `:859`, `:862`: `patch_i16(try_pos + 3, (catch_target as i64 - operand_end as i64) as i16)` (and finally variant) — silent wrap when the try/catch/finally body emits > ~32 KiB of bytecode between the `Try` op and its handler.
  - Contrast: `src/vm/compiler.rs:1401-1409` (`patch_jump`) returns a Diagnostic on i16 overflow, with the comment "a function body larger than 32 KiB would previously wrap silently and produce a mis-jumping chunk".
- **Impact:** two outcomes. (a) Wrapped target lands off-boundary/out-of-range → `validate_chunk` rejects at load with a *misleading* "invalid jump target" error (bytecode.rs:1117-1122 — Try offsets are checked as jump targets, `bytecode.rs:1104-1110`). (b) Wrapped offset happens to land on a valid instruction boundary inside the body → chunk validates and **mis-executes**: the exception jumps into the middle of the try body. (b) is plausible in large functions full of same-sized instructions.
- **User impact:** a program whose try block is >32 KiB of emitted code (large generated dispatch tables, long literal-heavy catch blocks) silently corrupts control flow or fails to load; nothing warns.
- **Fix direction:** route the four Try patches through the same `i16::try_from` check as `patch_jump`.
- **Confidence:** the silent-wrap code path is certain; outcome (b) requires the wrapped offset to land on a boundary (not demonstrated by execution, but structurally possible — flagged as such).

### F4 — MEDIUM / certain (complexity): jump-target validation is O(jumps × instructions) — quadratic DoS on `exec`
- **Evidence:** `src/vm/bytecode.rs:1117`: `!starts.contains(&(target as usize))` — linear scan of `starts` per jump.
- **Impact:** a hostile `.matrixc` packed with `Jump` instructions (3 bytes each; ~3.5 M of them in a 10 MB file) makes `validate_chunk` perform ~10¹³ comparisons before the first instruction runs — minutes-to-hours of CPU for one `spid3r exec`. Also degrades legitimately huge generated functions at every load.
- **Fix direction:** `HashSet<usize>` for `starts`, or since both `starts` and sorted targets are monotone during the scan, a merge/two-pointer pass; O(n).
- **Confidence:** certain on code; impact figures are arithmetic estimates, not measured.

### F5 — LOW-MEDIUM / certain on code, reachability depends on siblings: compiler panics (`expect`) on `break`/`continue` outside a loop instead of diagnosing
- **Evidence:** `src/vm/compiler.rs:477` `.expect("break outside loop")`, `:487` `.expect("continue outside loop")`; sibling invariants: `:531`, `:645`, `:715` (`loops.pop().unwrap()`), `:298`, `:888` (`compilers.pop().unwrap()`).
- **Impact:** the compiler is the last line of defense before bytecode exists; if any path compiles without the semantic pass rejecting `break` at top level (semantic/ is owned by siblings — I did not audit whether every compile entry runs `semantic::check_file` first), a user's `break;` outside a loop becomes a Rust panic instead of a Diagnostic. Invariant-backed expects are fragile to future edits.
- **Fix direction:** return `Err(Diagnostic::at(...))` on empty `loops` (cheap, removes the cross-crate coupling).
- **Confidence:** certain on code shape; reachability not fully audited (out of my boundary) — hence LOW-MEDIUM.

### F6 — LOW / certain: `emit_const` wraps the constant-pool index at 65,536 — silent miscompile; no pool/function/class limit exists
- **Evidence:** `src/vm/bytecode.rs:314-321` (`Chunk::emit_const`): `let idx = self.constants.len() as u16;` and reuse path `return i as u16;` — no check against `u16::MAX`. Grep across `src/vm/compiler.rs` finds limit checks for locals (255, `:187-191`), args (255, `:209-213`), captures (128, `:302-308`, `:895-901`), list literals (255, `:995-1001`) — but **none** for constants/functions/classes, whose indices are u16 operands (`Constant`, `Closure`, `Class`, `Invoke` name idx).
- **Impact:** constant #65536 in one function gets index 0 → wrong value used at runtime; `validate_chunk` passes (index 0 is valid), so the miscompile is silent. Requires >65,535 distinct constants in a single function (plausible with generated string tables), or >65,535 nested functions/classes.
- **Fix direction:** same style of Diagnostic as the other limits ("too many constants in one function (max 65535)").
- **Confidence:** certain (code); reachability low.

### F7 — LOW / certain: serializer roundtrip nits — no trailing-byte check, lossy UTF-8, unbounded recursion depth
- **Evidence:**
  - `src/vm/bytecode.rs:969-994` (`deserialize_vmfunc`): magic (`:976`), version (`:985-993`), and all reader bounds are checked (`:714-775`, incl. `checked_add` at `:750` and the count() DoS guard at `:768-775`, `code_len ≤ remaining` at `:830-833`) — good — but the function returns `get_vmfunc(&mut r)` without checking `r.p == b.len()`: appended garbage after the script is silently accepted. Cosmetic-to-moderate: a "validated" file that isn't the file you think.
  - `src/vm/bytecode.rs:752`: `String::from_utf8_lossy` — a corrupt constant string roundtrips to replacement chars instead of erroring (constant value changes silently).
  - Recursion: `get_chunk → get_func_proto → get_chunk` (`:829-878`, `:880+`) and `validate_chunk_inner` recurse unbounded; a crafted deeply-nested file (~30 bytes/level) can exhaust the host stack → Rust stack-overflow abort, not a clean Diagnostic. Note the interpreter runs on a large-stack thread (`src/interpreter/mod.rs:183-185`) — the deserializer's caller would need the same treatment or a depth cap.
- **Confidence:** certain on code; the abort scenario not executed.

### F8 — LOW / certain: crafted-but-valid bytecode can desynchronize handler/stack state without panicking (verifier scope limit)
- **Evidence:** `OpCode::EndTry` pops the top handler with no frame match check (`src/vm/mod.rs:1516-1518`); `EnterFinally` mutates whatever handler is on top (`:1459-1461`); `validate_chunk` does not model handler/stack pairing (it cannot without a stack-depth simulation). A hostile chunk can EndTry across frames → later `unwind` (`:2016-2120`) truncates/jumps the *current* top frame using a dead frame's `stack_len`/`catch_target` — misattribution and data loss, though all jump targets remain validated (no panic; `unwind`'s `stop`-boundary logic at `:2023-2046` still holds).
- **Impact:** corrupt execution of a hand-crafted file only; normal compiler output always pairs Try/EndTry (`src/vm/compiler.rs:795-864`). Worth one line in the spec: validation guarantees no panic *for most* shapes, not full behavioral safety.
- **Confidence:** certain on code; no panic demonstrated because targets are pre-validated.

### F9 — LOW / certain: minor optimizer/VM nits (no wrong behavior found)
- `src/vm/opt.rs:466-467` rebuilds `inst_offsets`/`inst_spans` correctly, but a jump target pointing past the last instruction maps to `code.len()` via the forward-fill (`next_new = new_off`) — validate rejects `target >= len` (bytecode.rs:1117), so such a chunk would fail *after* optimization; only reachable if the compiler already emitted a past-the-end target (it doesn't — `patch_jump` checks).
- `src/vm/mod.rs:1765-1776` `flush_pending_str` unwraps a `Mutex` lock — a poisoned cell (panic in a spawned task sharing that cell) turns a caught error into a panic. Cosmetic given tasks already isolate panics.
- Debugger breakpoints on the current line don't re-fire in a loop iteration (`src/vm/debug.rs` hook: `line != state.last_line`); stepping semantics otherwise sound (Over/Finish use frame-depth tracking).

## What is SOUND (verified, not assumed)

1. **`spid3r exec` validates before running.** All entry points call `validate_chunk` first: `run_compiled` (`mod.rs:274`), `run_module` (`mod.rs:316`), embedded modules via `run_module_from_func` (`mod.rs:2317-2323`). `validate_chunk_inner` recurses into nested functions/class methods (doc `bytecode.rs:999`), so spawned-task functions (`run_function`, `mod.rs:340-343`, no own validation) are transitively covered.
2. **Operand/constant reads cannot panic on any validated chunk.** `code_u8/u16/i16`, `const_at`, `func_proto_at`, `class_proto_at` all use `.get()` with safe fallbacks (`mod.rs:2397-2435`); stack underflow (`pop_top`/`pop_n`, `mod.rs:1779-1800`) and the `Return` underflow case (`mod.rs:1380-1390`) route into the error funnel; runtime jump handlers re-check targets (`mod.rs:899-940`). The GetLocal/Add/Less superinstruction fast paths (`mod.rs:468-590`) only fire on complete, validated instruction patterns, read slots via `.get()`, and guard the dst write (`dst < slots.len()`); the one hard `code[ip+3]` at `mod.rs:474` is in-bounds whenever the pattern matches a validated chunk.
3. **Optimizer is behavior-preserving on all four requested axes** (acceptance b):
   - *Integer overflow*: folding evaluates via `vm_eval_binary` (`opt.rs:213`) which wraps (`mod.rs:2485, 2502, 2513, 2525, 2538`) — identical to the interpreter (`src/interpreter/mod.rs:957, 991` also `wrapping_add/mul`; `Neg` wraps at `interpreter/mod.rs:714` = `mod.rs:2586`). Folded and unfolded programs observe the same wrapped value.
   - *Float NaN/inf*: division/modulo by zero (int or float) return `Err` → never folded (`mod.rs:2522-2524, 2535-2537`; `opt.rs:211-213` "an error here must still surface at run time"); NaN comparisons yield `None` ordering → `Err` → not folded; `inf` results fold only because the unfolded program produces the same `inf`.
   - *String ops*: folding uses the same `vm_eval_binary` `Add`/`Lt` string arms the VM executes; string `Lt` is byte-wise `cmp` in both engines.
   - *Short-circuit / branch rewriting*: `[bool][JumpIfFalse/True]` folding keeps stack balance and only fires when no label points into the pair (`opt.rs:254-304`); `[Not][JumpIfFalse]→[JumpIfTrue]` and `[Not][Not]→[Truthy]` (`opt.rs:306-340`) are exact because `Not = !truthy` is total in both engines (`mod.rs:2583-2584` = `interpreter/mod.rs:712`); `Loop`/`Try` chunks skip dead-code elimination (`opt.rs:18-20`); all offset rewrites are all-or-nothing with an i16 re-check (`opt.rs:22-25`, encode `:470-500`); `is_foldable` keeps the pool serializable (`opt.rs:541-545`, Bool/Null become dedicated opcodes).
4. **Jump/loop patching for break/continue is correct** (acceptance d): `patch_jump` is i16-checked with clean diagnostics (`compiler.rs:1401-1412`); continue targets the increment for `for-in` (`compiler.rs:703-710`) and the condition for `while`; break/continue pop only body locals above `LoopInfo.locals_base`, leaving `for-in`'s three machinery slots intact, and break lands *before* the final Uncapture/Pop cleanup (`compiler.rs:528-545, 642-660, 712-730`); `Uncapture` runs per-iteration at `start`. Closures: 7-bit upvalue encoding limits enforced (128 own captures, `compiler.rs:299-308, 889-901`).
5. **Return through try/finally** is correctly deferred: `Return` inside try/catch parks the value in `pending_return`, jumps to the finally block (`mod.rs:1399-1420`), and `EndTry` chains nested finallys before completing the return (`mod.rs:1516-1560`); explicit break/continue runs finallys inline via compiler-emitted `EnterFinally`+`EndTry` (`compiler.rs:757-800`); `unwind` respects the `stop` boundary so outer-run handlers are not consumed by nested sync calls (`mod.rs:2023-2046`, Invariant #3 comment).
6. **Call depth** capped at 1,000 with clean error (`mod.rs:44`, `call_vfunc_frame` `:1816-1826`) — matches the interpreter's limit.
7. **Serializer head**: magic + version checked (`bytecode.rs:970-993`), reader fully bounds-checked incl. checked arithmetic (`:714-775`, `:830-833`).
